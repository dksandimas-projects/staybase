## 1. Verdict

**Feature-complete. NOT production-ready.** The pass has now found and shipped
**fifteen** production-breaking defects, of which **six** were revenue-path
blockers that were invisible on the admin dashboard because the data behind them
was never written or never read.

**Phases P3–P5 closed out the pass and roughly doubled the finding count.** The
three later phases (finance/backup/kitchen/store · intercom/notifications/SEO ·
cross-cutting security) found a further **27 distinct findings**, including **two
P0/P1 defects that are still live in production right now**: the **kitchen list
is permanently empty** (the chef's sheet shows zero meals on every service date,
and 13 meals are booked across 7 dates), and the **MRB-11 money identity is
never asserted at the write boundary** (so `revenueAllocation.totalNet` silently
disagrees with `totalPrice` — the add-on money, the senior discount and the
corporate bookings are all affected). A security phase also found the
**reservation-ref email path skipped the guest credential check**, which let an
unauthenticated caller resolve a booking and fire guest emails.

The single most important structural finding: **5,514 green tests did not catch
any of the original six defects.** The suite is ~99% source-text regex assertions
that never execute a React component and never run a real Firestore query. Two of
the six (the rewards 500 and the Daily Close blank ledger) are exactly the class
of bug that only a real runtime can catch; both are now covered by behavioural
tests, but the systemic gap (audit finding H1) remains open.

**The systemic gap then produced a seventh class of defect the suite could not
see at all:** `guest-app/tsconfig.json` includes only `["src", "../hotel.config.ts",
"../shared"]`, so the entire `server/` directory — the whole API surface — was
outside the type-check, and the API ships via esbuild, which does not type-check
either. **Six identifiers in `guest-app/server` did not exist.** One of them
(`finalReservationId` and six siblings in the guest booking confirmation-email
view) threw a `ReferenceError` on **every guest booking create**: the booking
committed, the confirmation email never went out. There is now a test that
type-checks the server entry point and fails on any undefined identifier, so the
class cannot recur.

## 3. P0 — Production defects found and fixed (6)

All six are fixed, covered by regression tests, and **deployed to production**
— see §5 for the verification evidence.

### P0-1 · Spark Rewards registration returns HTTP 500 — every new member fails
`guest-app/server/handlers/members.ts` → `handleRegisterMember` wrote the
member-number counter *before* reading `members/{uid}/pointsHistory/welcome`
inside the same transaction. The admin SDK rejects that:
`Firestore transactions require all reads to be executed before all writes.`
So **every** `POST /api/members/register` answered 500 *"We could not join Spark
Rewards right now."* — the `/signup` and `/rewards` enrolment paths were dead in
production. Fires whenever `rewardsConfig.welcomePoints > 0` (live = 50).

**Fix:** defer the counter write until after all reads. **Test:** new
`firebase/tests/members-register-transaction.emulator.test.ts` (4 tests, Admin
SDK against the emulator — the web SDK does not enforce the ordering rule
client-side, so the test would have passed falsely).

### P0-2 · The Daily Close ledger is permanently empty — missing Firestore index
`admin-app/src/pages/ReportsPage.tsx:4635,4709` query
`collectionGroup(db,"payments"/"refunds")` with a `recordedAt` range +
`orderBy("recordedAt","desc")`, which needs a `COLLECTION_GROUP_DESC` index.
`firebase/firestore.indexes.json` had **no** `payments`/`refunds`
`fieldOverrides` in prod **or** staging. The error handler at `:4704` swallows
it, so the table renders *"No transactions recorded on this date."* while the
method breakdown (no orderBy ⇒ auto-indexed) correctly shows the day's totals.
The over-refund guard and the cash-denial path sit behind the same dead query.

**Fix:** 2 `fieldOverrides` added to `firebase/firestore.indexes.json`
(17-line diff). **Requires a Firestore index deploy** — see §5.

### P0-3 · The corporate inquiry form is dead — the whole B2B lead funnel 400s
The public form (`guest-app/src/pages/CorporateStaysPage.tsx`) collects the
contact's **first + last name** and posts
`{ companyName, firstName, lastName, email, phone, numRooms, preferredDates,
specialRequirements, _hp, turnstileToken }`. It never sends a flat
`contactPerson`. The form's own comment claims *"`contactPerson` is derived
server-side as `${firstName} ${lastName}`"* — **that derivation did not exist**:
`inquirySchema` (`guest-app/server/handlers/corporate-inquiries.ts:19`) required
`contactPerson`, so every submission failed Zod validation and the endpoint
answered **400 "Please check the inquiry form and try again."**

**Confirmed in production:** `corporateInquiries` was **empty (0 docs)** — no
corporate lead had ever reached the pipeline through the public form. The
inquiry fixtures that existed were written directly by staff.

**Fix:** `contactPerson` is now optional; the handler derives it from
`firstName`/`lastName` before storing. The change is strictly *more* permissive
— a legacy client that sends `contactPerson` is unaffected.
**Test:** new `guest-app/tests/api/corp-inq-01-inquiry-name-contract.test.ts`
(5 tests) which **parses the real form's payload keys out of the form source**
and posts exactly those — so the form and the API can never drift apart again.

### P0-4 · Every refund path returns HTTP 500 — refunds are unrecordable
`guest-app/server/lib/refunds.ts` built its document references with
`transaction.firestore.collection("bookings")`. The firebase-admin `Transaction`
class has **no public `firestore` getter** (only the private `_firestore`), so
this threw
`TypeError: Cannot read properties of undefined (reading 'collection')` and
`POST /api/bookings/add-refund` answered **500** on every booking × every
amount. All four refund paths were dead (cancellation, breakfast,
other-add-on, standalone add-refund) and the over-refund guard was unreachable
behind the same throw.

**Fix:** thread the Firestore **instance** through the helper (`db: Firestore`)
and use it only for path construction; the caller's transaction still performs
every read and write. 4 call sites updated.
**Test:** new `guest-app/tests/api/crl-02-refund-transaction-firestore.test.ts`
(5 tests) that calls the real helper with a fake db + fake transaction and
asserts the resolved paths — verified to reproduce the exact production
`TypeError` when the fix is reverted.

### P0-5 · Every room type showed a red "Doesn't fit your group" on `/book`
`deriveRoomTypeCapacityFit` (`shared/utils/roomTypes.ts`) measured the fit
against `currentCartCount`. On a fresh Step 1 the cart is empty — zero capacity
— so the verdict was `"doesnt-fit"` for **every** room type, while the same
card printed *"You'd need 1 of Standard Twin for your group."* The public
booking page opened with a red "doesn't fit" chip on all four cards, on a
guest-facing funnel.

**Fix:** the helper gained a `"type"` basis (measure against the rooms the
guest would need); the room-type card uses it when the type is not yet in the
cart. The cart-line chip keeps the `"cart"` basis and the Step 1 → Step 2
submit gate is untouched (it uses `requiredExtraBedsFor`, not this helper), so
the two indicators can never disagree.
**Test:** 7 new tests in `shared/__tests__/room-types.test.ts`.

### P0-6 · Breakfast and add-on dates showed one day early, in the Philippines
`formatBreakfastDateLabel` (`guest-app/src/pages/BookingPage.tsx:356`) parsed
`new Date("2026-11-05T00:00:00")` — **browser-local** — then formatted it with
`timeZone: "UTC"`. Parse-local + format-UTC is a guaranteed one-day mismatch
east of UTC. The hotel is in Asia/Manila (UTC+8), so **every guest booking
from the Philippines saw breakfast and add-on dates one day early**, including a
first breakfast "on" a date before check-in. The OCT-H2 audit (2026-10-20)
fixed the sibling *enumerator* with the same `Z` anchor but missed the
*formatter*, so the shift survived the fix. The admin's own counterparts
(`ManageBreakfastPage.tsx`, `ManageOtherAddOnsPage.tsx`) already anchor with
`Z` — so **the guest and the kitchen saw different dates for the same booking**.

**Fix:** the formatter moved to `guest-app/src/utils/formatBreakfastDateLabel.ts`
(own module, following the repo's own `formatCutoffTime.ts` precedent) with
the `Z` anchor. **Test:** new
`guest-app/tests/api/br-03-breakfast-date-label.test.ts` (9 tests) that pins
the timezone per case — verified to fail 6/9 with the old parse, reproducing
the production `Nov 4 (Wed)` for a `Nov 5` service date.

### 5.1 Deploy recipe — the Firestore collection-group index

Two operational gotchas cost real time and are worth keeping:

1. **`queryScope` MUST be `COLLECTION_GROUP`.** A field override deployed with
   `"queryScope": "COLLECTION"` creates an **ancestor-scoped** index (the
   deployed config carried an `ancestorField` → `__default__/fields/*`), which
   does **not** serve a collection-group query. The query still fails.
2. **The Firebase CLI silently skips a `queryScope` change.** It prints
   *"Skipping existing field override"* and applies **nothing**. To change the
   scope you must deploy `"indexes": []` first (removing the ancestor-scoped
   index) and then deploy the desired scope.
3. A composite-index form is rejected by Firestore: *"this index is not
   necessary, configure using single field index controls"*.

```bash
cd /Users/danielkennethsandimas/GitHub/staybase
# step 1: fieldOverride indexes = []  (removes the ancestor-scoped index)
npx --no-install firebase deploy --only firestore:indexes --project spark-inn-prod
# step 2: fieldOverride indexes = [{ "order": "DESCENDING", "queryScope": "COLLECTION_GROUP" }]
npx --no-install firebase deploy --only firestore:indexes --project spark-inn-prod
```

### 5.2 Why `guest-app/server` was never type-checked

`guest-app/tsconfig.json` includes only `["src", "../hotel.config.ts",
"../shared"]`. The API ships through `esbuild --bundle`, which does **not**
type-check. So a reference to an identifier that does not exist compiles,
bundles, deploys, and throws a `ReferenceError` at runtime. The pass found
**42** latent type errors, of which **16 were guaranteed runtime crashes**:

| File:line | Identifier | Effect |
|---|---|---|
| `bookings.ts` (email view) | `finalReservationId`, `childBookingRefs`, `childLookupTokens`, `childPricing`, `resolvedRoomSelections`, `guestName`, `corporateDetails` | The **guest booking confirmation email** threw on every guest booking create. The booking committed; the email never went out. |
| `bookings.ts` (guest cancel) | `parsed` | The guest self-service cancel threw before it could dispatch. |
| `bookings.ts` (refund email) | `bookingReservationId` | The refund state-change email never went out. |
| `bookings.ts` (verify payment) | `bookingData` | The already-confirmed response threw instead of returning. |
| `bookings.ts` (add room) | `DEFAULT_ROOM_TYPES` | A hotel without a configured room-type catalog crashed. |
| `corporate-inquiries.ts` | `actualBreakfastRate` | Latent — the ternary short-circuited on an always-false flag. |

The remaining 26 errors are type-narrowing / duplicate-binding issues that
esbuild ignores at runtime (two duplicate import bindings — a `SyntaxError`
under native ESM — were removed at the same time).

The new guard test (`guest-app/tests/api/rpt-05-server-undefined-identifiers.test.ts`)
type-checks the server entry point and fails on **any** `TS2304` / `TS2552` /
`TS18004` / `TS2448` (undefined identifier) or `TS2300` (duplicate binding). It
costs ~4s. It is the reason the class cannot recur.
