## 4. RESOLVED — root cause found, fix written and tested (needs deploy) — the admin Bookings LIST loses its payment-ledger projection

### Symptom

On `https://admin.sparkinnbohol.com/bookings` the quick-view chips read:

```
All bookings 69   Needs attention 10   Balance due 69   Cancelled 19
```

**"Balance due 69" means every booking in the hotel is showing an unpaid balance**, and no
row shows a "Paid" pill — including bookings that are fully paid.

**The correct value is 55.** Recomputing the admin's *exact* folio math against live
production data reproduces **55**, and it matches the QA report's own live measurement
(**14 PAID / 3 PARTIAL / 50 UNPAID**). The delta between the app and the truth is
**exactly +14 on "Balance due" and exactly +5 on "Needs attention"** — the precise
signature of an **empty payment-ledger index** (5 of those bookings are `checked-out`
with a balance, which is the only balance-dependent clause in the needs-attention
predicate).

### RESOLVED — root cause found, fix written and tested (2026-10-23, second session)

**Root cause: the listener effect depended on the `currentUser` OBJECT, whose identity
changes on every ID-token refresh — so the list's ledger listener was torn down and
re-subscribed before its first snapshot could land, and the ledger index stayed empty.**

The chain, in full:

1. `AdminContext`'s auth handler called `getIdTokenResult(firebaseUser, true)` on **every**
   `onAuthStateChanged` event. Forcing a refresh mints a new ID token; the Auth SDK fires
   `onAuthStateChanged` again for that token; the handler forces another refresh. A feedback
   loop — measured in the live browser as **five forced refreshes in ~3ms at load, then one
   every 30 seconds**.
2. Every firing built a **brand-new `currentUser` object**.
3. The Bookings LIST's ledger listeners (`collectionGroup("payments")` and
   `collectionGroup("refunds")`) listed `currentUser` in their dependency arrays, so each
   refresh unsubscribed and re-subscribed them.
4. `onSnapshot` delivers its first snapshot asynchronously. A listener re-subscribed before
   that snapshot lands never delivers one. The index stayed empty — **with no console error**,
   because nothing was denied.
5. The booking DRAWER was unaffected because its listener depends on `selectedBooking?.id` —
   a **stable primitive**. That asymmetry is the whole defect.

The list therefore read exactly what an empty index produces, which is why the drawer and
the list disagreed on the same booking.

**What was proven before landing on this** (each independently, on live production):

| Claim | How it was proven |
|---|---|
| The money math + ledger projection are CORRECT | Re-ran the admin's own `normalizeLedgerDoc` → `buildBookingPaymentIndex` → `resolveBookingOnsitePayments` → `computeBookingFolio` against production. An **empty** index reproduces the live chips exactly (**0 paid / 69 balance due / 10 needs attention**); a **populated** index reproduces the QA truth exactly (**14 / 55 / 5**). |
| The deployed bundle is byte-identical to a fresh build of this source | Built `admin-app` locally and diffed it against the deployed `index-Df4l67CC.js`: **3,769,151 bytes each, 39 differing bytes total** (the Firebase API key + one jsPDF string). The whole RPT-01 region is bit-for-bit the source. |
| The rules allow the group read | A real staff token (`role: front-desk`) reading `collectionGroup("payments")` through the **client** SDK returns all **20** payments, no error. |
| The listener is NOT denied in the browser | A denied collection-group query calls the error callback with `permission-denied` and delivers **no** snapshot (measured). The live app logged **no** such error — only an unrelated `calls`/`callSessions` denial. |
| The `getIdToken(true)` handshake was NOT the cause | The client SDK's group listener delivers all 20 docs **without** any handshake. The handshake was a red herring; suspicion #1 in the old list is **disproved**. |

**The fix** (in `admin-app/src/context/AdminContext.tsx`):

1. The auth handler forces the token refresh **once per uid**, not per auth event, and keeps
   the `currentUser` object's identity **stable** across refreshes (returns the previous
   object when nothing meaningful changed). This alone stops every `[currentUser]`-dep
   effect from re-subscribing.
2. Both ledger listeners now depend on the stable `currentUser?.uid` instead of the object.
3. Both ledger listeners attach with the `getIdToken(true)` handshake (parity with the
   reservations listener) **and** hydrate through a one-shot `getDocs` read, which cannot be
   starved by re-subscription timing. The listener then keeps the index live.

### NEW FINDING — the front desk's incoming-call listener is denied in production

Found in the live browser console while diagnosing the ledger defect (the only console
error on the admin Bookings page):

```
Error listening to WebRTC calls: FirebaseError: Missing or insufficient permissions.
```

`AdminContext` listens on `collectionGroup(db, "callSessions")` to raise the desk's
incoming-call banner. The rules file grants that collection group **nothing**:

- `match /callSessions/{sessionToken}` authorizes a **direct path** read of one session
  document — it does not authorize a **collection-group** query over the `callSessions`
  collection.
- A collection-group query needs the group form. The same rules file already uses it for
  the intercom inbox: `match /{path=**}/messages/{messageId}` (the `messages` group). The
  `callSessions` group has no equivalent.
- The sibling `match /calls/{roomId}/{document=**}` rule covers the **legacy** path only,
  and the app deliberately stopped reading it ("the legacy path is now staff-only, so the
  client SDK can no longer read or forge a call document").

So the desk's incoming-call listener is denied for every staff session. **This is a
separate defect from RPT-01 and is NOT fixed by the change above** — it needs a rules
change (a staff-read group rule for `callSessions`) and, per the rules-deploy discipline,
the rules must not ship ahead of the app build that depends on them.

**A rules change is a security decision — it grants staff read access to every call
session document.** It is not an agent's call to make unattended.

## 10. Pitfalls that cost time this session — do not repeat them

1. **A worktree has no `.husky/_/`.** Husky's generated shims are gitignored and live only
   in the primary tree, so **no hook runs in a worktree** — no version bump, no commit-msg
   validation, no pre-commit bundle check. Run `node_modules/.bin/husky` inside the
   worktree to install them, or bump `shared/VERSION.ts` and commit with `HUSKY=0`
   (the repo's own `scripts/amend-version-bump.mjs` uses `HUSKY: "0"` for amends).
2. **The version bump is manual in practice.** `prepare-commit-msg` bumps on
   `fix:`/`feat:`/`refactor:`/`release:` but **not** on `chore:`. Every code commit that
   touches `shared/` or `guest-app/server/` leaves the API bundle stale → a follow-up
   `chore(bundle):` commit is required. `check:api-bundle` only runs when `shared/`,
   `guest-app/server/` or `hotel.config.ts` are staged, and it **fails** if the committed
   bundle differs from a fresh build.
3. **Build the API bundle with a REAL copy of `node_modules`, never a symlink.** The
   committed bundle embeds relative `node_modules` paths; a symlinked tree produces a
   wildly different diff. Use `cp -Rc`.
4. **`git checkout main` fails inside a worktree** while the primary tree has `main`
   checked out. Merge via a temp branch and push, or merge in the primary tree.
5. **A push to `main` ALREADY auto-deploys both apps** — the guest project has a
   GitHub-Integration hook on `ref=main`. Verified 2026-10-23: every push to `main`
   produced two READY deployments per project with no manual action. **Do not also fire
   the manual Vercel hooks** — that is what created duplicate deployments during this
   session (harmless, but it makes "which deployment is live?" harder to answer). The
   hooks are the fallback for a `dev`-only push or a disconnected hook. See §9.
   Corollary: **a docs-only commit is a safe no-op deploy** — it rebuilds and serves
   byte-identical assets, because Vite hashes are content-based.
6. **`git apply --3way` silently applied only PART of a multi-branch patch** and reported
   no conflicts (the failure was hidden by piping through `head`). Integration was redone
   with **real commits + `git merge --no-ff`**, which surfaced every file. Use real
   commits; verify with `git diff --name-only <base> HEAD` and check the file count.
7. **The guest app and the admin app are different origins**, and the admin app's
   `vercel.json` catch-all rewrite answers unknown paths with **HTTP 200 + `text/html`**
   (the SPA shell). A staff API call that builds its URL from the admin origin gets a
   **200** whose `res.json()` throws. `res.ok` is meaningless when a SPA rewrite is in the
   path.
8. **A failed read must never render as an empty state.** Decisions #312, #313 and #314
   are all the same lesson. The rule lives in a PURE resolver so it is unit-tested, not
   just observable in a browser, and `error` is always checked **before** `empty`.
9. **A bare `//` inside JSX children is literal text**, not a comment — JSX paints it.
   The AST scan in `find-jsx-comment-leaks.mjs` is the structural net; a text grep
   cannot see it.
10. **A `//` inside a JS string is fine**; only JSX *children* are affected.
11. **The Firestore rules are deployed separately from the apps.** A code release that
    tightens the rules is not live until `firebase deploy --only firestore:rules` runs.
12. **The Browser tool cannot reach a background tab.** `open_tab` creates a *new* tab and
    makes it current; there is no tab-select action. In this session that meant the
    signed-in admin tab became unreachable and the owner had to switch tabs manually
    twice. **Open only the tabs you actually need.**
13. **Each browser tab has its own Firebase Auth session** here — a fresh tab lands on the
    admin login page even when another tab is signed in.
14. **Never type passwords into a browser login form.** Use an `ask_user` takeover.
15. **React controlled `<input type="date">` cannot be driven** by the Browser
    `fill`/`type` actions.
16. **Turnstile gates all public guest endpoints before schema validation**, and the
    embedded browser cannot complete it (Cloudflare `300010`) — a harness limit, not a
    product defect.
17. **Rate limits:** `POST /api/bookings/create` 5/IP/min (≥15 s apart) ·
    `validate/voucher` 20/IP/min · `bookings-addons-config` and
    `bookings-breakfast-config` 60/IP/min · `store:*` 10/IP/min.
18. **Never commit `.env` files, and never override `git user.email` / `user.name`.**
    The global config is the source of truth (`Daniel Kenneth Sandimas <
    dksandimas.projects@gmail.com>`); a commit that lands under the wrong author must be
    amended and force-pushed.
19. **The QA report's §6b table is the source of truth for what is still live.** Rows are
    marked `**FIXED — SHIPPED 2026-10-22, see §5c.**` in place rather than deleted, so the
    original measurement stays on the record. Follow that pattern.
20. **`docs:audit` has a pre-existing baseline of 18 errors / 2 warnings** (several docs
    are 2–20× over their token ceilings). Do not try to fix them as part of a feature
    batch — just do not **add** to the count.
