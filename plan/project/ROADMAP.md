(**previously shipped EXB-03 — capacity overflow rule** Per owner decision 2026-07-31 #1 + decision #145, the CHD-04 two-hard-cap validation (`numAdults > maxCapacity` + `numChildren > maxChildren`) was **wrong for rooms with extra beds**: writing it as two independent raised caps double-counts the beds and lets a room sleep more people than it has beds for. The precise rule, per the EXB-03 spec, is `max(0, adults − maxCapacity) + max(0, children − maxChildren) ≤ extraBedCount`, plus `extraBedCount ≤ maxExtraBeds` (the per-type cap, unchanged). Extra beds grant additional occupant slots usable by an adult **or** a child — the rule does not distinguish which bed serves which occupant. The single check subsumes the CHD-04 two-hard-cap shape: when `extraBedCount === 0` the rule reduces to the two hard caps; when `extraBedCount > 0` it allows overflow up to the extra bed count. **New helper** — `requiredExtraBedsFor({ numAdults, numChildren, maxCapacity, maxChildren })` in `shared/utils/roomTypes.ts` returns `{ overflowAdults, overflowChildren, requiredExtraBeds }`; the helper is the only authoritative capacity check on the three call sites (`handleCreateBooking`, `handleCreateWalkin`, `handleRescheduleBooking`). **3 call sites** — `handleCreateBooking` and `handleCreateWalkin` replace the two original `if (numAdults > typeMaxCapacity) {...}` + `if (numChildren > typeMaxChildren) {...}` hard rejects with one call to the helper; the per-type `extraBedCount ≤ maxExtraBeds` cap is preserved as the first gate so the room type's hard limit still fires before the overflow check. `handleRescheduleBooking` (which CHD deferred — see the CHD-04 roadmap note "the reschedule transaction (line 4683) gets the same split validation in a follow-up; the existing PMH-02 extraction routes the reschedule math through the shared helpers so the CHD-04 follow-up is a focused diff") gets the same overflow check in this PR, reading the existing snapshotted `booking.extraBedCount` from the doc and the new room type's `maxCapacity` + `maxChildren` + `maxExtraBeds` from the transaction's `hotelConfig` read; legacy pre-CHD bookings without `numAdults` / `numChildren` derive `numAdults = numGuests, numChildren = 0` (the historical "all guests are adults" shape). ### Pending Booking Expiry (PEX) — proposed 2026-07-31 · P1, gates MRB
> **Finding 2026-07-31, while scoping the CVQ-12 room cap.** `ROOM_OCCUPYING_STATUSES` includes **`pending`**, so a submitted-but-unpaid booking holds its room — and **no expiry or auto-cancel mechanism exists anywhere**. An abandoned booking blocks a real one indefinitely until staff cancel it by hand. `/api/bookings/create` is rate-limited to 5 requests per IP per minute, which today caps the damage at 5 rooms/minute because a booking can only hold one room.
>
> **Owner decisions (2026-07-31):** (a) **no cap on rooms per online booking** — "all if available"; (b) **yes, auto-cancel unpaid pending bookings after a set window.** These two are coherent *together*: the cap was only ever one mitigation, and expiry is the better one because it closes the vector rather than working around it. But it makes the window **load-bearing** — with no cap, the expiry window is the *only* thing bounding how long one request can hold the entire hotel. Choose it deliberately; see PEX-01.
>
> **Gates MRB.** Without expiry, an uncapped multi-room booking lets one unpaid request hold every available room forever. PEX must ship before MRB-06 exposes multi-room to guests.
>
> Record as `plan/docs/DECISIONS-FEATURES.md #147`.

- ✅ **PEX-01 — Expiry window + immutable deadline snapshot** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry` (v0.200.2). The window lives at `settings/hotelConfig.paymentHoldWindowHours`; default 24h, admin-allowed range 1..72h, normalized via the new `normalizePaymentHoldWindowHours` helper. `handleCreateBooking` writes a `holdExpiresAt` Timestamp computed at the same `now` captured at the top of the transaction (no race with a concurrent Settings change). The snapshotted deadline is byte-equivalent to whatever the cron would later compute. **`null`** for `payment-uploaded` bookings (no auto-expiry, staff-review state) and for legacy callers that omit `paymentHoldWindowHours`. **Decision** — 24h default per the PEX-08 spec's "longer window for 1–2 rooms / shorter for large groups" guidance; the admin UI is a follow-up (the data path + normalization are in place so the UI is a straightforward clone of the existing DSC Discounts tab). Recorded in `plan/docs/DECISIONS-FEATURES.md #147`.
- ✅ **PEX-02 — One authoritative occupancy policy, used everywhere** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry`. New `shared/utils/bookingOccupancy.ts` exports `isBookingOccupyingRoom(booking, now)` + the `BOOKING_OCCUPYING_STATUSES` constant. The rule: `cancelled` / `checked-out` → never occupies; `payment-uploaded` → always occupies (staff-review, never auto-expired per PEX-04); `payment-confirmed` / `confirmed` / `checked-in` → always occupies; `pending` → occupies only if `holdExpiresAt` is null (legacy) or strictly in the future. Every call site that asks "does this booking block the room?" now routes through the shared rule on top of the coarse `status in [...]` Firestore query: the public availability endpoint, the room-blocks handler, and the create / walkin / reschedule transactions. No caller may maintain its own `pending + createdAt` interpretation.
- ✅ **PEX-03 — Atomically retire an expired hold before reusing its room** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry`. The public availability endpoint displays an eligible expired hold as free (per PEX-02's shared rule). When the create / walkin / reschedule transaction finds a room with an expired `pending` hold, the same Firestore transaction cancels the hold with `cancellationReason: "payment-hold-expired"` (the `EXPIRED_HOLD_CANCELLATION_REASON` constant) and creates the replacement booking. A partial failure cannot leave the expired hold in the booking's room. **Guest B takes the room and a late payment cannot revive Guest A** — the retirement is in the same transaction as the new booking's `transaction.set`. The per-retirement `booking-cancelled` email is fired from the post-transaction path (best-effort; the cancellation reason is the discriminator the template uses to switch the headline + rebook CTA).
- ✅ **PEX-04 — Model who is expected to act; do not infer it from a stored screenshot** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry`. `payment-uploaded` is explicitly in the always-occupies set (staff is reviewing, never auto-expired). A positive net payment ledger is also out of scope (the rule keys on `status` + `holdExpiresAt`, not the ledger — the `isBookingOccupyingRoom` helper does not touch the ledger, by design; if a positive ledger is ever needed, it goes through the existing `cancel` paths, not the auto-expiry path). `handleRejectPayment` is now transactional: it reads the window from `settings/hotelConfig.paymentHoldWindowHours` in the same write and stamps a fresh `holdExpiresAt` from `paymentRejectedAt`. The retained `paymentProofPath` / legacy `paymentProofUrl` are audit evidence only and do NOT exempt the booking — the `holdExpiresAt` is the only authority. If the guest does not re-upload, the daily cron retires the booking at the new deadline.
- ✅ **PEX-05 — Immediate deadline disclosure, not an unreliable daily advance warning** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry`. The `/api/bookings/create` response payload includes `holdExpiresAt` so the Step 4 confirmation page can render "Held until X (hotel-local time)". The booking-submitted email receives the same field. The cleanup email reuses the existing `booking-cancelled` template; the `cancellationReason: "payment-hold-expired"` field is the discriminator the template uses to switch the headline + rebook CTA. **No advance-warning email** — Hobby cron precision is daily and the deadline may be shorter than 24h for large groups; we do not promise a window the deployment cannot guarantee. A proof re-upload returns the booking to `payment-uploaded` (staff-review, no auto-expiry) — that state transition is the "expiry is paused" message in the email.
- ✅ **PEX-06 — Daily cleanup cron in the authoritative deployment config** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry`. New `guest-app/server/handlers/hold-expiry.ts` mounted at `/api/holds/expire`, gated by `CRON_SECRET` (same auth pattern as the janitor sweep). ### Cancellation & Refund Lifecycle (CRL) — proposed 2026-08-01 · P1, split delivery
> Owner request 2026-08-01: define and close the gaps between cancellation, policy eligibility, refund approval, and money actually returned. **Decision #160 reserved; write the decision entry only when implementation lands.**
>
> **Investigation findings:** cancellation is transactional and releases inventory, restores voucher/corporate usage, records a reason, and sends an email; refunds are admin-only immutable negative payment entries capped at net collected. The gaps are operationally important: the guest UI only exposes cancellation for `pending` / `payment-uploaded`, while the public API accepts paid/confirmed cancellations; the editable 48-hour policy is prose and is not evaluated by the server; cancellation does not create or track a refund obligation; standard cancellations do not stamp dedicated actor/time/source fields; the cancellation email does not state the refund outcome; and `/api/bookings/add-refund` has no caller-supplied idempotency key, so a retry after an uncertain response can append a second refund.
>
> **Delivery split:** CRL-01..04 are legacy-safe and should land before MRB. CRL-05..09 are reservation-authoritative and land with the MRB items named below rather than creating a booking-owned workflow that immediately needs moving. No implementation may claim money was returned merely because a reservation was cancelled or a refund was approved—the system only marks a refund processed after staff completes the external cash/GCash/bank/other movement and records the ledger entry.
>
> **Working policy defaults pending owner validation:** 48 hours before the scheduled 2:00 PM check-in in `config.timezone`; 100% of net collected refundable at or before the cutoff; 0% inside the cutoff; no-show and early departure 0% automatically; admin discretionary override allowed with a required reason. The structured rule and rendered policy wording snapshot at reservation creation so later Settings edits never rewrite an existing guest's terms. Legacy bookings without a snapshot use the current policy with an explicit legacy-fallback marker. Corporate reservations inherit the standard policy unless their account has an explicit snapshotted override.

- ✅ **CRL-01 — Make refund submission idempotent (IMMEDIATE, highest finance risk)** — **Shipped 2026-08-01 at v0.211.3** (commit `e8c5b27` on `fix/crl-01-refund-idempotency`). ### Multi-Room Booking (MRB) — proposed 2026-07-31 · large, phased
> Owner request 2026-07-31, referencing a Booking.com availability table: guests must be able to book **multiple rooms and multiple room types in one flow**. Applies to all three create surfaces — guest `/book`, the admin New Booking modal (per NBS), and corporate `/corporate/book`.
>
> **Current model is strictly one room per booking.** `Booking` carries scalar `roomId` / `roomNumber` / `ratePerNight` / `numGuests`, and no grouping concept exists anywhere — `groupId`, `reservationId`, `groupBooking` return zero hits across `shared/`, `guest-app/server/`, and both apps. Corporate is one-room-per-booking too, so there is no precedent to extend. `roomId`/`roomNumber` read sites: **admin-app 303 · guest-app/server 169 · guest-app/src 78 · shared 13**.
>
> **Architecture revised 2026-08-01 (owner): one room-independent reservation header + N one-room booking documents.** The 2026-07-31 decision was half right: N room records are still required, and the rejected `rooms: [...]` array on one booking remains rejected because it invalidates the scalar `roomId` assumption at ~563 read sites and breaks per-room check-in, registration, ID, signature, housekeeping, room move, and checkout. What is superseded is linking those records only by `groupId` and making one designated room the financial “primary.” A cancelled room must never secretly own an active reservation's money. New shape: `reservations/{reservationId}` owns the public reference, lead booker/contact, source/corporate context, shared payment proof, discounts, group totals, and folio; each `bookings/{id}` carries `reservationId` and remains tied to exactly one physical room with its dates, occupancy, rate/add-on snapshots, registration, and lifecycle. No `isGroupPrimary` or `groupPrimaryBookingId`.
>
> **Owner decisions (2026-07-31, amended 2026-08-01):** (1) **one folio on the reservation header** — the one-bill outcome is unchanged, only its owner changes; (2) **all rooms share one date range at creation** — one stay per reservation, as in the reference screenshot; (3) **one booker at booking time**, per-room occupant names and IDs captured at check-in where registration already happens; (4) **all three create surfaces** in scope; (5) **every new single-room booking also gets a reservation header** so money, lookup, email, and reporting do not maintain separate single-room/group implementations. Exact adults/children/extra beds must be assigned to each room before review, but occupant identities wait until check-in. Mint one public `reservationRef` per reservation and denormalize it onto child bookings for existing admin search/display compatibility; there are no public or staff sibling refs. ### MRB — Resolved decisions (2026-08-01, recorded ahead of implementation)
- ✅ **Q1. Loyalty clawback — recompute + negative ledger entry, never rewrite the running total.** If a room is cancelled after the reservation was settled and loyalty was awarded, recompute the points that the new (lower) settled total would have earned and record the delta as a **new negative `pointsHistory` transaction** — the same shape as every other award. `rewardsPoints` is never decremented in place. This keeps the existing invariant `rewardsPoints == sum(pointsHistory.points)` (documented in `GOTCHAS.md`, pinned by a PMH-05 property test) true for member accounts touched by MRB, and gives support a legible audit trail ("+120 reservation R-045 settled" followed by "-40 room cancelled post-settlement, R-045") instead of a silently different total. MRB-05 implements the recompute-and-record step as part of the room-cancellation transaction that updates the reservation/room state.
- ✅ **Q2. Rounding-remainder audit legibility — labeled adjustment line, never silently reallocated.** Per decision #159, the rounding remainder from splitting the reservation total across room lines lands on the lowest room position. If that specific room is later cancelled, the remainder is **not** moved to another room's line. It stays attached to the cancelled room's audit record as a labeled "rounding adjustment (₱X)" entry. - **2026-07-24 — booking drawer hidden behind its own backdrop (MBZ-01..04 inversion regression)** — `1507a88`, `fix/mbz-z-index-regression` → `dev`. The first MBZ attempt set every backdrop to `z-[60]` while leaving every panel at `z-50`; in a single stacking context, higher z-index wins regardless of DOM order, so every overlay's own backdrop then covered its own panel and the booking drawer disappeared behind the fade. The fix replaces the single-z-bump with a **two-tier z-index system**: tier 1 (`z-50`) for Drawer + mobile Sidebar (backdrop + panel share `z-50`, DOM order keeps panel on top of its own backdrop), tier 2 (`z-[60]`) for Modal (same pattern at the higher tier).
