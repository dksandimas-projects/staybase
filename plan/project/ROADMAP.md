- **Must be updated on every merge to `dev`** (per `plan/docs/CONTRIBUTING.md §When to Update Which MD`). - Check off items as they're completed (`⬜` → `✅`); for `XX-01..05` style items, mark each sub-item or convert to one `✅ **XX**` line with the shipped commit(s).

Don't leave the implementation unrecorded.

### Weekend Rate Visibility (WRV) — reported 2026-07-31 · small
> Owner asked whether the guest can be shown the weekend rate when separate weekend pricing applies. **Mostly already built** — verified in code, not just in the doc: each Step 1 room-type card renders a "This stay uses mixed nightly rates" panel breaking out every rate line as `label: nights × rate` + subtotal, and Step 3's `PriceBreakdown` renders the same labelled lines.
>
> **But it is hidden in the one case that needs it most.** The panel was gated on `hasMixedRates = typeRoomBreakdown.roomLines.length > 1` in `guest-app/src/pages/BookingPage.tsx`. A stay that is **entirely** weekend nights — Saturday→Sunday, the most common weekend booking — produced a single rate line, so the panel did not render. Meanwhile the card headline read "**From** {base rate} per night" while the total charged the weekend rate. The guest saw a headline rate, a higher total, and no line anywhere reconciling them. "From" hedged it, but it read as a pricing surprise — and it was the worst case for confusion precisely because there was no second line on screen making the weekend rate self-evident.

- ✅ **WRV-01 — Show the rate panel whenever any line is non-regular, not only when lines > 1** — **Shipped 2026-08-01** on `feature/wrv-weekend-rate-visibility`. Gate changed from `roomLines.length > 1` to `hasNonRegularRate = roomLines.some(line => line.source !== "regular")`. A single-line weekend stay now renders a single line item — the source's own label + `nights × rate` + line subtotal (e.g. "Weekend nights: 1 × ₱2,700" with the ₱2,700 subtotal on the right). No "mixed nightly rates" claim, which would be false. Mixed stays are unaffected — the existing heading + per-source line list still renders. Seasonal/holiday-only stays are fixed by the same change.
- ✅ **WRV-02 — Make both selectable rate-option labels truthful** — Room Only and Room + Breakfast option prices now derive from `optionNightlyRate` + `optionRatePrefix`. Single-source stays show the source's actual nightly amount (no "From" prefix). Multi-source stays prefix the option price with "From" and rely on the breakdown + exact total. Fully regular stays fall through to the base rate with no "From" prefix. Both labels reuse the existing `typeRoomBreakdown` + the existing `liveBreakfastRate × effectiveBreakfastOccupancy` breakfast term — no second pricing formula.
- ✅ **WRV-03 — Test + MD sync** — 7 new source-text guards in `guest-app/src/__tests__/weekend-rate-visibility.test.ts` pin: the gate is `hasNonRegularRate` (NOT `roomLines.length > 1`); the single-source panel renders one line item WITHOUT the "mixed nightly rates" heading; the multi-source panel keeps the existing heading + line list; the entire panel is gated on `hasNonRegularRate`; both option price labels use `optionRatePrefix` + `optionNightlyRate` derived from `roomLines[0].nightlyRate` (single source) or the base rate (multi source); fully regular stays get no "From" prefix. MDs: `plan/features/BOOKING-FLOW.md §Step 1` — replaced "if selected dates include mixed pricing" with "whenever any night uses a non-standard rate", added the option-price-must-match-stay rule, and added an acceptance criterion for the single-source non-regular case. `plan/docs/DECISIONS-FEATURES.md #151` records the design.

### Walk-in Payment Method from Settings (WPM) — proposed 2026-07-31
> Reported by the owner 2026-07-31: the walk-in modal's **Payment Term** dropdown is the only payment selector in the admin app that is hardcoded. `BookingsPage.tsx` renders three literal `<option>` tags — `pay-at-hotel` / `cash` / `card` — while the bookings filter, the store filter, **Record Payment**, and **Verify & Record Payment** all map `onsitePaymentMethodOptions`, which is derived live from `settings/hotelConfig.paymentMethods[]`. The value is written straight to `booking.paymentMethod`, so the two lists share a keyspace but not a source.
>
> Three concrete consequences: (1) `card` is not a configured method at all — it exists only in `LEGACY_ONSITE_PAYMENT_METHOD_OPTIONS`, the fallback used when the hotel has zero configured methods — so a walk-in saved as `card` gets a key the Payment-method filter can never offer; (2) real configured methods (`gcash`, `bank`, `paypal`) cannot be selected at walk-in creation, forcing staff to file "Pay at Hotel" and record the true tender separately; (3) the modal's labels ("Cash on Hand", "Onsite Card Reader") drift from the admin-editable labels in Settings and never follow a rename.
>
> No server change: `WalkinBookingSchema` already accepts `paymentMethod: z.string().trim().min(1).max(80)`, and `paymentMethods` is already destructured from `useAdmin()` in `BookingsPage.tsx`. Scope is the admin client + docs. Decisions below were confirmed with the owner on 2026-07-31; record as `plan/docs/DECISIONS-FEATURES.md #141` when the fix ships.

### Pending Booking Expiry (PEX) — proposed 2026-07-31 · P1, gates MRB
> **Finding 2026-07-31, while scoping the CVQ-12 room cap.** `ROOM_OCCUPYING_STATUSES` includes **`pending`**, so a submitted-but-unpaid booking holds its room — and **no expiry or auto-cancel mechanism exists anywhere**. An abandoned booking blocks a real one indefinitely until staff cancel it by hand. `/api/bookings/create` is rate-limited to 5 requests per IP per minute, which today caps the damage at 5 rooms/minute because a booking can only hold one room.
>
> **Owner decisions (2026-07-31):** (a) **no cap on rooms per online booking** — "all if available"; (b) **yes, auto-cancel unpaid pending bookings after a set window.** These two are coherent *together*: the cap was only ever one mitigation, and expiry is the better one because it closes the vector rather than working around it. But it makes the window **load-bearing** — with no cap, the expiry window is the *only* thing bounding how long one request can hold the entire hotel. Choose it deliberately; see PEX-01.
>
> **Gates MRB.** Without expiry, an uncapped multi-room booking lets one unpaid request hold every available room forever. PEX must ship before MRB-06 exposes multi-room to guests.
>
> Record as `plan/docs/DECISIONS-FEATURES.md #147`.

- ✅ **PEX-01 — Expiry window + immutable deadline snapshot** — **Shipped 2026-08-01** on `feature/pex-pending-booking-expiry` (v0.200.2). ### Discount Scope Configuration (DSC) — proposed 2026-07-31 · resolves CVQ-06

> **CVQ-06 detail (the reasoning behind the default).** The senior/PWD 20% **already applies to breakfast today** — `calculateBookingTotal` computes `subtotal = roomTotal + breakfastTotal` and takes the discount off that subtotal. ### Cancellation & Refund Lifecycle (CRL) — proposed 2026-08-01 · P1, split delivery
> Owner request 2026-08-01: define and close the gaps between cancellation, policy eligibility, refund approval, and money actually returned. **Decision #160 reserved; write the decision entry only when implementation lands.**
>
> **Investigation findings:** cancellation is transactional and releases inventory, restores voucher/corporate usage, records a reason, and sends an email; refunds are admin-only immutable negative payment entries capped at net collected. The gaps are operationally important: the guest UI only exposes cancellation for `pending` / `payment-uploaded`, while the public API accepts paid/confirmed cancellations; the editable 48-hour policy is prose and is not evaluated by the server; cancellation does not create or track a refund obligation; standard cancellations do not stamp dedicated actor/time/source fields; the cancellation email does not state the refund outcome; and `/api/bookings/add-refund` has no caller-supplied idempotency key, so a retry after an uncertain response can append a second refund.
>
> **Delivery split:** CRL-01..04 are legacy-safe and should land before MRB. CRL-05..09 are reservation-authoritative and land with the MRB items named below rather than creating a booking-owned workflow that immediately needs moving. No implementation may claim money was returned merely because a reservation was cancelled or a refund was approved—the system only marks a refund processed after staff completes the external cash/GCash/bank/other movement and records the ledger entry.
>
> **Working policy defaults pending owner validation:** 48 hours before the scheduled 2:00 PM check-in in `config.timezone`; 100% of net collected refundable at or before the cutoff; 0% inside the cutoff; no-show and early departure 0% automatically; admin discretionary override allowed with a required reason. The structured rule and rendered policy wording snapshot at reservation creation so later Settings edits never rewrite an existing guest's terms. Legacy bookings without a snapshot use the current policy with an explicit legacy-fallback marker. Corporate reservations inherit the standard policy unless their account has an explicit snapshotted override.

### Multi-Room Booking (MRB) — proposed 2026-07-31 · large, phased
> Owner request 2026-07-31, referencing a Booking.com availability table: guests must be able to book **multiple rooms and multiple room types in one flow**. Applies to all three create surfaces — guest `/book`, the admin New Booking modal (per NBS), and corporate `/corporate/book`.
>
> **Current model is strictly one room per booking.** `Booking` carries scalar `roomId` / `roomNumber` / `ratePerNight` / `numGuests`, and no grouping concept exists anywhere — `groupId`, `reservationId`, `groupBooking` return zero hits across `shared/`, `guest-app/server/`, and both apps. Corporate is one-room-per-booking too, so there is no precedent to extend. `roomId`/`roomNumber` read sites: **admin-app 303 · guest-app/server 169 · guest-app/src 78 · shared 13**.
>
> **Architecture revised 2026-08-01 (owner): one room-independent reservation header + N one-room booking documents.** The 2026-07-31 decision was half right: N room records are still required, and the rejected `rooms: [...]` array on one booking remains rejected because it invalidates the scalar `roomId` assumption at ~563 read sites and breaks per-room check-in, registration, ID, signature, housekeeping, room move, and checkout. What is superseded is linking those records only by `groupId` and making one designated room the financial “primary.” A cancelled room must never secretly own an active reservation's money. New shape: `reservations/{reservationId}` owns the public reference, lead booker/contact, source/corporate context, shared payment proof, discounts, group totals, and folio; each `bookings/{id}` carries `reservationId` and remains tied to exactly one physical room with its dates, occupancy, rate/add-on snapshots, registration, and lifecycle. No `isGroupPrimary` or `groupPrimaryBookingId`.
>
> **Owner decisions (2026-07-31, amended 2026-08-01):** (1) **one folio on the reservation header** — the one-bill outcome is unchanged, only its owner changes; (2) **all rooms share one date range at creation** — one stay per reservation, as in the reference screenshot; (3) **one booker at booking time**, per-room occupant names and IDs captured at check-in where registration already happens; (4) **all three create surfaces** in scope; (5) **every new single-room booking also gets a reservation header** so money, lookup, email, and reporting do not maintain separate single-room/group implementations. Legacy booking documents without `reservationId` remain self-contained and readable; pre-live TEST DATA is reset rather than migrated.
>
> **Behavior contract approved 2026-08-01:** reserve `plan/docs/DECISIONS-FEATURES.md #159` for the implementation-time decision entry (`#143` was consumed by PMH-02 after the original MRB reservation). The public experience is one reservation; room records remain independently operable. Exact adults/children/extra beds must be assigned to each room before review, but occupant identities wait until check-in. Mint one public `reservationRef` per reservation and denormalize it onto child bookings for existing admin search/display compatibility; there are no public or staff sibling refs. Lookup resolves the reservation header, then its room bookings.
>
> | Action / concept | Reservation or room scope |
> |---|---|
> | Dates at creation, payment proof, payments, folio, receipt, initial confirmation, pre-arrival reschedule | **Group** |
> | Registration/ID, room assignment or move, check-in/out, housekeeping, intercom, early arrival/departure, in-stay extension | **Room** |
> | Incidentals and store orders | Entered against a room; charged to the reservation folio |
> | Staff cancellation | Explicit choice: selected room or entire reservation |
> | Guest cancellation | Entire reservation by default; no ambiguous one-click room cancellation |
> | Partial cancellation | Remove that room's itemized charges, preserve an audit adjustment, and use the existing refund ledger for money already collected |
> | Email after a partial action | One “reservation updated” message listing the change, remaining rooms, revised total/balance, and refund/payment state |
> | Loyalty | Award once to the lead member from the final settled reservation total, never once per child booking |
>
> **Pricing and limit defaults:** a percentage voucher/member discount applies across eligible room lines; a flat voucher applies once to the reservation and is recomputed against the remaining eligible lines after a partial cancellation; mixed room-type eligibility discounts only eligible lines. Voucher usage counts once per reservation and is restored only when no active room still receives that voucher. Corporate-code `usageCap` counts rooms because it represents room allocation; cancelling an eligible room before check-in restores one use. The PEX snapshotted hold window applies uniformly to the reservation (current default 24h); MRB does not introduce an undocumented shorter large-reservation timer.
>
> **Aggregate status + reporting contract:** the reservation summary derives its main lifecycle label from non-cancelled child bookings: payment pending → `Awaiting payment`; all confirmed → `Confirmed`; a mix of confirmed/checked-in → `Partially checked in`; all active rooms checked in → `In house`; a mix containing checked-out rooms → `Partially checked out`; all active rooms checked out → `Completed`. Cancellation is a secondary count (`1 of 3 rooms cancelled`) so it never hides the operational state; only an all-cancelled reservation is `Cancelled`. Every room retains its exact status. Reservation/acquisition/cancellation counts come from reservation headers; occupancy and room-nights remain per room booking; ADR is room revenue divided by rooms sold. Availability failure preserves the cart, identifies the short room type/quantity, and creates nothing.

Deliver MRB itself in phases: reservation model + server (01–05) before any UI (06–08). **See §Pre-MRB Hardening (PMH) above** — PMH-02 gates MRB-04, and PMH-01 keeps the reservation-header cutover before real guest money reaches production.

>
> **Investigation finding (verified 2026-08-01):** no reservation entity exists in `shared/`, either app, the server, or Firebase rules. The public ref is generated on a booking; lookup queries `bookings.bookingRef`; payments and charges live under `bookings/{id}`; Reports joins those subcollections by booking ID. MRB must deliberately move shared/commercial ownership instead of layering a header over unchanged writers. Already in favour: the MBP picker (`/my-booking` returning `kind: "list"`) is most of the nested-room lookup UI; the room-assignment loop generalises to N; the daily counter is already inside the transaction; Firestore's 500-document limit is far above the hotel's inventory.
>
> **Source-of-truth invariant (approved 2026-08-01):** reservation-authoritative fields are public ref, lead booker/contact, source/corporate context, payment proof/state, voucher/member discount, consent, group totals, and folio. Room-booking-authoritative fields are physical room/type, actual dates, adults/children/extra beds, rate/add-on/tax line snapshots, registration/ID/signature, check-in/out, housekeeping, and room lifecycle. Compatibility copies on child bookings are read-only projections; no UI or rule may edit them independently. `Reservation.paymentStatus` is the money/proof authority; existing `Booking.status` remains the room occupancy/lifecycle authority. A payment action changes the reservation and any required room transition atomically—never N unrelated client writes.
>
> **Materialized summary invariant:** because Firestore has no joins, each reservation stores room/active/cancelled/checked-in/checked-out counts, aggregate lifecycle label, total, paid, balance, earliest arrival, and latest departure. Child bookings remain authoritative; every server operation that changes a room or ledger entry updates the reservation projection in the same transaction. The main Bookings list and payment/balance queues use reservation rows; arrivals, departures, in-house, housekeeping, and calendar remain room-stay views. Searching a ref opens the reservation; searching a room opens that room inside it.
>
> **Idempotency + financial-line invariant:** the client preallocates the reservation ID and every intended child booking ID. The reservation stores a canonical request fingerprint. An exact replay returns the existing reservation without reassigning inventory, incrementing voucher/corporate usage, awarding loyalty, or sending email; the same ID with a different fingerprint returns a conflict. Each room snapshots its room/add-on subtotal, reservation-discount allocation, VAT allocation, and final line total; the reservation total is the exact sum of those lines. Rounding remainder goes deterministically to the lowest room position so cancellation and export reconstruction remain exact.
>
> **Lifecycle invariant:** reservation-scoped PII/proofs/ledgers participate in security rules, data erasure, TEST DATA tagging/reset, backup/export, retention, and orphan-Storage cleanup. A production cancellation never deletes the reservation; an all-cancelled reservation remains the audit/financial record. The canonical PEX deadline lives on the reservation and is copied to held child rooms for availability reads; proof upload pauses the whole reservation, rejection refreshes the reservation and child copies atomically, and expiry cancels the header plus every still-held child in one transaction.
