## How to Use This File

- **Must be updated on every merge to `dev`** (per `plan/docs/CONTRIBUTING.md §When to Update Which MD`). The closing the loop is: when a `feat:` / `fix:` / `refactor:` lands, this file gets a `docs:` PR in the same batch. The roadmap is the project's source of truth for "what's open" — drift between the code and the roadmap makes the next person pick wrong work.
- Check off items as they're completed (`⬜` → `✅`); for `XX-01..05` style items, mark each sub-item or convert to one `✅ **XX**` line with the shipped commit(s).
- Update "Last updated" date at the top on each edit.
- Add a one-line `Shipped YYYY-MM-DD — <commit hash>` note to the section header so future readers can find the implementation.
- **Off-roadmap fixes/featuers** (a `fix:` that wasn't on the roadmap before it shipped) — add a short note under a `### Recently shipped (off-roadmap)` section near the bottom of Phase 12, with the commit hash, so the roadmap still reflects what's actually in the code. Don't leave the implementation unrecorded.
- Add notes under items if there are blockers or decisions made.
- Commit with `docs: update ROADMAP.md` prefix (no version bump).
- **This file holds current status and open work only.** Completed-phase checklists, shipped audit-fix batches, and closed findings live in `plan/project/archive/ROADMAP-ARCHIVE-2026-07-17.md` (historical, do not load routinely) and in Git history. When a phase or fix batch fully ships, move its detail to the archive and keep a one-line ✅ status here.

### Children in Booking (CHD) — proposed 2026-07-31
> Client request 2026-07-31: split occupancy into **adults (12+)** and **children (0–11, free of the room rate)**, with a configurable child limit. No children concept exists today — `Booking.numGuests` is a single scalar and `RoomTypeEntry.maxCapacity` is a single number (Single 1 · Std Double 2 · Std Twin 2 · Executive 2 · Family 4, across 48 read sites).
>
> **Owner decisions (2026-07-31):** (1) **children pay the full adult breakfast rate** — "free" applies to the room charge only; (2) **separate adult and child caps per room type** — a Single can allow 0 children while Family allows more; (3) the limit is configured **per room type**, not globally; (4) **count only, no per-child ages** — the guest picks "how many children aged 0–11", the age rule is stated in the UI, and no dates of birth are collected (which also keeps identifiable data about minors out of scope for RA 10173). Record as `plan/docs/DECISIONS-FEATURES.md #144`.
>
> **Key consequence of decision (1): `numGuests` keeps its current meaning — total occupancy — and the breakfast math is untouched.** `breakfastRate × numGuests × nights` is duplicated across **six** independent implementations (`bookings.ts` create/walk-in/move, `rate-breakdown.ts` ×2, `shared/utils/pricing.ts`, plus the corporate-inquiry conversion). Because children pay the full breakfast rate, all six keep multiplying by total occupancy and **none of them changes**. Had children been free or discounted for breakfast, this feature would have required editing money math in six places. Add `numAdults` + `numChildren` **alongside** `numGuests`, do not replace it.
>
> **No migration.** Existing bookings read as `numAdults = numGuests`, `numChildren = 0`. Existing room types read as `maxCapacity` = the adult cap with `maxChildren` defaulting per the seed — the same permissive `!== undefined` normalize-on-read pattern already used for the #111 payment-method surface flags.
>
> **Depends on RTS.** CHD-03 adds fields to the Settings → Room Types Add/Edit modal, which writes through the exact `updateRoomType` path that RTS-01/RTS-02 are fixing. Land RTS first or the new fields inherit the same last-write-wins bug.

Server derives and validates `numGuests === numAdults + numChildren` on write rather than trusting either value from the client. Types: `shared/types/index.ts`; schemas: `shared/schemas/booking.ts` (both the public create and the `.strict()` `WalkinBookingSchema`).

### Room Type & Rates Save Defects (RTS) — reported 2026-07-31 · P1
> Owner reported two broken surfaces on 2026-07-31: **room type deletion** and **rates management cannot save**. Both are write-path defects on the same field — `settings/hotelConfig.roomTypes[]` — so they are tracked together. Code read on `dev` @ `36d4112`. All 930 admin tests pass, which is itself a finding: the suite is source-text assertions, so neither defect is behaviorally covered.
>
> **RTS-01 is a confirmed root cause with a concrete mechanism. RTS-04/05/06 are candidate mechanisms for the deletion report and are NOT yet reproduced** — RTS-03 is the gate that decides which one (or more) is real. Do not start on RTS-04..06 before RTS-03 says which applies.

- ⬜ **RTS-01 — CONFIRMED: `handleSaveRates` races itself; only one room type's rates survive** — `RatesPage.tsx` builds `roomTypes.map(t => updateRoomType(t.value, {...}))` and fires them all through one `Promise.all`. `updateRoomType` in `AdminContext.tsx` does `const updated = roomTypes.map(...)` — reading `roomTypes` from its **render-time closure** — then `saveRoomTypes(updated)` writes the **entire array** via `setDoc(..., { merge: true })`. A merge write replaces an array field wholesale, so N concurrent calls each compute "the original array with exactly one type changed" from the *same* stale snapshot, and the last write to land wins. **Every other room type's edit is silently discarded.** `Promise.all` resolves clean (all N writes genuinely succeeded), so the "Rates saved" toast fires and the user watches the values snap back when the `onSnapshot` echo arrives. Matches the report exactly.
- ⬜ **RTS-02 — Fix: one batched array write, not N racing ones** — add a bulk `saveRoomTypes`-style API to `AdminContext` that takes the fully-computed next array and performs a **single** write; `handleSaveRates` computes the whole matrix once and calls it once. Per-field functional state updates do not fix this on their own — the race is at the Firestore write, not in React state. Audit for other `Promise.all` + `updateRoomType` call sites before shipping (`uploadRoomTypePhoto`, `removeRoomTypePhoto`, and the Settings room-type edit modal all call it singly today and are safe).
- ⬜ **RTS-03 — Reproduce the deletion failure and pin which mechanism applies** — gate for RTS-04..06. Capture: the room type being deleted, whether any rooms still reference it, whether a toast appeared (and its exact text), and whether the row vanished and then came back. On staging, delete a type with zero attached rooms while watching the console + the Firestore doc.
- ⬜ **RTS-04 — Candidate: optimistic local state is never rolled back on a failed write** — `saveRoomTypes` calls `setRoomTypes(newTypes)` **before** the write, then `await updateSettings(...)`. `updateSettings` catches its own errors, fires a "Failed to save settings" toast, and **returns `false` rather than throwing** — so `saveRoomTypes`'s own `try/catch` is dead code and its callers never learn the write failed. `deleteRoomType` therefore resolves successfully, `SettingsPage`'s `catch` sees nothing, and the row disappears from the table until the next snapshot silently restores it. **Presents exactly as "deletion doesn't work."** This is a real defect on its own merits regardless of RTS-03's verdict — `addRoomType` / `updateRoomType` / `deleteRoomType` all report success on a failed write.
- ⬜ **RTS-05 — Candidate: the 3-second auto-disarm on the two-step delete confirm** — `SettingsPage.tsx` resets `pendingDeleteRoomType` to `null` 3s after arming. There is no countdown or progress affordance, so a user who clicks **Delete**, reads the label change to "Click to confirm", hesitates past 3s, and clicks again simply **re-arms** it. Repeat indefinitely and nothing ever deletes. If RTS-03 confirms this, the fix is a longer window, a visible countdown, or a proper confirm dialog — the same `ConfirmForm` primitive Phase 11.7 already ships.
- ⬜ **RTS-06 — Candidate: deleting the LAST room type resurrects all 8 defaults** — the `roomTypes` sync effect in `AdminContext.tsx` is guarded by `hotelConfig.roomTypes.length > 0`. Delete down to an empty array and the write persists `[]` correctly, but on the next page load the effect **skips**, leaving local state on its `DEFAULT_ROOM_TYPES` initializer — so every deleted type reappears. Narrow (only bites at zero types) but unambiguous. Fix: distinguish "not loaded yet" from "loaded and legitimately empty".
- ⬜ **RTS-07 — Tests + MD sync** — the existing 930 admin tests are source-text assertions and caught none of this. Add behavioral coverage: a multi-type rate save persists **every** type (the RTS-01 regression guard — this is the one that matters), a failed settings write does not leave the UI showing a deleted row, and the roomTypes sync effect handles a legitimately empty array. MDs: `plan/features/RATE-MANAGEMENT.md` (single-batch write contract), `plan/features/SETTINGS.md §Room Types` (delete guard + confirm behavior), `plan/docs/GOTCHAS.md` (**never fan out per-item writes to a single Firestore array field — compute the whole array and write once**; this is the reusable lesson and applies equally to `paymentMethods[]`, `bookingSources[]` per NBS-04, and `seasonalRateOverrides[]`).
