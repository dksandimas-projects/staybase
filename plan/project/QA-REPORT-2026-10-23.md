## 0. Headline

Three defects that stop a member of staff doing their job are **live in production right now**:

1. **Six staff mutations are dead** — the admin app sends `turnstileToken: undefined` to endpoints the server gates behind Cloudflare Turnstile, and mounts no widget to get one. **Mark served**, **record a breakfast refund**, **add/remove an other-add-on**, and their refund equivalents all return `HTTP 400 Bot verification token is missing.` (§3.1)
2. **The desk cannot see a room call** — the admin app's incoming-call listener is a `collectionGroup("callSessions")` query, and against production that query is **denied with HTTP 403 for both staff roles**, while the single-collection and `messages` reads return 200. Every sign-in logs `Missing or insufficient permissions`. (§3.10)
3. **Google sign-in is broken on the guest site** — `guest-app/vercel.json` omits `https://apis.google.com` from `script-src`, so the browser blocks the Firebase Auth script. The root and admin CSPs have it; only the file that governs the guest deployment does not. (§3.9)

Two more defects change numbers the desk relies on:

4. The hotel's revenue streams **under-report by ₱3,950** — two bookings carry other add-ons that never reach `revenueAllocation`, so every report that reads the allocation is wrong while the folio bills the guest correctly. The repo's own finance scanner finds the same two rows. (§3.4)
5. The admin folio **nets pending refund liabilities against money already collected**, so a cancelled booking with ₱2,800 collected is shown as owing ₱100. Correcting for it reproduces the handoff's independently recorded truth exactly — **14 paid / 55 balance due** — against the app's **0 / 69 / 10**, and the authenticated browser pass reproduces that same signature end-to-end (§3.3, §3.6)

And two more found in the authenticated pass:

6. `booking.paidAmount` went **negative** (₱−1,000) on one booking because the refund path decremented a base that was never seeded; that same field is what the add-on reschedule path reads to decide whether a meal was paid for. (§3.5)
7. The front desk is **shown admin-only navigation it cannot use** — `Rates`, `Members` and `Settings` appear in the nav and every one of them answers "ACCESS DENIED". The route guard is real; the nav is not role-filtered. (§3.11)

And one smaller one found while fixing a test flake:

8. The dashboard's **"Pending refunds" card lands on the wrong Reports tab** — it navigates to `/reports?tab=liability`, but the Reports page never reads a `tab` parameter, so the desk's shortcut to the money-to-process queue opens the Performance tab instead. (§3.12)

And one correction to the handoff itself: **every public guest write endpoint is Turnstile-gated, including the staff breakfast and add-on paths** — §5.2's claim that *"Staff endpoints are ungated"* is no longer true, and the code that would have caught it asserts only that a URL string appears in the source.

The independent reconciliation (I01–I17) and the repo's own finance scanner agree on every material number. **No production record was created, modified or deleted by this pass.**

### 3.1 — S1 · Six staff mutations are dead in production: the admin app sends no bot token

**This is the highest-severity finding of the pass.**

`guest-app/server/apiRouter.ts` gates these endpoints behind Cloudflare Turnstile — **including the ones that require staff authentication**:

| Endpoint | Gate | Admin client behaviour |
|---|---|---|
| `POST /api/bookings/breakfast/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/breakfast/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/breakfast/mark-refund-paid` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/addons/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/mark-refund-paid` | `verifyTurnstile` | **no admin wrapper exists at all** |

The admin app (`admin-app/src/context/AdminContext.tsx`) sends a decorative header the server never reads:

```ts
headers: {
  "Content-Type": "application/json",
  "Authorization": token ? `Bearer ${token}` : "",
  "X-Spark-Inn-Turnstile": "client-echo"   // the server never reads this header
},
body: JSON.stringify({ ...input, turnstileToken: undefined })  // the field the server reads
```

The comment directly above it states the requirement correctly — *"the client must echo it on every mutation. The apiRouter's `verifyTurnstile` reads it from `req.body.turnstileToken`"* — and then sends `undefined`.

The admin app **mounts no Turnstile widget at all**: there is no `cf-turnstile` element, no `challenges.cloudflare.com` reference and no `turnstile.render` call anywhere in `admin-app/src`. The guest app does mount one (`guest-app/src/hooks/useTurnstileToken.ts`), so the guest side is fine.

Server behaviour (`apiRouter.ts`, `verifyTurnstile`):

```ts
if (!token) {
  return { success: false, error: "Bot verification token is missing." };
}
```

⇒ Every one of those calls returns **HTTP 400 `Bot verification token is missing.`**

**Reproduction**

1. Sign in to the admin app as `adminbot@gmail.com`.
2. Open any booking that has a breakfast selection → **Breakfast** tab.
3. Toggle **Mark served** (or **Save changes**, or **Mark as paid** on a refund liability).
4. The toast reads *"Bot verification token is missing."* and the network panel shows `POST /api/bookings/breakfast/mark-served → 400`.

**Impact**

- The staff cannot mark a meal served → the kitchen list never closes a meal → **BR-08** (the "late served" email that fires on a staff serve action) can never fire.
- The staff cannot record a breakfast refund liability → **BR-08 / BR-09** and the whole refund-liability surface are dead.
- The staff cannot add or remove an other-add-on → **AO-09** and **MRB-11d** are dead.
- The other-add-on refund "mark as paid" surface has **no client at all**.

**Why the existing tests did not catch it.** The repo's own unit tests assert only that the URL string appears in the source:

```ts
expect(adminContext).toContain("/api/bookings/breakfast/mark-served");
```

They never assert that a token is sent, so the suite stays green while the feature is broken in production. `e2e/tests/deploy-posture.spec.ts` adds the missing regression guard.

**Secondary defect — the handoff is stale.** `plan/project/HANDOFF-2026-10-23.md` §5.2 states *"Staff endpoints are ungated and were used for equivalent coverage."* That is no longer true: the breakfast and add-on staff paths **are** gated, and `bookings/cancel` is gated for guests but bypassed for staff. Only the core booking-lifecycle staff endpoints (`create-walkin`, `checkin`, `checkout`, `add-payment`, `verify-and-record-payment`, `reschedule`, `mark-payment-confirmed`, `reject-payment`, `cancel`) are ungated.

### 3.2 — S2 (environment, not a defect) · Turnstile cannot be satisfied from this network

The guest app's write surface is behind Turnstile, and the challenge platform hostnames do not resolve here:

```
https://brunhild.challenges.cloudflare.com/...  →  net::ERR_NAME_NOT_RESOLVED
https://hagen.challenges.cloudflare.com/...      →  timeout
https://valid.alchallenges.cloudflare.com/...    →  fetch failed
https://challenges.cloudflare.com/               →  HTTP 200   (reachable)
```

A real Chrome UA, `--disable-blink-features=AutomationControlled`, the Manila locale/timezone, and a 45-second wait were all tried; the hidden `input[name="cf-turnstile-response"]` never received a value.

The server side is healthy — a deliberate bad token is rejected correctly:

```
POST https://challenges.cloudflare.com/turnstile/v0/siteverify
→ HTTP 200 {"error-codes":["invalid-input-response"],"success":false}
```

⇒ This is a **network limitation of the QA host, not a product defect.** It blocks every guest-side write scenario (booking creation, lookup, self-cancel, breakfast edits, voucher validation, corporate-code validation, inquiry and contact submission) **and** the staff breakfast/add-on scenarios — the latter not by network but by finding 3.1.

The anti-automation posture itself is **verified as working**: an unverified caller is refused with HTTP 400 `Bot verification token is missing.` before any schema validation, which is the correct order.

### 3.3 — S2 · The admin folio nets *pending* refund liabilities against money already collected

`BREAKFAST.md §Removal semantics` is explicit:

> *Removing a paid meal: … a `bookings/{id}/refunds/{refundId}` entry is created with `category: "breakfast"`, `status: "pending"`, `type: "refund"`, `amount: -priceSnapshot`; **the booking's `paidAmount` is unchanged (the refund is a liability, not a debit)**.*

But the admin's ledger normaliser never reads `status`:

```ts
// admin-app/src/utils/bookingPaymentEntries.ts — normalizeLedgerDoc
const type = data.type === "refund" || amount < 0 ? ("refund" as const) : ("payment" as const);
return { ..., amount, ... };   // ← `status` is dropped
```

and `buildBookingPaymentIndex` sums every entry into `paymentsTotal`. A **pending** liability is therefore subtracted from money the hotel still holds.

Production effect (reconciliation check **I06b**):

| Booking | Collected | Pending refund | Admin shows paid | Admin shows balance |
|---|---|---|---|---|
| `SI-20261021-00058` (cancelled) | ₱2,800 | −₱100 (breakfast, pending) | **₱2,700** | **₱100** |
| `SI-20261021-00060` (cancelled) | ₱2,800 | −₱100 (breakfast, pending) | **₱2,700** | ₱0 |

`SI-20261021-00058` is a **cancelled** booking that the desk is shown as owing **₱100** on. The correct figures are ₱2,800 collected, ₱0 outstanding, with a ₱100 refund liability shown separately (which is where the Refunds view belongs).

This also propagates into the quick-view chips: correcting for it moves the recomputed chip counts from 13/56 to **14 paid / 55 balance due**, which is exactly the truth the handoff recorded independently.

### 3.4 — S2 · Other add-on revenue still never reaches the revenue allocation (MRB-11b)

The MRB-11 backfill fixed the allocation *identity* but not the add-on *content*:

| Booking | `otherAddOnTotal` | `revenueAllocation.addOnNet` | `rateBreakdown.addOns` |
|---|---|---|---|
| `SI-20261021-00053` | ₱1,500 (3 × ₱500 airport transfer) | **₱0** | **`[]`** |
| `SI-20261021-00055` | ₱1,000 (2 × ₱500 airport transfer) | **₱0** | **`[]`** |

Reconciliation check **I16** quantifies it:

```
allocation revenue stream totalNet = ₱282,760.00
folio billed                      = ₱286,710.00
Δ                                 = −₱3,950.00
```

The guest is billed **₱9,600** on `SI-20261021-00053` (₱8,100 room + ₱1,500 transfer) through the folio, but every revenue stream that reads `revenueAllocation` under-reports by ₱3,950 across the book. The historical report lists this as *"AO-04 — FIXED, SHIPPED 2026-10-22"*; the two rows are unchanged in production.

Note the interaction with finding 3.1: the staff path that would repair this (`addons/staff-update`) is dead, and the guest path is Turnstile-gated — so there is currently **no working path** that can set `addOnNet` for an existing booking.

**A second, independent symptom on the same booking.** The drawer's Add-Ons tab for `SI-20261021-00053` shows **"Other Add-Ons — Total: ₱1,500"** but only itemises **₱500** (the 2026-11-06 line). The 2026-11-05 line reads *"No add-ons for this date."* — yet that date carries 2 × ₱500 in the raw document.

The cause is in the **seeded record**, not in the app's rule: the 2026-11-05 selection is written without `addedAt`, `addedBy` **or `removedAt`**:

```
2026-11-05 → [{ addOnId: "airport-transfer", quantity: 2, priceSnapshot: 500, … }]   ← no addedAt / removedAt
2026-11-06 → [{ addOnId: "airport-transfer", quantity: 1, priceSnapshot: 500, addedAt: "…", removedAt: null, … }]
```

and the drawer keeps only entries where `removedAt === null` (`admin-app/src/components/BookingDrawerWorkspace.tsx:2664-2666`) — the documented liveness convention (`plan/features/BREAKFAST.md` §Removal semantics), applied correctly. The stored `otherAddOnTotal` was written by a different path and still counts the malformed row.

The visible consequence for staff is a **drawer whose own two numbers disagree**: a total of ₱1,500 that cannot be itemised. This is a **seed-data defect**, not an app-logic defect — but it makes `SI-20261021-00053` unusable as a reference fixture, and it means the ₱3,950 in the table above is *partly* a data-shape problem rather than purely a missing write path. The assignment forbids backfilling records, so the row is left as it is and reported here.

### 3.5 — S3 · `booking.paidAmount` went negative on one booking and the refund path used an unseeded base

`SI-20261021-00011` (`A2FD10Walkin0001`):

```
totalPrice        = ₱5,400
ledger (collected)= ₱4,400   (₱5,400 payment − ₱1,000 cancellation refund)
booking.paidAmount= −₱1,000  ← NEGATIVE
```

The refund path decremented `paidAmount` from a base that was never seeded, so the field is negative rather than ₱4,400. ### 3.9 — S1 · The guest app's CSP blocks the Google auth script — Google sign-in is broken

The guest site loads `https://apis.google.com/js/api.js` at runtime (Firebase Auth's `signInWithPopup`). The **guest** deployment's Content-Security-Policy does not allow it:

```
https://www.sparkinnbohol.com/      script-src 'self' 'unsafe-eval' https://www.gstatic.com
                                     https://www.google.com https://www.googletagmanager.com
                                     https://challenges.cloudflare.com https://browser.sentry-cdn.com
                                     → apis.google.com MISSING

https://admin.sparkinnbohol.com/    … https://www.google.com https://apis.google.com …
                                     → apis.google.com PRESENT
```

The browser therefore blocks the script and logs a CSP violation on guest pages:

```
Loading the script 'https://apis.google.com/js/api.js?onload=__iframefcb331067' violates the
following Content Security Policy directive: "script-src 'self' 'unsafe-eval' …"
```

**The cause is a file-level omission.** Three CSPs exist in this repository:

| File | Governs | `apis.google.com` in `script-src` |
|---|---|---|
| `vercel.json` (root) | — (not a deployment) | **yes** |
| `admin-app/vercel.json` | admin.sparkinnbohol.com | **yes** |
| `guest-app/vercel.json` | **www.sparkinnbohol.com** | **NO** |

`plan/project/ROADMAP.md` records the original fix (commit `03b18d4`, MBUX-10 Bug B): *"the CSP permits the Google auth iframe script in BOTH `vercel.json` files"*. The fix was applied to the root and the admin app; the file that actually governs the guest deployment was **not** updated.

**Reproduction**

1. Open `https://www.sparkinnbohol.com/signin` in a browser with the console open.
2. The CSP violation is logged on page load.
3. Click **Continue with Google** — the popup cannot initialise, because the script that bootstraps it was blocked.

**Why the existing test did not catch it.** `guest-app/tests/api/mbux-10-phase-15-closeout.test.ts` asserts *"the CSP permits the Google auth iframe script in BOTH `vercel.json` files"* — it checks two files and never the third, so the suite stays green while the guest site is broken.

**Fix** — one token in `guest-app/vercel.json`:

```
script-src 'self' 'unsafe-eval' https://www.gstatic.com https://www.google.com
          https://apis.google.com https://www.googletagmanager.com
          https://challenges.cloudflare.com https://browser.sentry-cdn.com
```

`e2e/tests/deploy-posture.spec.ts` (`SEC-CSP`) is the regression guard: it reads the **live** CSP header and fails while the guest origin omits the host.

### 3.10 — S2 · The desk's incoming-call listener is denied in production — the front desk cannot see a room call

Every admin-app sign-in logs:

```
Error listening to WebRTC calls: FirebaseError: Missing or insufficient permissions.
```

for **both** the admin and the front-desk identity. The listener is `collectionGroup(db, "callSessions")` in `admin-app/src/context/AdminContext.tsx:5591` — it is how the desk learns that a guest is ringing.

**Proved against production with real staff ID tokens** (Firestore REST `runQuery`, `allDescendants: true`):

| Query | Admin | Front desk |
|---|---|---|
| `collectionGroup("callSessions")` — the desk's incoming-call listener | **HTTP 403** | **HTTP 403** |
| `collection("callSessions")` — the same collection, top level only | HTTP 200 | HTTP 200 |
| `collectionGroup("messages")` — the desk's inbox thread | HTTP 200 (2 docs) | HTTP 200 (2 docs) |
| `collection("intercoms")` — control | HTTP 200 (8 docs) | HTTP 200 (8 docs) |

So the denial is **specific to the group query**, and it hits both staff roles identically — it is a rules-shape problem, not a role problem.

**Cause.** A Firestore collection-group query must be *provably* safe: the rule set has to guarantee the query can only return documents the caller may read, for **every** path in the group, including paths that do not exist yet. The rules grant the two `callSessions` shapes unconditionally:

```rules
match /callSessions/{sessionToken} {
  allow read, create, update, delete: if true;
  match /iceCandidates/{candidateId} {
    allow read, create, update, delete: if true;
  }
}
```

but the `intercoms/{roomId}` block is **conditional**:

```rules
match /intercoms/{roomId} {
  allow read: if isStaff();      // ← conditional
  allow write: if isStaff();
}
```

**Corrected root cause (2026-10-24).** This section originally blamed the conditional `intercoms` arm for poisoning the group query. That is **wrong**, and the emulator proves it: a Firestore `match /intercoms/{roomId} { … }` block applies to `intercoms/{roomId}` **only** — `match` blocks do **not** cascade into a document's subcollections. So the `intercoms/{roomId}` arm never covered `intercoms/*/callSessions/**` in the first place.

The real cause is the inverse: **no rule covered the nested path at all.** The `match /callSessions/{sessionToken}` block matches a **top-level** `callSessions` collection only; a session stored under a room (`intercoms/{roomId}/callSessions/{token}`) is a different path and matched **no** `allow` rule. A collection-group query over `callSessions` has to be provably safe for **every** path in the group, so one path with no rule denies the whole query — for both staff roles.

**Fix (shipped 2026-10-24)** — give the nested shape its own unconditional-for-staff rule, mirroring the `messages` group:


### 11.1 What is deliberately NOT fixed

**§3.4 — the other add-ons never reach `revenueAllocation`.** The diagnosis is now exact, and it is *not* the write path the QA report first guessed:

- `revenueAllocation.addOnNet` is computed from **`extraBedTotal`** — the extra-bed revenue — at every one of the seven write sites. The BR-12 **other add-ons** (`otherAddOnTotal`, the airport transfer) are a **different stream that the allocation schema never learned about**: `BookingRevenueAllocation` has `roomNet`, `breakfastNet`, `addOnNet`, `deductionNet`, `totalNet` and nothing else.
- Consequently `revenueAllocation.totalNet` equals `booking.totalPrice` (the room bill) and **excludes** `otherAddOnTotal`: `SI-20261021-00053` is allocated ₱8,100 against a ₱9,600 folio bill.
- Fixing it means **extending the allocation schema** with an other-add-on stream, changing the invariant (`roomNet + breakfastNet + addOnNet − deductionNet === totalNet`) and `totalNet`'s meaning (`totalPrice` → `totalPrice + otherAddOnTotal`), and updating every writer and reader: **452 references across 41 files**, including `shared/__tests__/mrb-11-revenue-streams.test.ts` (58) and the MRB-11 rebuild tooling. A backfill of the 69 stored allocations is also required — and that is a **production data write**.
- `scripts/backfill-mrb11-allocation.ts` already exists for the MRB-11 rebuild, so the backfill machinery is in place.

**Why it was left alone here:** it is a schema migration with a money-model invariant change and a 69-row production backfill — not a defect that can be patched safely inside a QA follow-up. Half-migrating it would break the repo's MRB-11 suite and leave the books in a worse state than the under-reporting. It is recorded in `plan/project/ROADMAP.md` as its own unit of work with the exact change spelled out.
