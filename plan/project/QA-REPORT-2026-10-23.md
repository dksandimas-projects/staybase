## 0. Headline

Three defects that stop a member of staff doing their job are **live in production right now**:

1. **Six staff mutations are dead** — the admin app sends `turnstileToken: undefined` to endpoints the server gates behind Cloudflare Turnstile, and mounts no widget to get one. **Mark served**, **record a breakfast refund**, **add/remove an other-add-on**, and their refund equivalents all return `HTTP 400 Bot verification token is missing.` (§3.1)
2. **The desk cannot see a room call** — the admin app's incoming-call listener is a `collectionGroup("callSessions")` query, and against production that query is **denied with HTTP 403 for both staff roles**, while the single-collection and `messages` reads return 200. Every sign-in logs `Missing or insufficient permissions`. (§3.10)
3. **Google sign-in is broken on the guest site** — `guest-app/vercel.json` omits `https://apis.google.com` from `script-src`, so the browser blocks the Firebase Auth script. The root and admin CSPs have it; only the file that governs the guest deployment does not. (§3.9)

Two more defects change numbers the desk relies on:

4. The hotel's revenue streams **under-report by ₱3,950** — two bookings carry other add-ons that never reach `revenueAllocation`, so every report that reads the allocation is wrong while the folio bills the guest correctly. The repo's own finance scanner finds the same two rows. (§3.4)
5. The admin folio **nets pending refund liabilities against money already collected**, so a cancelled booking with ₱2,800 collected is shown as owing ₱100. Correcting for it reproduces the handoff's independently recorded truth exactly — **14 paid / 55 balance due** — against the app's **0 / 69 / 10**, and the authenticated browser pass reproduces that same signature end-to-end (§3.3, §3.6)

And two more found in the authenticated pass:

6. `booking.paidAmount` went **negative** (₱−1,000) on one booking because the refund path decremented a base that was never seeded; that same field is what the add-on reschedule path reads to decide whether a meal was paid for. (§3.5)
7. The front desk is **shown admin-only navigation it cannot use** — `Rates`, `Members` and `Settings` appear in the nav and every one of them answers "ACCESS DENIED". The route guard is real; the nav is not role-filtered. (§3.11)

And one smaller one found while fixing a test flake:

8. The dashboard's **"Pending refunds" card lands on the wrong Reports tab** — it navigates to `/reports?tab=liability`, but the Reports page never reads a `tab` parameter, so the desk's shortcut to the money-to-process queue opens the Performance tab instead. (§3.12)

And one correction to the handoff itself: **every public guest write endpoint is Turnstile-gated, including the staff breakfast and add-on paths** — §5.2's claim that *"Staff endpoints are ungated"* is no longer true, and the code that would have caught it asserts only that a URL string appears in the source.

The independent reconciliation (I01–I17) and the repo's own finance scanner agree on every material number. **No production record was created, modified or deleted by this pass.**

### 3.1 — S1 · Six staff mutations are dead in production: the admin app sends no bot token

**This is the highest-severity finding of the pass.**

`guest-app/server/apiRouter.ts` gates these endpoints behind Cloudflare Turnstile — **including the ones that require staff authentication**:

| Endpoint | Gate | Admin client behaviour |
|---|---|---|
| `POST /api/bookings/breakfast/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/breakfast/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/breakfast/mark-refund-paid` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/addons/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/mark-refund-paid` | `verifyTurnstile` | **no admin wrapper exists at all** |

The admin app (`admin-app/src/context/AdminContext.tsx`) sends a decorative header the server never reads:

```ts
headers: {
  "Content-Type": "application/json",
  "Authorization": token ? `Bearer ${token}` : "",
  "X-Spark-Inn-Turnstile": "client-echo"   // the server never reads this header
},
body: JSON.stringify({ ...input, turnstileToken: undefined })  // the field the server reads
```

The comment directly above it states the requirement correctly — *"the client must echo it on every mutation. The apiRouter's `verifyTurnstile` reads it from `req.body.turnstileToken`"* — and then sends `undefined`.

The admin app **mounts no Turnstile widget at all**: there is no `cf-turnstile` element, no `challenges.cloudflare.com` reference and no `turnstile.render` call anywhere in `admin-app/src`. The guest app does mount one (`guest-app/src/hooks/useTurnstileToken.ts`), so the guest side is fine.

Server behaviour (`apiRouter.ts`, `verifyTurnstile`):

```ts
if (!token) {
  return { success: false, error: "Bot verification token is missing." };
}
```

⇒ Every one of those calls returns **HTTP 400 `Bot verification token is missing.`**

**Reproduction**

1. Sign in to the admin app as `adminbot@gmail.com`.
2. Open any booking that has a breakfast selection → **Breakfast** tab.
3. Toggle **Mark served** (or **Save changes**, or **Mark as paid** on a refund liability).
4. The toast reads *"Bot verification token is missing."* and the network panel shows `POST /api/bookings/breakfast/mark-served → 400`.

**Impact**

- The staff cannot mark a meal served → the kitchen list never closes a meal → **BR-08** (the "late served" email that fires on a staff serve action) can never fire.
- The staff cannot record a breakfast refund liability → **BR-08 / BR-09** and the whole refund-liability surface are dead.
- The staff cannot add or remove an other-add-on → **AO-09** and **MRB-11d** are dead.
- The other-add-on refund "mark as paid" surface has **no client at all**.

**Why the existing tests did not catch it.** The repo's own unit tests assert only that the URL string appears in the source:

```ts
expect(adminContext).toContain("/api/bookings/breakfast/mark-served");
```

They never assert that a token is sent, so the suite stays green while the feature is broken in production. `e2e/tests/deploy-posture.spec.ts` adds the missing regression guard.

**Secondary defect — the handoff is stale.** `plan/project/HANDOFF-2026-10-23.md` §5.2 states *"Staff endpoints are ungated and were used for equivalent coverage."* That is no longer true: the breakfast and add-on staff paths **are** gated, and `bookings/cancel` is gated for guests but bypassed for staff. Only the core booking-lifecycle staff endpoints (`create-walkin`, `checkin`, `checkout`, `add-payment`, `verify-and-record-payment`, `reschedule`, `mark-payment-confirmed`, `reject-payment`, `cancel`) are ungated.

### 3.2 — S2 (environment, not a defect) · Turnstile cannot be satisfied from this network

The guest app's write surface is behind Turnstile, and the challenge platform hostnames do not resolve here:

```
https://brunhild.challenges.cloudflare.com/...  →  net::ERR_NAME_NOT_RESOLVED
https://hagen.challenges.cloudflare.com/...      →  timeout
https://valid.alchallenges.cloudflare.com/...    →  fetch failed
https://challenges.cloudflare.com/               →  HTTP 200   (reachable)
```

A real Chrome UA, `--disable-blink-features=AutomationControlled`, the Manila locale/timezone, and a 45-second wait were all tried; the hidden `input[name="cf-turnstile-response"]` never received a value.

The server side is healthy — a deliberate bad token is rejected correctly:

```
POST https://challenges.cloudflare.com/turnstile/v0/siteverify
→ HTTP 200 {"error-codes":["invalid-input-response"],"success":false}
```

⇒ This is a **network limitation of the QA host, not a product defect.** It blocks every guest-side write scenario (booking creation, lookup, self-cancel, breakfast edits, voucher validation, corporate-code validation, inquiry and contact submission) **and** the staff breakfast/add-on scenarios — the latter not by network but by finding 3.1.

The anti-automation posture itself is **verified as working**: an unverified caller is refused with HTTP 400 `Bot verification token is missing.` before any schema validation, which is the correct order.

### 3.3 — S2 · The admin folio nets *pending* refund liabilities against money already collected

`BREAKFAST.md §Removal semantics` is explicit:

> *Removing a paid meal: … a `bookings/{id}/refunds/{refundId}` entry is created with `category: "breakfast"`, `status: "pending"`, `type: "refund"`, `amount: -priceSnapshot`; **the booking's `paidAmount` is unchanged (the refund is a liability, not a debit)**.*

But the admin's ledger normaliser never reads `status`:

```ts
// admin-app/src/utils/bookingPaymentEntries.ts — normalizeLedgerDoc
const type = data.type === "refund" || amount < 0 ? ("refund" as const) : ("payment" as const);
return { ..., amount, ... };   // ← `status` is dropped
```

and `buildBookingPaymentIndex` sums every entry into `paymentsTotal`. A **pending** liability is therefore subtracted from money the hotel still holds.

Production effect (reconciliation check **I06b**):

| Booking | Collected | Pending refund | Admin shows paid | Admin shows balance |
|---|---|---|---|---|
| `SI-20261021-00058` (cancelled) | ₱2,800 | −₱100 (breakfast, pending) | **₱2,700** | **₱100** |
| `SI-20261021-00060` (cancelled) | ₱2,800 | −₱100 (breakfast, pending) | **₱2,700** | ₱0 |

`SI-20261021-00058` is a **cancelled** booking that the desk is shown as owing **₱100** on. The correct figures are ₱2,800 collected, ₱0 outstanding, with a ₱100 refund liability shown separately (which is where the Refunds view belongs).

This also propagates into the quick-view chips: correcting for it moves the recomputed chip counts from 13/56 to **14 paid / 55 balance due**, which is exactly the truth the handoff recorded independently.

### 3.4 — S2 · Other add-on revenue still never reaches the revenue allocation (MRB-11b)

The MRB-11 backfill fixed the allocation *identity* but not the add-on *content*:

| Booking | `otherAddOnTotal` | `revenueAllocation.addOnNet` | `rateBreakdown.addOns` |
|---|---|---|---|
| `SI-20261021-00053` | ₱1,500 (3 × ₱500 airport transfer) | **₱0** | **`[]`** |
| `SI-20261021-00055` | ₱1,000 (2 × ₱500 airport transfer) | **₱0** | **`[]`** |

Reconciliation check **I16** quantifies it:

```
allocation revenue stream totalNet = ₱282,760.00
folio billed                      = ₱286,710.00
Δ                                 = −₱3,950.00
```

The guest is billed **₱9,600** on `SI-20261021-00053` (₱8,100 room + ₱1,500 transfer) through the folio, but every revenue stream that reads `revenueAllocation` under-reports by ₱3,950 across the book. The historical report lists this as *"AO-04 — FIXED, SHIPPED 2026-10-22"*; the two rows are unchanged in production.

Note the interaction with finding 3.1: the staff path that would repair this (`addons/staff-update`) is dead, and the guest path is Turnstile-gated — so there is currently **no working path** that can set `addOnNet` for an existing booking.

**A second, independent symptom on the same booking.** The drawer's Add-Ons tab for `SI-20261021-00053` shows **"Other Add-Ons — Total: ₱1,500"** but only itemises **₱500** (the 2026-11-06 line). The 2026-11-05 line reads *"No add-ons for this date."* — yet that date carries 2 × ₱500 in the raw document.

The cause is in the **seeded record**, not in the app's rule: the 2026-11-05 selection is written without `addedAt`, `addedBy` **or `removedAt`**:

```
2026-11-05 → [{ addOnId: "airport-transfer", quantity: 2, priceSnapshot: 500, … }]   ← no addedAt / removedAt
2026-11-06 → [{ addOnId: "airport-transfer", quantity: 1, priceSnapshot: 500, addedAt: "…", removedAt: null, … }]
```

and the drawer keeps only entries where `removedAt === null` (`admin-app/src/components/BookingDrawerWorkspace.tsx:2664-2666`) — the documented liveness convention (`plan/features/BREAKFAST.md` §Removal semantics), applied correctly. The stored `otherAddOnTotal` was written by a different path and still counts the malformed row.

The visible consequence for staff is a **drawer whose own two numbers disagree**: a total of ₱1,500 that cannot be itemised. This is a **seed-data defect**, not an app-logic defect — but it makes `SI-20261021-00053` unusable as a reference fixture, and it means the ₱3,950 in the table above is *partly* a data-shape problem rather than purely a missing write path. The assignment forbids backfilling records, so the row is left as it is and reported here.

### 3.5 — S3 · `booking.paidAmount` went negative on one booking and the refund path used an unseeded base

`SI-20261021-00011` (`A2FD10Walkin0001`):

```
totalPrice        = ₱5,400
ledger (collected)= ₱4,400   (₱5,400 payment − ₱1,000 cancellation refund)
booking.paidAmount= −₱1,000  ← NEGATIVE
```

The refund path decremented `paidAmount` from a base that was never seeded, so the field is negative rather than ₱4,400. The admin's paid column is computed from the ledger index (so the desk sees ₱4,400), but `shared/utils/bookingAddOnReschedule.ts` uses `paidAmount` as the "was this meal paid for?" budget — a negative base makes that test fail, so **a paid breakfast removed on this booking would not open a refund liability**.

Reconciliation check **I06** flags it. 14 further bookings carry ledger entries but **no** `paidAmount` field at all (legacy rows); the admin does not use the field for the paid column, so this is a consistency gap rather than a visible defect — but it is the same field the add-on reschedule path reads.

### 3.8 — S4 · The 404 handler leaks `undefined` into the error message

```
GET https://www.sparkinnbohol.com/api/version
→ 404 {"success":false,"error":"Endpoint /api/version/undefined not found."}
```

The route parser splits the path into `domain`/`action`, and the message template interpolates the missing `action` verbatim. Cosmetic, but it tells a caller that the server is confused rather than that the path is wrong.

**Related note (OP-02).** The handoff describes a `GET /api/version` endpoint returning the API bundle version. **No such endpoint exists** — `/api/version`, `/api/health`, `/api/rooms` and `/api/availability` all 404 with the message above; the router only dispatches `domain/action` pairs. ### 3.9 — S1 · The guest app's CSP blocks the Google auth script — Google sign-in is broken

The guest site loads `https://apis.google.com/js/api.js` at runtime (Firebase Auth's `signInWithPopup`). The **guest** deployment's Content-Security-Policy does not allow it:

```
https://www.sparkinnbohol.com/      script-src 'self' 'unsafe-eval' https://www.gstatic.com
                                     https://www.google.com https://www.googletagmanager.com
                                     https://challenges.cloudflare.com https://browser.sentry-cdn.com
                                     → apis.google.com MISSING

https://admin.sparkinnbohol.com/    … https://www.google.com https://apis.google.com …
                                     → apis.google.com PRESENT
```

The browser therefore blocks the script and logs a CSP violation on guest pages:

```
Loading the script 'https://apis.google.com/js/api.js?onload=__iframefcb331067' violates the
following Content Security Policy directive: "script-src 'self' 'unsafe-eval' …"
```

**The cause is a file-level omission.** Three CSPs exist in this repository:

| File | Governs | `apis.google.com` in `script-src` |
|---|---|---|
| `vercel.json` (root) | — (not a deployment) | **yes** |
| `admin-app/vercel.json` | admin.sparkinnbohol.com | **yes** |
| `guest-app/vercel.json` | **www.sparkinnbohol.com** | **NO** |

`plan/project/ROADMAP.md` records the original fix (commit `03b18d4`, MBUX-10 Bug B): *"the CSP permits the Google auth iframe script in BOTH `vercel.json` files"*. The fix was applied to the root and the admin app; the file that actually governs the guest deployment was **not** updated.

**Reproduction**

1. Open `https://www.sparkinnbohol.com/signin` in a browser with the console open.
2. The CSP violation is logged on page load.
3. Click **Continue with Google** — the popup cannot initialise, because the script that bootstraps it was blocked.

**Why the existing test did not catch it.** `guest-app/tests/api/mbux-10-phase-15-closeout.test.ts` asserts *"the CSP permits the Google auth iframe script in BOTH `vercel.json` files"* — it checks two files and never the third, so the suite stays green while the guest site is broken.

**Fix** — one token in `guest-app/vercel.json`:

```
script-src 'self' 'unsafe-eval' https://www.gstatic.com https://www.google.com
          https://apis.google.com https://www.googletagmanager.com
          https://challenges.cloudflare.com https://browser.sentry-cdn.com
```

`e2e/tests/deploy-posture.spec.ts` (`SEC-CSP`) is the regression guard: it reads the **live** CSP header and fails while the guest origin omits the host.

### 3.10 — S2 · The desk's incoming-call listener is denied in production — the front desk cannot see a room call

Every admin-app sign-in logs:

```
Error listening to WebRTC calls: FirebaseError: Missing or insufficient permissions.
```

for **both** the admin and the front-desk identity. The listener is `collectionGroup(db, "callSessions")` in `admin-app/src/context/AdminContext.tsx:5591` — it is how the desk learns that a guest is ringing.

**Proved against production with real staff ID tokens** (Firestore REST `runQuery`, `allDescendants: true`):

| Query | Admin | Front desk |
|---|---|---|
| `collectionGroup("callSessions")` — the desk's incoming-call listener | **HTTP 403** | **HTTP 403** |
| `collection("callSessions")` — the same collection, top level only | HTTP 200 | HTTP 200 |
| `collectionGroup("messages")` — the desk's inbox thread | HTTP 200 (2 docs) | HTTP 200 (2 docs) |
| `collection("intercoms")` — control | HTTP 200 (8 docs) | HTTP 200 (8 docs) |

So the denial is **specific to the group query**, and it hits both staff roles identically — it is a rules-shape problem, not a role problem.

**Cause.** A Firestore collection-group query must be *provably* safe: the rule set has to guarantee the query can only return documents the caller may read, for **every** path in the group, including paths that do not exist yet. The rules grant the two `callSessions` shapes unconditionally:

```rules
match /callSessions/{sessionToken} {
  allow read, create, update, delete: if true;
  match /iceCandidates/{candidateId} {
    allow read, create, update, delete: if true;
  }
}
```

but the `intercoms/{roomId}` block is **conditional**:

```rules
match /intercoms/{roomId} {
  allow read: if isStaff();      // ← conditional
  allow write: if isStaff();
}
```

**Corrected root cause (2026-10-24).** This section originally blamed the conditional `intercoms` arm for poisoning the group query. That is **wrong**, and the emulator proves it: a Firestore `match /intercoms/{roomId} { … }` block applies to `intercoms/{roomId}` **only** — `match` blocks do **not** cascade into a document's subcollections. So the `intercoms/{roomId}` arm never covered `intercoms/*/callSessions/**` in the first place.

The real cause is the inverse: **no rule covered the nested path at all.** The `match /callSessions/{sessionToken}` block matches a **top-level** `callSessions` collection only; a session stored under a room (`intercoms/{roomId}/callSessions/{token}`) is a different path and matched **no** `allow` rule. A collection-group query over `callSessions` has to be provably safe for **every** path in the group, so one path with no rule denies the whole query — for both staff roles.

**Fix (shipped 2026-10-24)** — give the nested shape its own unconditional-for-staff rule, mirroring the `messages` group:

```rules
match /{path=**}/callSessions/{sessionToken} {
  allow read: if isStaff();
}
```

**Regression test:** `firebase/tests/call-sessions-collection-group-read.emulator.test.ts` now pins the staff group read (both roles), the single-doc read, the token-holder read, and that an anonymous caller is still refused. **It runs** — Temurin 21 was installed and `npm run test:rules` is green on this host: **13 files, 125 tests, 0 failed**.

> The first version of that test was written on 2026-10-23 and had never executed (no JDK). When it finally ran, it **failed** — because it used an identity with no staff `role` claim, so it was asserting a denial that had nothing to do with the defect. It was rewritten against the real role claims before the rule change, so the test now fails for the right reason and passes for the right reason.

**Impact**

- The desk never receives an incoming-call notification — a guest who taps *Call the front desk* in the room intercom gets no ring on the desk's side.
- It also affects any other consumer of the `callSessions` group.
- The `messages` group is unaffected, so **text chat still works** — the desk sees and replies to guest messages. Only the voice-call surface is dead.

### 3.13 — S2 · A signed-in member is quoted the member rate and billed the full rate

**Found by executing the guest-write scenarios (2026-10-25) — the scenario was BLOCKED until the bot-protection switch opened the public write path.**

The client knew who the guest was — it read the member profile from the auth context (`useGuestAuth()`), **mirrored** the discount into the price summary (`memberDiscountPct` at `BookingPage.tsx:525-531`) and then posted the booking anonymously. ### 3.14 — S3 · Removing an other add-on reports a failure for a change that succeeded

**Found by executing the guest-write scenarios (2026-10-25) — scenario AO-08.**

The guest **Manage Other Add-Ons** page assembled its save batch inline and emitted **both** a `change` op with quantity 0 **and** a `remove` op for the same line:

```ts
// guest-app/src/pages/ManageOtherAddOnsPage.tsx — before the fix
} else if (draftEntry.quantity !== origEntry.quantity) {     // quantity 0 → a CHANGE op
  changeOps.push({ selectionKey: key, addOnId, quantity: draftEntry.quantity, … });
}
…
if (!draftEntry || draftEntry.removedAt !== null || draftEntry.quantity === 0) {
  removeOps.push({ selectionKey: key, addOnId });             // …and a REMOVE op
}
```

The server processes **REMOVEs first, then ADDs, then CHANGEs** (`guest-app/server/handlers/addons-manage-save.ts:304`, `:387`, `:472`). So the change op landed on a selection the remove had already taken away and failed with `SELECTION_NOT_ORDERED` — which the handler maps to the guest-facing message **"Nothing to change — add the add-on first."** (`:133`).

**The removal itself was applied.** The transaction commits before the op error is reported, so the add-on was removed, the total was corrected, and the refund liability was written — and the guest was told it failed.

**Reproduced live (2026-10-25):** the guest adds an airport transfer (₱500), saves, sets the quantity back to 0 and saves again:

| | Before the fix |
|---|---|
| The add | ✅ *"Add-ons saved."* · total ₱500 |
| The removal | ❌ *"Nothing to change — add the add-on first."* |
| What the server stored | the line **was** removed (`removedAt` set), the total **was** corrected |

The production evidence is in the record list (§9.1.1): bookings `SI-20261025-00008` and `SI-20261025-00009` still carry a **live** ₱500 add-on — the guest gave up after the error and never re-saved. The fixed run (`SI-20261025-00011`) carries the same line as **removed**, with `otherAddOnTotal: 0`.

**Impact**

- A guest who removes an add-on is told it failed. Most guests will try again, and some will contact the front desk about a change that already happened.
- The staff path was never affected: the admin drawer uses a mutually exclusive `op.kind` (`add` / `change` / `remove`), so it never sent both ops for one line.

**Fix:** the batch is assembled by the shared helper `buildOtherAddOnManageOps` — **a quantity of 0 is a REMOVAL, never a change with quantity 0** — and the server no longer misreports a redundant quantity-0 change op on a removed selection (it is a no-op, not a failure). **Shipped in v2.20.1** — §11.9.

**Regression guard added:** `guest-app/tests/api/oct-m6-addon-removal-ops.test.ts` (7 runtime assertions + 4 source tripwires).

### 3.15 — S1 · A guest booking WITH breakfast cannot be created at all

**Found by executing the guest-write scenarios (2026-10-25) — scenario BF-03. This is the most severe finding in the report: it is a hard outage on a revenue-bearing path.**

The guest picks breakfast on step 2 of the booking flow and confirms. The server answers **HTTP 500**:

```
[MRB-11] revenue allocation invariant violation: roomNet(2400) + breakfastNet(0)
  + addOnNet(0) - deductionNet(0) = 2400, expected totalNet(2600).
  This is a server-side bug — the pricing chain returned an inconsistent allocation.
```

**The root cause.** Per **BR-03 (2026-10-12, decision #232)** the breakfast became a **reservation-level** term — per date × per guest — and the create path's per-STAY `breakfastTotal` is now always `0` (`guest-app/server/handlers/bookings.ts:3200`). But the MRB-11 revenue allocation still read the **per-STAY** field:

```ts
// guest-app/server/handlers/bookings.ts — before the fix
revenueAllocation: assertBookingRevenueAllocationInvariant(
  {
    roomNet: pricingForRoom.roomTotal,
    breakfastNet: pricingForRoom.breakfastTotal,   // ← the per-STAY value: always 0
    …
    totalNet: pricingForRoom.totalPrice             // ← the child's share, WHICH carries the breakfast
  },
  …
)
```

The child's total carries the reservation's breakfast (₱200 for two guests), the breakfast stream says ₱0, and the invariant — which exists precisely to catch a pricing chain that does not add up — **throws**. The guest sees a failed booking and a generic error. Nothing is written; no money moves; the stay is simply lost.

**Why it is arithmetic, not a rounding wobble.** With `w_i` the child's room weight:

```
childTotal  = w_i/Σw · (Σw + breakfast − deductions)
room_i + extraBed_i = w_i
⇒ breakfast_i = w_i/Σw · breakfast
```

so the child's share of the breakfast **must** be allocated with the same weights as the child's total. Reading the per-STAY field instead is off by exactly the breakfast amount — ₱200 here, which is exactly the gap in the error message.

**How long has it been live?** The shape dates from BR-03/BR-08 (2026-10-12/14). It was never visible in the QA pass because **no booking with breakfast could exist** — the QA pass could not create one, so the check had nothing to check. It only became visible once the bot-protection switch re-opened the public write path.

**What production data shows.** The only bookings in production with a live breakfast slot are four **walk-in** records from the hotel's own "Pre-Go Live 2" test run (2026-10-21) — the staff path, which does not go through the public create handler. Two of them (`SI-20261021-00037`, `-00052`) carry a correct allocation; two (`SI-20261021-00056`, `-00057`) carry `breakfastNet: 0` with the breakfast inside `roomNet` — the same class of gap, on the walk-in path, where it does not throw.

**Impact**

- **Every guest who selects breakfast is unable to book.** The hotel's headline add-on — ₱100 a meal, per guest, per night — is unbuyable through the public site.
- The failure is a 500, not a 4xx: the guest cannot tell that the cause was breakfast, and the front desk sees a server error rather than a booking request.
- Nothing is charged and no partial record is left behind — the transaction rolls back — so the blast radius is "lost bookings", not "wrong bills".

**Fix:** the child's share of the reservation's breakfast is allocated with the same weights as the child's total (`allocateRoundedAmount(breakfastTotal, roomStayWeights)`), and the aggregate sums those shares. The per-STAY field is no longer the allocation's source. **Shipped in v2.20.2** — §11.9.

**Regression guard added:** `guest-app/tests/api/br-03-breakfast-allocation.test.ts` (4 runtime assertions on the arithmetic + 4 source tripwires) and `e2e/tests/guest-write.spec.ts` · *BF-03 · the breakfast price follows the guest count* — which books with breakfast through the real UI and asserts the server charges two meals and the allocation balances.

### 6.2 What the suite deliberately does NOT do

- **It never asserts a weaker expectation to get a green run.** Where a product defect is real, the test **fails** and the report names the defect (§3.1, §3.9).
- **It never creates a booking.** Every guest write path is gated; the specs assert the gate, and the creation legs are recorded as BLOCKED.
- **It never writes credentials, tokens or auth state to disk.** No `storageState` file is produced.
- **It never skips silently.** A missing credential produces a skip with an explicit reason in the run output. With the credentials supplied, the suite now runs **every** spec — there are no skips left.

### 11.1 §3.4 — the other add-ons now reach the revenue allocation

The earlier diagnosis of this finding was wrong, and the corrected one is what the fix is built on.

**What it is NOT.** It is not a write path that lost the value. `revenueAllocation.addOnNet` is computed from **`extraBedTotal`** — the extra-bed revenue — at every one of the seven write sites, and the MRB-11 allocation schema (`roomNet`, `breakfastNet`, `addOnNet`, `deductionNet`, `totalNet`) has **no stream for the BR-12 other add-ons at all**. `totalNet` equalled `booking.totalPrice`, which per OCT-FOL-01 (decision #298) **excludes** the other add-ons — they sit on top of the room bill for the balance. **What it ALSO was.** A write-path gap on top of that: the two add-on write paths — the guest's "Manage Other Add-Ons" page (`guest-app/server/handlers/addons-manage-save.ts`) and the staff add-on update (`addons-staff-update.ts`) — wrote `otherAddOnSelections` / `otherAddOnTotal` onto the booking **but never re-derived `revenueAllocation`**. ### 11.5 §3.6 — the first fix was wrong, and the deployment proved it

This is the one finding where the fix itself had to be corrected, and the record is worth keeping.

**The first fix (v2.19.0) was wrong.** It moved the ledger resolution from the snapshot callback to the commit point, on the theory that the mapper had been committing a stale copy over the rows the re-hydration effect had already repaired. The deploy proved it wrong: the live list still read **69 / 10 / 69** with **0** "Fully paid" pills.

**The actual root cause was the effect's dependency list:**

```js
useEffect(() => {
  setBookings((prev) => {
    if (!prev.length) return prev;      // ← short-circuits on an empty list
    …
  });
}, [paymentIndex, currentUser]);        // ← the ROWS were not a dependency
```

The payments listener and the bookings listener are independent, so this order is possible:

1. the payments listener delivers → the index is built → the effect runs → `prev.length` is 0 → it short-circuits;
2. the bookings listener delivers → the rows are committed **unhydrated**;
3. the index does not change again → **the effect never runs again** → nothing ever re-derives the rows.

Step 3 is the bug: the effect only watched the *index*, so the one moment it could have repaired the rows — after they arrived — was the one moment it could not see them.

**The fix (v2.19.1):** depend on the rows as well — `}, [paymentIndex, currentUser, bookings]);` — so whichever arrives last re-derives them. No render loop: the updater returns `prev` when nothing changed, so React bails out.

**Live proof (v2.19.1, measured):**

| | Before | After | Independent recomputation (I18) |
|---|---:|---:|---:|
| All bookings | 69 | 69 | 69 |
| **Balance due** | **69** | **53** | **53** |
| **Needs attention** | **10** | **5** | **5** |
| "Fully paid" pills (mobile) | **0** | **14** | 16 bookings paid |

### 11.5.1 The list's model is not the folio's model — and that is not a defect

The list builds its folio **without the incidental charges**: `getBookingFolio` passes `selectedBookingCharges` only for the **selected** booking, so a row in the list has `chargesTotal = 0` (the drawer loads the charges per booking). The list's "Balance due" is therefore legitimately **lower** than the folio's.

So there are two correct figures, and the reconciliation now computes **both**:

| Check | Model | Result |
|---|---|---|
| **I11** | the **folio**'s model (room + other add-ons + store + incidental charges) | PAID 15 · Balance due 54 · Needs attention 6 |
| **I18** | the **list**'s model (room + other add-ons + store, no charges) | PAID 16 · PARTIAL 1 · UNPAID 52 · Balance due 53 · Needs attention 5 |

The Playwright chip assertion is pinned to **I18** (the list's own model), so it is checked against an independent recomputation rather than against the app's own output. Before the fixes the list's figure was 69 — which is neither model.

The "Fully paid" pill is rendered **only by the mobile card** (`renderBookingCard`); the desktop table has no payment-state column at all, so the desktop list can only be checked through the advanced filter (FL-02). The e2e spec now says so explicitly instead of looking for an element the desktop layout never renders.

### 11.6 What the bot-protection switch re-opened — and what it costs

The owner switched the hotel-wide bot protection off (`settings/hotelConfig.botProtectionMode: "disabled"`, recorded against the admin's uid on 2026-10-25) so the guest-write scenarios could be executed. It works — the server honours it on **every** gated path, because the check now sits inside `verifyTurnstile` itself, before the token check:

| Path | With the switch ON | With it OFF |
|---|---|---|
| `POST /api/email/booking-submitted` (no credential) | 400 "Bot verification token is missing." | **400** "Booking reference and guest email are required." ✓ SEC-10 |
| `POST /api/email/booking-submitted` (wrong email) | 400 "Bot verification token is missing." | **404** "Booking not found." ✓ SEC-11 |
| `POST /api/validate/voucher` (`FLAT500` on the wrong room) | 400 "Bot verification token is missing." | **400** "Voucher does not apply to this room type." ✓ VC-03 |
| `POST /api/validate/voucher` (`EXPIRED1`) | 400 "Bot verification token is missing." | **400** "Voucher has expired." ✓ VC-04 |
| `POST /api/validate/voucher` (`OFFNOW`) | 400 "Bot verification token is missing." | **200** `{"discountType":"percent","discountValue":15}` ✓ VC-01 |
| `POST /api/validate/corporate-code` (nonsense) | 400 "Bot verification token is missing." | **400** "That code is not recognized. Check the code, or continue without a code." ✓ CO-05 |

Six scenarios moved out of BLOCKED, and a new Playwright spec (`e2e/tests/guest-write-paths.spec.ts`) pins all six against the **deployed** server.

#### The cost — please turn the switch back off when the QA is done

The booking lookup accepts a **ref alone** by design (`feat/relax-booking-lookup`, decision #209 of 2026-08-10 — `plan/features/BOOKING-LOOKUP.md:143`):

> "Enumeration is bounded by the 3-digit daily sequence (~1000 keys/day) **+ Turnstile + the 10/min rate limit + 3-failure 1-hour backoff**."

The live endpoint returns the guest's **phone number, stay dates, nightly rate, total and special requests** for a ref with a **wrong or empty** email. The catalogue's LK-02 wording ("a wrong email never leaks a booking") was retired by that decision and should be re-worded.

With Turnstile off, **one of the three load-bearing defences is disabled**. What remains is the 10/min per-IP limit and the per-target 3-failure 1-hour backoff — enough to stop a burst, not enough to stop a slow sweep of a day's refs. The refs are `SI-YYYYMMDD-NNNN` (a 5-digit sequence in production), so a day is ~10⁵ keys.

**Recommendation:** treat the switch as a **testing window**, not a mode. Run the guest-write scenarios, then set it back to `"turnstile"` from the same admin screen (the audit fields clear with it). The switch is fail-closed, so forgetting to turn it back on is the only risk — the red banner in Settings → Environment Testing exists for exactly that.

### 11.7 The client now reads the same switch

`verifyTurnstile` honoured the mode on the server, but the **guest client** gated on the token in six places — the booking Confirm button, the voucher Apply, the lookup submit, the cancel, the extend-stay and the corporate inquiry form — so the browser could not submit at all. That is the repo's own recorded lesson, in `BookingPage.tsx`:

> "The lesson generalises: whenever the client gates on a value the server does not validate, the gate is decorative."

The client now reads the same `botProtectionMode` through the public hotel-config projection and skips the token requirement **only** when the mode is exactly `"disabled"`. The Turnstile widget does not mount at all in that mode. Every gate is still in force in the default mode.

### 11.9 The three findings the guest-write scenarios found

The guest-write scenarios could not run until the bot-protection switch opened the public write path. Running them found **three** defects that no other check could reach — each of them on a path that had never been executed end to end.

| Finding | Severity | The symptom in production | The fix |
|---|---|---|---|
| **§3.13** the member rate the guest is charged | S2 | a signed-in member was quoted ₱2,160 and charged ₱2,400 | the booking create carries the member's ID token (both the public and the corporate flow) |
| **§3.14** the add-on removal | S3 | the guest was told "Nothing to change — add the add-on first." for a removal that had already been applied | `buildOtherAddOnManageOps` — a quantity of 0 is a REMOVAL, never a change with quantity 0 — plus the server no longer misreports the redundant op |
| **§3.15** a booking with breakfast | **S1** | the guest's booking failed with HTTP 500 — *"revenue allocation invariant violation"* | the child's share of the reservation's breakfast is allocated with the same weights as the child's total |

**What the three have in common.** Each is a case where **two layers disagreed about the same value**:

- §3.13 — the client computed a member discount the server was never told about;
- §3.14 — the client sent two contradictory operations for one line, and the server processed them in an order that made the second one fail;
- §3.15 — the server's allocation read the breakfast from the per-STAY field while the pricing chain used the reservation-level one.

None of them is a typo. Each is a **contract between two layers that was never exercised**, because the public write path was closed to the whole QA pass. That is the finding underneath the three: **the write path had never been run, so nothing on it could be trusted.**

**The guard pattern.** Each fix is pinned twice — once in the repo's own test suite (so the defect cannot come back in a branch) and once by the browser spec (so it cannot come back in a deploy):

| Finding | Repo guard | Browser guard |
|---|---|---|
| §3.13 | `guest-app/tests/api/rw-02-member-rate-token.test.ts` | `e2e/tests/guest-write.spec.ts` · *RW-02* — the amount shown vs the amount charged |
| §3.14 | `guest-app/tests/api/oct-m6-addon-removal-ops.test.ts` | `e2e/tests/guest-write.spec.ts` · *AO-08* — add, then remove, then the total is back to zero |
| §3.15 | `guest-app/tests/api/br-03-breakfast-allocation.test.ts` | `e2e/tests/guest-write.spec.ts` · *BF-03* — two guests are charged two meals |

**One more thing the pass found — a guard that had never been green.** `guest-app/tests/api/bot-protection-client-gate.test.ts` asserted that the public-config reader "carries the mode" with a case-sensitive literal scan for `botProtectionMode` — but the reader never spells the field out; it inherits it from the shared type, where the name appears as the capitalised `BotProtectionMode`. **The guard had been RED since the day it was written** (the client-switch commit, `ba8173c9`), and the earlier "all green" verification had missed it. It now pins the real invariant: the reader uses the shared public projection, and the projection declares the optional mode field.
