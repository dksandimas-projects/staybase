## 0. Headline

Three defects that stop a member of staff doing their job **were live in production when this pass ran on 2026-10-23**. All three are now **fixed, shipped and verified live** (§11.8). The findings below are written as they were observed on 2026-10-23:

1. **Six staff mutations are dead** — the admin app sends `turnstileToken: undefined` to endpoints the server gates behind Cloudflare Turnstile, and mounts no widget to get one. **Mark served**, **record a breakfast refund**, **add/remove an other-add-on**, and their refund equivalents all return `HTTP 400 Bot verification token is missing.` (§3.1)
2. **The desk cannot see a room call** — the admin app's incoming-call listener is a `collectionGroup("callSessions")` query, and against production that query is **denied with HTTP 403 for both staff roles**, while the single-collection and `messages` reads return 200. Every sign-in logs `Missing or insufficient permissions`. (§3.10)
3. **Google sign-in is broken on the guest site** — `guest-app/vercel.json` omits `https://apis.google.com` from `script-src`, so the browser blocks the Firebase Auth script. The root and admin CSPs have it; only the file that governs the guest deployment does not. (§3.9)

Two more defects change numbers the desk relies on:

4. The hotel's revenue streams **under-report by ₱3,950** — two bookings carry other add-ons that never reach `revenueAllocation`, so every report that reads the allocation is wrong while the folio bills the guest correctly. The repo's own finance scanner finds the same two rows. (§3.4)
5. The admin folio **nets pending refund liabilities against money already collected**, so a cancelled booking with ₱2,800 collected is shown as owing ₱100. Correcting for it reproduces the handoff's independently recorded truth exactly — **14 paid / 55 balance due** — against the app's **0 / 69 / 10**, and the authenticated browser pass reproduces that same signature end-to-end (§3.3, §3.6)

And two more found in the authenticated pass:

6. `booking.paidAmount` went **negative** (₱−1,000) on one booking because the refund path decremented a base that was never seeded; that same field is what the add-on reschedule path reads to decide whether a meal was paid for. (§3.5)
7. The front desk is **shown admin-only navigation it cannot use** — `Rates`, `Members` and `Settings` appear in the nav and every one of them answers "ACCESS DENIED". The route guard is real; the nav is not role-filtered. (§3.11)

And one smaller one found while fixing a test flake:

8. The dashboard's **"Pending refunds" card lands on the wrong Reports tab** — it navigates to `/reports?tab=liability`, but the Reports page never reads a `tab` parameter, so the desk's shortcut to the money-to-process queue opens the Performance tab instead. (§3.12)

And one correction to the handoff itself: **every public guest write endpoint is Turnstile-gated, including the staff breakfast and add-on paths** — §5.2's claim that *"Staff endpoints are ungated"* is no longer true, and the code that would have caught it asserts only that a URL string appears in the source.

**Then the guest-write pass (2026-10-25) found three more**, because the hotel-wide bot-protection switch finally let the public write path run — a path that had **never been executed end to end** before (§11.9):

9. **A guest booking WITH breakfast could not be created at all** — the server answered **HTTP 500** (*"revenue allocation invariant violation"*) because the revenue allocation read the breakfast from the per-stay field while the pricing chain used the reservation-level one. The hotel's headline add-on was unbuyable through the public site. (§3.15)
10. **A signed-in member was quoted the 10% member rate and charged the full rate** — the review step showed ₱2,160 and the server charged ₱2,400, because the booking create never carried the member's ID token. (§3.13)
11. **Removing an other add-on reported a failure for a change that had succeeded** — the guest was told *"Nothing to change — add the add-on first."* for a removal the server had already applied. (§3.14)

All three are fixed and deployed (v2.20.1, v2.20.2), and the **final Playwright run is 111 passed · 0 failed · 11 skipped** against the deployed v2.20.3.

**Then the Tier-3 write pass (2026-10-26) found five more**, because the four approved **write** scenarios — the refund chain, the in-room store, the points redemption and the rewards signup — were executed against production for the first time (§11.10):

12. **The guest's "Manage breakfast" page could never render a stay** — the handler read its parameters from the request **body**, and a GET has no body, so every load answered HTTP 400. (§3.18)
13. **The drawer's "Refunds due" panel was dead** — `booking.refunds` was declared on the `Booking` type and never populated, so a pending refund liability could never be settled from the UI. (§3.19)
14. **A member's past bookings were never linked to their account** — the registration endpoint only links them once the email is verified, and nothing ever re-ran it, so "My Stays" was empty for every email/password member. (§3.20)
15. **The email-verification link could never be completed** — the link points at Firebase's own action handler, so the guest lands back on `?emailVerified=true` with **no** `oobCode`; the app only ever looked for the `oobCode`, and the first fix then refreshed the token before the session had been restored. The guest was told to check an inbox that never received a mail. (§3.21)
16. **`www.sparkinnbohol.com` was not an authorized domain** — so the server's verification link was refused outright (*"Domain not allowlisted by project"*), **no verification email was ever sent**, and Google sign-in was broken on the guest site. (§3.22)

And one more, found by the reconciliation the Tier-3 pass itself provoked:

17. **The refund the desk records was written without a settled status** — the drawer's "Record Refund" had already paid the money out and decremented `paidAmount`, but the record carried no `status`, so every read path classified it as a **pending liability**: the guest's balance was understated by the refund amount, and the dashboard's "Refunds due" queue listed a refund that had **already been paid in cash**. (§3.23)

All six are fixed and deployed (v2.20.6 → v2.20.11). **ST-04 found no defect at all** — the server's stock guard held on the first attempt.

And the last two, fixed in **v2.20.12**:

18. **The desk's store-order actions were a raw client-side write** — so the order state machine existed only as UI *buttons*. Any staff client could write any status onto any order, including cancelling an order that had already been **delivered** and whose cash tender had been recorded. The result is the worst shape a store order can take: money collected against a void order, a guest who is never told, and a reconciliation delta that never closes. The transitions are server-owned now, and the server **refuses any transition on an order that holds a tender**. (§3.7)
19. **The 404 handler leaked `undefined`** into the error message — `Endpoint /api/version/undefined not found.`. Cosmetic, but it told the caller the server was confused rather than that the path was wrong. It now echoes the path that was asked for. (§3.8)

**No findings remain open.** The matrix now has **no FAIL row at all** (70 PASS · 0 FAIL · 2 PARTIAL · 7 BLOCKED · 31 MANUAL · 5 N/A), and the independent reconciliation is **13 PASS · 0 FAIL**.

> ### ⚠️ A second audit addendum — 2026-10-27: the ADMIN app was silently not deploying
>
> **While applying the fixes above, the admin app's build was broken, and the only reason it was found is that the deployed admin app was checked against its expected version.** The production **admin** app was on **v2.21.9** while the production **guest** app was on **v2.21.16**. > **The cause was this audit's own F-D3 work.** The new finance-scanner test imported the root script `scripts/finance-integrity-scan.ts`, which imports `firebase-admin` and `dotenv`. The admin app declares **neither**, and the admin Vercel project has `rootDirectory=admin-app`, so only the `admin-app` workspace is installed — those two packages are simply absent there. On a developer machine the root `node_modules` hoisting makes them resolve, so **the local build passed and the deployed build did not**. The admin app was therefore missing the **kitchen-list fix**, the **store-report CSV export** and the **F-A6 instruction fix** for the whole period.
>
> **The fix and the standing guard.** The scanner is split into a **pure core** (`scripts/finance-scan-core.ts` — the rules, with no imports at all) and the **script** (the Firestore reads and the CLI, which re-exports the core), and both tests now import the pure core. A new gate — `npm run check:app-closure`, wired into `npm test` — asks TypeScript for the **exact program each app would compile** and fails when any file in it references a package outside that app's own dependency closure. It is proved in both directions: run against the pre-fix test file it fails with the same three `TS2307` findings, and with `firebase-admin` and `dotenv` renamed out of the resolution path — a faithful simulation of the isolated Vercel install — the pre-fix admin build reproduces Vercel's exact 8 errors while the post-fix build passes.
>
> **The lesson worth keeping: a local build passing is not the same as a deployed build passing**, because the deployed build installs a different set of packages. That is now checked rather than assumed.

### 3.1 — S1 · Six staff mutations are dead in production: the admin app sends no bot token

**This is the highest-severity finding of the pass.**

`guest-app/server/apiRouter.ts` gates these endpoints behind Cloudflare Turnstile — **including the ones that require staff authentication**:

| Endpoint | Gate | Admin client behaviour |
|---|---|---|
| `POST /api/bookings/breakfast/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/breakfast/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/breakfast/mark-refund-paid` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/staff-update` | `verifyTurnstile` | sends `turnstileToken: undefined` **explicitly** |
| `POST /api/bookings/addons/mark-served` | `verifyTurnstile` | sends **no** `turnstileToken` |
| `POST /api/bookings/addons/mark-refund-paid` | `verifyTurnstile` | **no admin wrapper exists at all** |

The admin app (`admin-app/src/context/AdminContext.tsx`) sends a decorative header the server never reads:

```ts
headers: {
  "Content-Type": "application/json",
  "Authorization": token ? `Bearer ${token}` : "",
  "X-Spark-Inn-Turnstile": "client-echo"   // the server never reads this header
},
body: JSON.stringify({ ...input, turnstileToken: undefined })  // the field the server reads
```

The comment directly above it states the requirement correctly — *"the client must echo it on every mutation. The apiRouter's `verifyTurnstile` reads it from `req.body.turnstileToken`"* — and then sends `undefined`.

The admin app **mounts no Turnstile widget at all**: there is no `cf-turnstile` element, no `challenges.cloudflare.com` reference and no `turnstile.render` call anywhere in `admin-app/src`. The guest app does mount one (`guest-app/src/hooks/useTurnstileToken.ts`), so the guest side is fine.

Server behaviour (`apiRouter.ts`, `verifyTurnstile`):

```ts
if (!token) {
  return { success: false, error: "Bot verification token is missing." };
}
```

⇒ Every one of those calls returns **HTTP 400 `Bot verification token is missing.`**

**Reproduction**

1. Sign in to the admin app as `adminbot@gmail.com`.
2. Open any booking that has a breakfast selection → **Breakfast** tab.
3. Toggle **Mark served** (or **Save changes**, or **Mark as paid** on a refund liability).
4. The toast reads *"Bot verification token is missing."* and the network panel shows `POST /api/bookings/breakfast/mark-served → 400`.

**Impact**

- The staff cannot mark a meal served → the kitchen list never closes a meal → **BR-08** (the "late served" email that fires on a staff serve action) can never fire.
- The staff cannot record a breakfast refund liability → **BR-08 / BR-09** and the whole refund-liability surface are dead.
- The staff cannot add or remove an other-add-on → **AO-09** and **MRB-11d** are dead.
- The other-add-on refund "mark as paid" surface has **no client at all**.

**Why the existing tests did not catch it.** The repo's own unit tests assert only that the URL string appears in the source:

```ts
expect(adminContext).toContain("/api/bookings/breakfast/mark-served");
```

They never assert that a token is sent, so the suite stays green while the feature is broken in production. `e2e/tests/deploy-posture.spec.ts` adds the missing regression guard.

**Secondary defect — the handoff is stale.** `plan/project/HANDOFF-2026-10-23.md` §5.2 states *"Staff endpoints are ungated and were used for equivalent coverage."* That is no longer true: the breakfast and add-on staff paths **are** gated, and `bookings/cancel` is gated for guests but bypassed for staff. Only the core booking-lifecycle staff endpoints (`create-walkin`, `checkin`, `checkout`, `add-payment`, `verify-and-record-payment`, `reschedule`, `mark-payment-confirmed`, `reject-payment`, `cancel`) are ungated.

### 3.7 — S3 · A cancelled store order can still hold its tender — the desk's order actions were a raw client-side write

**FIXED in v2.20.12 (2026-10-26) · the state machine now lives on the server, and the one QA record the broken path wrote has been repaired.**

Reconciliation check **I17** reproduces the historical F-C1/F-C2 finding, unchanged:

```
delivered revenue                ₱250.00
tenders                          ₱180.00
Δ revenue − tenders              +₱70.00
```

- `SO-20261021-00011` — delivered, add-to-bill, ₱100, `isBilled: true`, **no tender doc**. This is the order that correctly lands on the room folio of `A1BF04Single00001` (folio grand total ₱1,900 = ₱1,800 room + ₱100 store charge — **ST-02 passes at the data level**), so the absence of a tender is consistent for an add-to-bill order and is the correct half of the Δ.
- `SO-20261021-00012` — **cancelled** but still holding a ₱30 tender.

Also live: four store orders sit at `status: "placed"` with `total: 0` (`SO-20261021-00002/00004/00009` and `SO-20261021-00003`), which can never be delivered into a non-zero folio.

**What the first half of the finding's title turned out to be.** "A store order can be delivered without a tender" is **correct behaviour** for an add-to-bill order — its money rolls into the room folio, not into the store's tender ledger (`STORE-MANAGEMENT.md`: *"COD maps to Cash, Add to Bill remains on the booking folio"*). The reconciliation check was wrong about that, and it was the **check** that made I17 fail on a correct record (§4.2). The check now asks the right question: a **direct-paid** delivery owes a tender; an add-to-bill delivery does not. With that correction, I17 named exactly the one record that really was wrong.

**The real defect.** The desk's store-order actions were a **raw client-side Firestore write** — `updateDoc` on `storeOrders/{orderId}` in the admin app. So the state machine existed only as UI **buttons**; nothing enforced it. Any staff client could write **any** status onto **any** order — including cancelling an order that had already been **delivered**, whose direct-payment tender had been recorded. The production record proves it: `SO-20261021-00012` was delivered at 09:31:48 (tender ₱30, cash, recorded by the admin), and cancelled six seconds later with the reason *"QA-TEST A7 C-02b: cancel after delivery"* — the 2026-10-21 pass had built the evidence on purpose.

Three things were wrong with that path at once:

1. **The money.** A cancelled order holding a ₱30 tender is money collected against a void order — and a reconciliation delta that never closes.
2. **The guest.** The drawer says *"The guest will be notified by email"*, and the client-side cancel **sent no email at all**.
3. **The refund.** The guest's own cancel fires a **staff refund review** when a paid GCash order is cancelled (CRL-04), because the guest has already sent the money and a cancellation alone does not issue a refund. The **desk's** cancel did not — so a paid order the desk voided had no refund owner.

**The fix (v2.20.12).** Every staff transition is server-owned now:

| Transition | Owner |
|---|---|
| `confirmed` | `POST /api/store/confirm-order` — the staff endpoint that owns the stock decrement |
| `out-for-delivery` | `POST /api/store/update-order-status` — **new** |
| `cancelled` | `POST /api/store/update-order-status` — **new** |
| `delivered` | `POST /api/store/deliver-order` — owns the tender |

One implementation per rule; the client no longer carries a second copy of the money arithmetic.

**THE TENDER GUARD.** A direct-paid order's tender is written at delivery, under `storeOrders/{id}/payments/delivery-tender`. If that document exists, the money has already been collected — so the order can no longer be voided. It can only be **refunded**, which is a different instrument (`POST /api/bookings/add-refund`). Every transition now refuses a tendered order with HTTP 409, and the state machine is enforced server-side rather than by a button.

The desk also learns about a refusal: the drawer's three buttons now **await** the server and show a toast, and the cancelled state is only displayed once the server has accepted it. (The old path failed as an unhandled promise rejection while the drawer showed the order as cancelled anyway.) The cancel fires the guest's *"store order cancelled"* email and, for a paid GCash order, opens the CRL-04 refund review. The confirm endpoint's error messages now read like sentences instead of raw codes.

**The one record the broken path wrote.** `SO-20261021-00012` was a QA fixture — tagged `isTestData: true`, with the reason *"QA-TEST A7 C-02b: cancel after delivery"*. `scripts/qa/cleanup-37-store-orders.ts` repaired it: it matches on this project's QA marker **and** requires the order to be test data **and** to hold a tender, so no live order can be reached by it. The order goes back to `delivered` — which is what actually happened, and what its `deliveredAt` and its tender both prove — and the cancellation fields are cleared.

**The reconciliation after the repair: `13 PASS · 0 FAIL · 2 WARN · 4 INFO`.** I17's Δ is now **₱100.00 — exactly the add-to-bill total**, which is what it should be.

**What is deliberately NOT closed.** The **Firestore rules** still allow a staff client to write a store order's status (`allow update: if isStaff()`). The app no longer does it, and the server refuses it, but the rules are the last line and they are still open. They are deployed **separately** from the apps (`firebase deploy --only firestore:rules`), so closing that is its own step with its own risk — **recommended as a follow-up ticket**, not done here.

### 3.10 — S2 · The desk's incoming-call listener is denied in production — the front desk cannot see a room call

Every admin-app sign-in logs:

```
Error listening to WebRTC calls: FirebaseError: Missing or insufficient permissions.
```

for **both** the admin and the front-desk identity. The listener is `collectionGroup(db, "callSessions")` in `admin-app/src/context/AdminContext.tsx:5591` — it is how the desk learns that a guest is ringing.

**Proved against production with real staff ID tokens** (Firestore REST `runQuery`, `allDescendants: true`):

| Query | Admin | Front desk |
|---|---|---|
| `collectionGroup("callSessions")` — the desk's incoming-call listener | **HTTP 403** | **HTTP 403** |
| `collection("callSessions")` — the same collection, top level only | HTTP 200 | HTTP 200 |
| `collectionGroup("messages")` — the desk's inbox thread | HTTP 200 (2 docs) | HTTP 200 (2 docs) |
| `collection("intercoms")` — control | HTTP 200 (8 docs) | HTTP 200 (8 docs) |

So the denial is **specific to the group query**, and it hits both staff roles identically — it is a rules-shape problem, not a role problem.

**Cause.** A Firestore collection-group query must be *provably* safe: the rule set has to guarantee the query can only return documents the caller may read, for **every** path in the group, including paths that do not exist yet. The rules grant the two `callSessions` shapes unconditionally:

```rules
match /callSessions/{sessionToken} {
  allow read, create, update, delete: if true;
  match /iceCandidates/{candidateId} {
    allow read, create, update, delete: if true;
  }
}
```

but the `intercoms/{roomId}` block is **conditional**:

```rules
match /intercoms/{roomId} {
  allow read: if isStaff();      // ← conditional
  allow write: if isStaff();
}
```

**Corrected root cause (2026-10-24).** This section originally blamed the conditional `intercoms` arm for poisoning the group query. That is **wrong**, and the emulator proves it: a Firestore `match /intercoms/{roomId} { … }` block applies to `intercoms/{roomId}` **only** — `match` blocks do **not** cascade into a document's subcollections. So the `intercoms/{roomId}` arm never covered `intercoms/*/callSessions/**` in the first place.

The real cause is the inverse: **no rule covered the nested path at all.** The `match /callSessions/{sessionToken}` block matches a **top-level** `callSessions` collection only; a session stored under a room (`intercoms/{roomId}/callSessions/{token}`) is a different path and matched **no** `allow` rule. A collection-group query over `callSessions` has to be provably safe for **every** path in the group, so one path with no rule denies the whole query — for both staff roles.

**Fix (shipped 2026-10-24)** — give the nested shape its own unconditional-for-staff rule, mirroring the `messages` group:

```rules
match /{path=**}/callSessions/{sessionToken} {
  allow read: if isStaff();
}
```

**Regression test:** `firebase/tests/call-sessions-collection-group-read.emulator.test.ts` now pins the staff group read (both roles), the single-doc read, the token-holder read, and that an anonymous caller is still refused. **It runs** — Temurin 21 was installed and `npm run test:rules` is green on this host: **13 files, 125 tests, 0 failed**.

> The first version of that test was written on 2026-10-23 and had never executed (no JDK). When it finally ran, it **failed** — because it used an identity with no staff `role` claim, so it was asserting a denial that had nothing to do with the defect. It was rewritten against the real role claims before the rule change, so the test now fails for the right reason and passes for the right reason.

**Impact**

- The desk never receives an incoming-call notification — a guest who taps *Call the front desk* in the room intercom gets no ring on the desk's side.
- It also affects any other consumer of the `callSessions` group.
- The `messages` group is unaffected, so **text chat still works** — the desk sees and replies to guest messages. Only the voice-call surface is dead.

### 3.14 — S3 · Removing an other add-on reports a failure for a change that succeeded

**Found by executing the guest-write scenarios (2026-10-25) — scenario AO-08.**

The guest **Manage Other Add-Ons** page assembled its save batch inline and emitted **both** a `change` op with quantity 0 **and** a `remove` op for the same line:

```ts
// guest-app/src/pages/ManageOtherAddOnsPage.tsx — before the fix
} else if (draftEntry.quantity !== origEntry.quantity) {     // quantity 0 → a CHANGE op
  changeOps.push({ selectionKey: key, addOnId, quantity: draftEntry.quantity, … });

…
```

**Reproduced live (2026-10-25):** the guest adds an airport transfer (₱500), saves, sets the quantity back to 0 and saves again:

|---|---|
| The add | ✅ *"Add-ons saved."* · total ₱500 |
| The removal | ❌ *"Nothing to change — add the add-on first."* |
| What the server stored | the line **was** removed (`removedAt` set), the total **was** corrected |

### 3.15 — S1 · A guest booking WITH breakfast cannot be created at all

**Found by executing the guest-write scenarios (2026-10-25) — scenario BF-03. This is the most severe finding in the report: it is a hard outage on a revenue-bearing path.**

The guest picks breakfast on step 2 of the booking flow and confirms. The server answers **HTTP 500**:

```
[MRB-11] revenue allocation invariant violation: roomNet(2400) + breakfastNet(0)
  + addOnNet(0) - deductionNet(0) = 2400, expected totalNet(2600).
  This is a server-side bug — the pricing chain returned an inconsistent allocation.
```

**The root cause.** Per **BR-03 (2026-10-12, decision #232)** the breakfast became a **reservation-level** term — per date × per guest — and the create path's per-STAY `breakfastTotal` is now always `0` (`guest-app/server/handlers/bookings.ts:3200`). But the MRB-11 revenue allocation still read the **per-STAY** field:

```ts
// guest-app/server/handlers/bookings.ts — before the fix
revenueAllocation: assertBookingRevenueAllocationInvariant(
  {
    roomNet: pricingForRoom.roomTotal,
    breakfastNet: pricingForRoom.breakfastTotal,   // ← the per-STAY value: always 0
    …
    totalNet: pricingForRoom.totalPrice             // ← the child's share, WHICH carries the breakfast
  },
  …
)
```

The child's total carries the reservation's breakfast (₱200 for two guests), the breakfast stream says ₱0, and the invariant — which exists precisely to catch a pricing chain that does not add up — **throws**. The guest sees a failed booking and a generic error. Nothing is written; no money moves; the stay is simply lost.

**Why it is arithmetic, not a rounding wobble.** With `w_i` the child's room weight:

```
childTotal  = w_i/Σw · (Σw + breakfast − deductions)
room_i + extraBed_i = w_i
⇒ breakfast_i = w_i/Σw · breakfast
```

so the child's share of the breakfast **must** be allocated with the same weights as the child's total. Reading the per-STAY field instead is off by exactly the breakfast amount — ₱200 here, which is exactly the gap in the error message.

**How long has it been live?** The shape dates from BR-03/BR-08 (2026-10-12/14). It was never visible in the QA pass because **no booking with breakfast could exist** — the QA pass could not create one, so the check had nothing to check. It only became visible once the bot-protection switch re-opened the public write path.

**What production data shows.** The only bookings in production with a live breakfast slot are four **walk-in** records from the hotel's own "Pre-Go Live 2" test run (2026-10-21) — the staff path, which does not go through the public create handler. Two of them (`SI-20261021-00037`, `-00052`) carry a correct allocation; two (`SI-20261021-00056`, `-00057`) carry `breakfastNet: 0` with the breakfast inside `roomNet` — the same class of gap, on the walk-in path, where it does not throw.

**Impact**

- **Every guest who selects breakfast is unable to book.** The hotel's headline add-on — ₱100 a meal, per guest, per night — is unbuyable through the public site.
- The failure is a 500, not a 4xx: the guest cannot tell that the cause was breakfast, and the front desk sees a server error rather than a booking request.
- Nothing is charged and no partial record is left behind — the transaction rolls back — so the blast radius is "lost bookings", not "wrong bills".

**Fix:** the child's share of the reservation's breakfast is allocated with the same weights as the child's total (`allocateRoundedAmount(breakfastTotal, roomStayWeights)`), and the aggregate sums those shares. The per-STAY field is no longer the allocation's source. **Shipped in v2.20.2** — §11.9.

**Regression guard added:** `guest-app/tests/api/br-03-breakfast-allocation.test.ts` (4 runtime assertions on the arithmetic + 4 source tripwires) and `e2e/tests/guest-write.spec.ts` · *BF-03 · the breakfast price follows the guest count* — which books with breakfast through the real UI and asserts the server charges two meals and the allocation balances.

### 3.16 — S3 · A payment-proof rejection can email the guest twice

**Found by the XCC-05 check (2026-10-25) — the provider's send log, not an inbox.**

XCC-05 ("each transactional email arrives exactly once") could not be answered from an inbox, so the evidence became the **provider's own send log** (Resend): what was handed to the provider, once per event. The log is readable without a mailbox, and it is stricter — an inbox shows what arrived, the log shows what was sent.

Scanning it turned up **two "payment proof rejected" emails for `SI-20261021-00046`, 1.25 seconds apart**, for **one** rejection (the booking carries a single `paymentRejectedAt` / `paymentRejectedBy` / `paymentRejectionReason` stamp).

**The root cause is a read-then-write race.** The route decided whether to email the guest from a **pre-read** of the booking's status:

```ts
// guest-app/server/apiRouter.ts — before the fix
const bookingId = String((req.body || {}).bookingId || "").trim();
const snap = await adminDb.collection("bookings").doc(bookingId).get();
const wasEligible = snap.data()?.status === "payment-uploaded";   // ← read BEFORE the write

const result = await handleRejectPayment(req, res);               // ← the transaction flips it to `pending`

if (wasEligible) { await sendBookingTrigger("payment-rejected", …); }
```

The handler's **transaction** is what flips `payment-uploaded` → `pending` (and it refuses a second rejection with *"Only a booking in 'payment-uploaded' status can be rejected"*). But the route's eligibility flag was computed **before** that transaction, so:

- two rejections of the same proof (a double tap, or a retry after a dropped response) both read `payment-uploaded`;
- the second call's transaction is retried by Firestore after the first commits, so the handler **refused** it — and the route emailed the guest anyway.

The loser of the race sent a second email for an event that had already been handled.

**Impact**

- A guest who rejects (and then re-rejects) a payment proof can receive two "action needed: payment proof rejected" emails — each with a "re-upload your proof" call to action, for one rejection.
- The same flag also drove the **staff bell notification**, so the desk could be notified twice too.
- The refund/ledger side was never affected: the handler's transaction is the single writer, and the losing call changed nothing.

**Fix:** the side effects moved **into the handler**, gated on the transition flag the transaction itself computes. The flag is read *inside* the transaction, so it is the committed truth — a racing second call re-reads the document after the first commits, sees `pending`, and neither transitions nor emails.

```ts
// guest-app/server/handlers/bookings.ts — after the fix
transitioned = isTargetInPaymentUploaded;      // read inside the transaction
…
if (transitioned || siblingRejectedCount > 0) {
  await sendBookingTrigger("payment-rejected", { … });
  await writeNotification({ … });
}
```

The route no longer pre-reads anything — it returns the handler's result, and the handler reports `transitioned` in its response so a caller can assert on it.

**Regression guard added:** `guest-app/tests/api/xcc-05-rejection-email-once.test.ts` (5 source tripwires: the route no longer decides from a pre-read, the handler owns the side effects, and they are gated on the transaction's own flag) + `scripts/qa/check-email-once.ts` (the send-log check itself).

### 3.21 — S1 · The email-verification link could never be completed, and the guest was told to check an inbox that never received a mail

**Found by executing RW-01 (2026-10-26).**

This is the finding the whole Spark Rewards onboarding rests on, and it took **two** corrections to get right.

**What the link actually is.** The server generates the verification link with the Admin SDK:

```ts
// guest-app/server/handlers/members.ts
const actionCodeSettings = {
  url: `${getServerBaseUrl()}/account/profile?emailVerified=true`,
  handleCodeInApp: true
};
const verificationLink = await adminAuth.generateEmailVerificationLink(email, actionCodeSettings);
```

The link that reaches the guest is therefore **not** an app-origin link — it is Firebase's **own action handler**:

```
https://spark-inn-prod.firebaseapp.com/__/auth/action?apiKey=…&mode=verifyEmail&oobCode=…&continueUrl=https%3A%2F%2Fwww.sparkinnbohol.com%2Faccount%2Fprofile%3FemailVerified%3Dtrue
```

It renders a two-step confirmation — **"Complete verification"**, then **"Continue"** — and only then does Firebase perform the verification and send the guest to the server's `continueUrl`: `/account/profile?emailVerified=true`.

**Correction 1 — the app never recognised that landing.** The app only looked for an `oobCode` **on its own origin**:

```ts
// before
const oobCode = new URLSearchParams(window.location.search).get("oobCode");
if (!oobCode) return;
```

The production landing carries **no** `oobCode` — Firebase's handler has already consumed it. So the app ignored the landing entirely: the guest clicked the link, the address was verified on Firebase's side, and the app still showed them the **"Verify your email"** banner.

**Correction 2 — and the refresh ran before the session existed.** The first fix (v2.20.9) recognised the `?emailVerified=true` marker but performed the token refresh in the mount effect. **The Firebase SDK restores the session asynchronously** — `auth.currentUser` is still `null` on the first render — so the refresh silently did nothing and the cached id token kept claiming `email_verified: false`. Measured live against v2.20.9:

- the verification itself completed (Firebase confirmed it, and the app consumed the marker);
- the member number survived the verification;
- but `/account/stays` answered **403 EMAIL_NOT_VERIFIED** — *"Please verify your email to see your past stays"* — because the request carried the **stale** token. **My Stays stayed empty.**

**The fix (v2.20.10).** The mount effect now only *recognises* the landing and remembers it; the refresh and the re-registration live in the effect that runs when the session **arrives** (and when an action code has just been applied), and it force-refreshes the token before it decides whether the address is verified. The registration that links the past bookings follows the same path, so it is only ever called with a token the server will accept.

**The cross-device hop — also fixed.** The verification link usually lands in a **different browser** than the one the guest signed up on: the mail is on their phone, the session is on their laptop. That landing has no session at all, so the registration cannot run there — and the guest then signs in later, to a portal that still shows nothing, because nothing ever re-ran `/api/members/register` for an already-enrolled member. A `localStorage` flag now carries the hop: the landing sets it, and the next sign-in with a verified address consumes it.

**Verified in production (v2.20.10)** by executing RW-01 end to end: the signup issues the member number, the emailed link is clicked, the address is verified, the past booking appears under **My Stays**, and the "Join Spark Rewards" prompt is gone. Pinned by **`guest-app/src/__tests__/email-verification-link.test.ts`** (11 tests).

### 3.23 — S2 · The refund the desk records was written without a settled status, so money the hotel had already paid out read back as money it still owed

**Found by the FD-10 scenario's own reconciliation (2026-10-26, against v2.20.10).**

The admin drawer's **"Record Refund"** (CRL-01) records a refund **in one shot** — the staff member has already handed the money back — and it decrements the booking's `paidAmount` as if it had left the till. But the refund record itself was written with **no `status` field at all**.

The read side disagrees. `shared/utils/bookingFolio.ts` → `isUnpaidRefund` classifies a refund by its `status` alone:

```ts
const status = typeof entry.status === "string" ? entry.status.trim().toLowerCase() : "";
return status !== "paid" && status !== "processed";   // ← no status ⇒ PENDING
```

and `sumCollectedPayments` **excludes** a pending refund from `paymentsTotal`. So a refund the desk had already paid out in cash was read back as a **liability the hotel still owed**.

**Measured live** on `SI-20261026-00002` with the app's own shared helper:

| | Before the fix |
|---|---:|
| the ledger | payment **+2600** · the desk's refund **−100** (status **absent** → read as a liability) · the breakfast refund **−100** (`status: "paid"` → settled) |
| the app's folio | `paymentsTotal` **2500** · balance **₱100 DUE** |
| `booking.paidAmount` (the write side, which *had* deducted the money) | **2400** |
| the ledger's settled sum (`sumCollectedPayments`) | **2500** |
| **Δ** | **₱100** — the reconciliation's **I06** FAIL |

Three consequences, in the order the desk meets them:

1. **The guest's outstanding balance was understated by ₱100.** The truth was ₱200 (2600 billed − 2400 net collected); the app said ₱100.
2. **The dashboard's "Refunds due" queue listed a refund that had already been paid in cash.** That is the expensive one: the desk, reading its own queue, pays the guest a **second** time.
3. **`booking.paidAmount` and the settled ledger disagreed by exactly the refund amount** — the two models of the same money, and the reconciliation's I06 check exists precisely to catch that.

**The file header already stated the contract this branch broke.** `guest-app/server/lib/refunds.ts` documents the two entry points it consolidates:

> *CRL-01's cancellation path CREATEd a refund doc directly in the paid state (no pending stage — staff records the refund in one shot through the drawer).*

The `status` is what makes that true on the **read** side, and it was never written. The write side believed it; the read side did not.

### 11.1 §3.4 — the other add-ons now reach the revenue allocation

The earlier diagnosis of this finding was wrong, and the corrected one is what the fix is built on.

**What it is NOT.** It is not a write path that lost the value. `revenueAllocation.addOnNet` is computed from **`extraBedTotal`** — the extra-bed revenue — at every one of the seven write sites, and the MRB-11 allocation schema (`roomNet`, `breakfastNet`, `addOnNet`, `deductionNet`, `totalNet`) has **no stream for the BR-12 other add-ons at all**. `totalNet` equalled `booking.totalPrice`, which per OCT-FOL-01 (decision #298) **excludes** the other add-ons — they sit on top of the room bill for the balance. So the allocation described only part of the bill, and every revenue stream that read it under-reported.

**What it ALSO was.** A write-path gap on top of that: the two add-on write paths — the guest's "Manage Other Add-Ons" page (`guest-app/server/handlers/addons-manage-save.ts`) and the staff add-on update (`addons-staff-update.ts`) — wrote `otherAddOnSelections` / `otherAddOnTotal` onto the booking **but never re-derived `revenueAllocation`**. So even a booking that carried the add-ons from creation kept the create-time snapshot. The 2026-10-22 commit `8c5e9bdd` ("re-derive the total and the allocation after a staff breakfast or add-on update") covers the *breakfast* path and the *discount* paths — the add-on paths were left out.

**The fix (2026-10-25).**

| Where | Change |
|---|---|
| `shared/utils/bookingFolio.ts` | `computeBookingRevenueAllocation` takes `otherAddOnTotal` and folds it into the `addOn` stream; `totalNet` becomes the booking's **whole** bill (`totalPrice + otherAddOnTotal`). `rebuildBookingRevenueAllocation` takes `otherAddOnTotal` + `previousOtherAddOnTotal` so a path that changes the add-ons swaps the old amount out instead of absorbing it into `deductionNet`. `round2` is exported so the server uses the same rounding. |
| `guest-app/server/handlers/bookings.ts` | The create (per-child + aggregate), walk-in (per-line + aggregate) and reschedule write sites carry the other add-ons. The per-child/per-line amount is attributed to the **first** child only — the create path spreads the add-ons onto every child doc, so attributing them to each would multiply them in the reservation aggregate. The add-room aggregate is now the **sum of the children's totals** rather than the header's room-bill `totalPrice`. |
| `guest-app/server/handlers/addons-manage-save.ts`, `addons-staff-update.ts` | Both re-derive the booking's `revenueAllocation` when the add-ons change — **the write-path gap**. |
| `shared/types/index.ts` | The `BookingRevenueAllocation` docs now say the total is the whole bill. |

| `scripts/qa/reconcile-production.ts` | I02 / I03 / I04 compare against the billed total; I04 now checks the add-ons are *inside* the add-on stream (the stream also carries the extra beds). |

### 11.5 §3.6 — the first fix was wrong, and the deployment proved it

This is the one finding where the fix itself had to be corrected, and the record is worth keeping.

**The first fix (v2.19.0) was wrong.** It moved the ledger resolution from the snapshot callback to the commit point, on the theory that the mapper had been committing a stale copy over the rows the re-hydration effect had already repaired. The deploy proved it wrong: the live list still read **69 / 10 / 69** with **0** "Fully paid" pills.

**The actual root cause was the effect's dependency list:**

```js
useEffect(() => {
  setBookings((prev) => {
    if (!prev.length) return prev;      // ← short-circuits on an empty list
    …
  });
}, [paymentIndex, currentUser]);        // ← the ROWS were not a dependency
```

The payments listener and the bookings listener are independent, so this order is possible:

1. the payments listener delivers → the index is built → the effect runs → `prev.length` is 0 → it short-circuits;
2. the bookings listener delivers → the rows are committed **unhydrated**;
3. the index does not change again → **the effect never runs again** → nothing ever re-derives the rows.

Step 3 is the bug: the effect only watched the *index*, so the one moment it could have repaired the rows — after they arrived — was the one moment it could not see them.

**The fix (v2.19.1):** depend on the rows as well — `}, [paymentIndex, currentUser, bookings]);` — so whichever arrives last re-derives them. No render loop: the updater returns `prev` when nothing changed, so React bails out.

**Live proof (v2.19.1, measured):**

| | Before | After | Independent recomputation (I18) |
|---|---:|---:|---:|
| All bookings | 69 | 69 | 69 |
| **Balance due** | **69** | **53** | **53** |
| **Needs attention** | **10** | **5** | **5** |
| "Fully paid" pills (mobile) | **0** | **14** | 16 bookings paid |

### 11.9 The three findings the guest-write scenarios found

The guest-write scenarios could not run until the bot-protection switch opened the public write path. Running them found **three** defects that no other check could reach — each of them on a path that had never been executed end to end.

| Finding | Severity | The symptom in production | The fix |
|---|---|---|---|
| **§3.13** the member rate the guest is charged | S2 | a signed-in member was quoted ₱2,160 and charged ₱2,400 | the booking create carries the member's ID token (both the public and the corporate flow) |

### 11.11 The last two findings, closed (v2.20.12)

Two findings were still open when the Tier-3 pass finished — **§3.7** and **§3.8** — and both are now fixed, deployed and verified live. The project ends with **no open finding**.

**§3.7 — the store order state machine.** The desk's order actions were a **raw client-side Firestore write**, so the state machine existed only as UI *buttons*. The fix moves every staff transition onto the server and adds the **tender guard**: an order whose direct payment has already been collected can no longer be voided, because that is a **refund** (`POST /api/bookings/add-refund`), not a cancellation.

**The guards are behavioural, not source-regexes.** `guest-app/tests/api/store-staff-order-status.test.ts` calls the real handler with a mocked Firestore and asserts on what it writes and what it refuses:

| It proves | Why it matters |
|---|---|
| a tendered order cannot be cancelled — **409**, and **nothing is written** | the defect itself |
| an illegal transition is refused, whatever the status | the state machine is server-side now |
| the stock is given back **exactly once** | no phantom shelf stock |
| a paid GCash order opens a **staff refund review** | the refund has an owner (CRL-04) |
| a COD order does **not** | the money was never collected, so there is nothing to refund |

`admin-app/src/__tests__/store-order-status-server-owned.test.ts` then pins the client boundary: the admin app must not write a store order's status to Firestore at all, must call the three server endpoints, and must surface a refusal as a toast rather than an unhandled rejection.

**One existing guard was updated, and it got stronger.** `batch-15-room-block-store-stock.test.ts` pinned *"the admin app decrements the stock on the placed → confirmed transition"* — a **client-side** copy of the money rule. It now pins the **server's** arithmetic (`handleConfirmStoreOrder`) *and* asserts the client no longer performs it. The behaviour it protected did not change; the owner of the rule did.

**§3.8 — the unknown-endpoint message.** The fallback 404 now echoes the path the caller asked for. The formatting lives in `guest-app/server/lib/apiPath.ts` so it can be tested without booting the router, and a test pins the old interpolation out so it cannot come back.

They are deployed **separately** from the apps (`firebase deploy --only firestore:rules`), so tightening them is its own production step with its own risk, and it is **not** something to slip into a code release. **Recommended as a follow-up ticket:** the `storeOrders` update rule should refuse a client-side change to `status`, the same way `vouchers` and `corporateCodes` were split by operation in P5-F01.
