### Top 5 things to fix first

These five items are the highest-blast-radius, lowest-effort wins. Each is a real bug that will hit production on day one, not a polish concern.

Replace with explicit allowlist from `config.domain` + `config.adminDomain`. (Cross-cutting SEV-1; Email/API SEV-1) **— [x] Fixed in 2423089** (commit `2423089` + merge `e93f04d`; `ALLOWED_ORIGINS` Set + Vary: Origin; 5 regression tests in `cors-allowlist.test.ts`)

Member is overcharged at checkout. The TODO comment acknowledges the gap. (Booking SEV-1; Rewards SEV-1; Email/API SEV-1; Rates SEV-2) **— [x] Fixed in a3b7b56** (commit `a3b7b56` + merge `bf3e699`; server reads `Authorization: Bearer <idToken>`, looks up `members/{uid}`, reads `settings/rewardsConfig`, applies 3rd stacking step; also fixes stacking order per #13b; 8 regression tests in `bookings-member-discount.test.ts`)

(Booking SEV-1; Rewards SEV-1) **— [x] Fixed in 056e7cf** (commit `056e7cf` + merge `592e4d7`; `handleCreateBooking`/`handleCreateWalkin` write lowercase; cancel query lowercased; 5 regression tests in `bookings-email-case.test.ts`)

(Rewards SEV-1; Admin SEV-1; Intercom SEV-2 as collateral) **— [x] Fixed in 5a9ed6a** (commit `5a9ed6a` + merge `1238c2b`; `AdminContext.members` now uses real `onSnapshot(collection(db, 'members'))` with unsubscribe cleanup; 4 regression tests in `admin-members-listener.test.ts`)

## Phase 1 — Per-Feature Findings

### 1.1 Booking Flow (36 findings)

#### SEV-1 (5)

- **S1.1 — Discount stacking math inverted server-side.** `handleCreateBooking` (bookings.ts:201-246) applies voucher discount first then senior/PWD on the remainder; `DECISIONS-FEATURES.md #13b` mandates senior/PWD → voucher → member. Flat-₱ vouchers are mispriced; member discount is never applied at all. **[x] Fixed in a3b7b56** (commit `a3b7b56`; server now computes senior/PWD first, then voucher, then member; 8 regression tests in `bookings-member-discount.test.ts`).
- **S1.2 — Member discount silently dropped server-side.** `handleCreateBooking` reads no member identity; no `memberDiscountPct` is sent. Client shows 10% discount; server charges full price. TODO at `BookingPage.tsx:97` acknowledges this. **[x] Fixed in a3b7b56** (server now reads Authorization Bearer + members/{uid} + rewardsConfig).
- **S1.3 — Email case-mismatch breaks lookup + self-cancel.** `handleCreateBooking` stores `guestEmail: guestDetails.email.trim()` (mixed case), but `handleLookupBooking` queries lowercased. Mixed-case email users cannot retrieve or cancel. **[x] Fixed in 056e7cf** (commit `056e7cf`; `handleCreateBooking`/`handleCreateWalkin` write lowercase; cancel query lowercased; 5 regression tests).
- **S1.4 — Self-cancel allowed after payment confirmed.** `handleCancelBooking:678-680` only blocks `checked-in`/`checked-out`/`cancelled`; `payment-confirmed` and `confirmed` can still be self-cancelled. UI hides the button but server is the source of truth. **[x] Fixed in Phase 11.6 Batch 6** (`guest-app/api/handlers/bookings.ts:742` now rejects self-cancel for any of `checked-in` / `checked-out` / `cancelled` / `confirmed` / `payment-confirmed` — only `pending` and `payment-uploaded` remain self-cancellable. 2 new behavioral tests in `guest-app/api/__tests__/bookings-create.test.ts` cover the 400 response for `confirmed` and `payment-confirmed`. The pre-existing happy-path cancel test was updated to use `status: "pending"`.)
- **S1.5 — `isCorporate` and `companyName` trusted from client.** `bookings.ts:74` reads `isCorporate` straight from the body; an attacker posting `isCorporate: true, corporateCode: "INVALID"` gets the corporate rate anyway.

#### SEV-2 (11)

- Admin guest-ID photo stored as base64 in Firestore doc (size limit risk).
- Step 1 hardcodes `breakfastRatePerPerson = 350` and `breakfastEnabled = true`; ignores `breakfastConfig`.
- `payment-confirmed` status unreachable in current flow (`addOnsitePayment` never sets it).
- Voucher re-validation race silently drops the discount (should return error, not zero-discount).
- `handleCancelBooking` doesn't lowercase email query.
- `BookingConfirmPage` uses static `rooms` array — wrong room name shown.
- `BookingConfirmPage` "Add to Calendar" is a stub `alert()`.
- `BookingConfirmPage` always shows Spark Rewards prompt (members see upsell).
- `BookingConfirmPage` missing "View /my-booking" link.
- Admin booking drawer missing notes field + unaccompanied-minor warning (RA 11862 compliance).
- `addRoomBlock` uses a string `blockReason` for date range — never enforced per-date.

#### SEV-3 (13)

Member discount hardcoded to 10%; admin status filter omits `payment-confirmed`; form validation is hand-rolled not Zod; upload failures use `alert()`; voucher error messages not user-friendly; permissive email regex; PayPal in type but not in UI; "Join Spark Rewards" missing Google Sign-In button on confirm; no "email already linked" check; discount rejection demotes status to `pending`; payment proof image not displayed in admin drawer; timeline copy misleading; `min` for check-out depends on local machine time, not hotel timezone.

#### SEV-4 (7)

`StepIndicator` lacks `aria-current`; `isSubmitting` not reset on success; booking ref fallback string has hardcoded date; `handleAddPayment` doesn't validate `amount > 0`; breakfast rate fallback `250` hardcoded; `nights = Math.max(..., 1)` hides 0-night error; `paypal` / `bank` dead keys in lookup label map.

#### Open questions

1. Email re-use on overlapping bookings — disallowed or allowed?
2. Member discount delivery for anonymous online bookings — ID token vs request body?
3. `payment-confirmed` as a real state — set automatically on full payment, or kept as no-op?
4. Room block date range semantics — structured fields or just string?
5. `isCorporate` server validation contract — what's the canonical source?

#### What's solid

- Availability-locking transaction is correctly implemented (runTransaction with preallocated `bookingId`).
- Voucher re-validation in the same transaction prevents expiry races and double-spend of last redemption.
- Per-staff `handledBy` and audit-friendly `updatedAt` on every status change.
- Admin booking drawer is a thoughtful operational surface (registration + ID + breakfast + discount + payments + folio + actions).
- Booking lookup's security-by-obscurity is right (ref + email required, lowercased, 3/ref/hour rate limit, 60s cooldown).
