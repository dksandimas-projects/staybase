#### MRB-15-09 — Admin reservations listener token refresh (off-roadmap bug fix)

**Shipped** (v0.255.1, `fix/mrb-15-09-admin-reservations-listener-token-refresh`, decision #182). **REAL BUG FIX** (operator-reported staging console error). The MRB-12 `subscribeToReservations` listener in `AdminContext` attached `onSnapshot(collection(db, "reservations"), ...)` after the auth gate at `onAuthStateChanged` validated the `role` claim, but the Firestore SDK uses its own cached ID token for the listener handshake — if the SDK's cache was one refresh behind the React `currentUser` state, the handshake landed with a stale token and the `isStaff()` rule on `/reservations/{id}` (`firebase/firestore.rules:140-141`) replied `Missing or insufficient permissions`. The error surfaced as `Error listening to reservations collection: FirebaseError: Missing or insufficient permissions.` in the staging admin console. The fix awaits `auth.currentUser?.getIdToken(true)` inside the listener `useEffect` BEFORE `onSnapshot` is called, with a `cancelled` flag for the unmount-mid-refresh race + a `.catch` for refresh-token failure. 8 new source-text tests in `admin-app/src/__tests__/mrb-15-09-admin-reservations-token-refresh.test.ts` pin the contract (effect is present; `getIdToken(true)` precedes `onSnapshot`; targets `auth.currentUser`; awaits via `.then`; has the `cancelled` race guard; still returns an unsubscribe; preserves the error-logging contract; logs the refresh failure in `.catch`). Pattern documented in `plan/docs/GOTCHAS.md` as a new "Auth" entry for any future staff-gated listener. Same fix shape applies to the other staff-gated listeners in `AdminContext` (bookings / rooms / roomPrivate / roomBlocks / notifications / members); not widened in this MR — the source-text test pins THIS listener's contract and the GOTCHAS entry guides the next listener.

#### MRB-15-10 — Room types hydration preserves CHD-03 / EXB-01 cap fields (off-roadmap bug fix)

**Shipped** (v0.255.2, `fix/mrb-15-10-room-types-hydration-preserve-cap-fields`, decision #183). **REAL BUG FIX** (operator-reported "it is still not saving the children and max bed updates in the admin settings in the room types"). The pre-MRB-15-10 hydration `useEffect` at `admin-app/src/context/AdminContext.tsx:4815-4834` (the `[hotelConfig.roomTypes]` listener that syncs local state on every snapshot echo) silently DROPPED the three CHD-03 / EXB-01 fields when mapping the snapshot to local state — the mapping preserved 11 fields (`value / label / shortLabel / imageUrls / bedDefinition / description / amenities / maxCapacity / pricePerNight / weekendRate / corporateRate`) but omitted `maxChildren / maxExtraBeds / extraBedRate`. Two visible symptoms: **(1) Display bug** — the Room Types table's `{type.maxChildren ?? 0}` and `{type.maxExtraBeds ?? 0}` columns always rendered `0` for every type, even when Firestore held a non-zero value (the `?? 0` fallback fired on the dropped field). The Edit form's `defaultValue={editType.maxChildren ?? 0}` and `defaultValue={editType.maxExtraBeds ?? 0}` rendered `0` in the input even when the stored value was non-zero. **(2) Save bug** — if the operator opened Edit, saw `0` in the input (the hydration drop), and saved WITHOUT changing the field, the form submitted the displayed `0` and the existing stored value was overwritten with `0`. Operators reasonably read this as "the save isn't working." The save write path itself is correct (the form reads the typed value and `updateRoomType` spreads it through to `saveRoomTypes`), but the round-trip on the next snapshot silently strips the values back out, so the user always sees 0. **Fix** — add the three fields to the mapping with the same normalization the `addRoomType` + `updateRoomType` writers use (`maxChildren: Math.max(0, Math.floor(Number(t.maxChildren) || 0))` for the integer cap; `maxExtraBeds` + `extraBedRate` get the same normalization). #### MRB-15-11 — Room type photo gallery — atomic photo append / remove / reorder (off-roadmap bug fix)

**Shipped** (2026-08-04 on `fix/mrb-15-11-photo-gallery-atomic-mutations`, per decision #188; v0.257.0 → v0.257.1). **REAL BUG FIX** (operator-reported 2026-08-04: "in the admin settings, upload photos for room types, when I select more than 1 image for upload, it only uploads 1 image at a time and replaces the previously uploaded image. Instead of uploading for example 5, I only get the last or the 5th image selected"). The pre-MRB-15-11 photo-gallery functions in `admin-app/src/context/AdminContext.tsx:4978-5034` did a read-modify-write on the in-memory `roomTypes` state — `uploadRoomTypePhoto` read `type.imageUrls` from the React-side cache of the Firestore snapshot, appended the new URL, then called `updateRoomType` → `saveRoomTypes(updated)` → `updateSettings("hotelConfig", { roomTypes: newTypes, ... })` (a full-document write of the entire `roomTypes` array). The SettingsPage handler at `admin-app/src/pages/SettingsPage.tsx:5566-5599` `for`-loops and `await`s each call so the calls are sequential — but the in-memory `roomTypes` is only updated when the Firestore subscription fires locally. Between the N sequential `await uploadRoomTypePhoto` calls, the subscription may not have fired yet, so the (N+1)th call read **stale** in-memory state (still the pre-first-upload value) and overwrote the array with a single-element array `[url(N+1)]`. 5 uploads → 5 overwrites of a single-element array → only the last URL survived. The same race applied to `removeRoomTypePhoto` (a `filter` + write on stale in-memory state) and to a lesser extent to `reorderRoomTypePhotos` (full-array write of the new order; single-user action, lower race surface, but still on stale in-memory state). **Fix** — wrap the read-modify-write in `runTransaction(db, async (tx) => { ... })` for all three functions. The transaction reads `tx.get(hotelConfigRef)` (Firestore, not the in-memory cache), does the `findIndex` + cap check + append / filter / reorder, then `tx.update(hotelConfigRef, { roomTypes: newRoomTypes, updatedAt: serverTimestamp() })`. Firestore's transaction guarantees serialized execution — every transaction sees the latest committed state, so the (N+1)th append sees the (N)th's write. The `MAX_ROOM_TYPE_PHOTOS` cap check goes INSIDE the transaction (atomic with the write — a parallel admin's append can't slip past it). The pattern applies to every read-modify-write against a Firestore document where the read can race with a parallel or sequential write — `removeRoomTypePhoto` + `reorderRoomTypePhotos` got the same treatment in the same fix. 11 source-text tests in `admin-app/src/__tests__/mrb-15-11-photo-gallery-atomic-mutations.test.ts` pin the contract.
