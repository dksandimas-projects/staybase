## CRL-07 — Reservation refund liability + admin workflow

- ✅ **CRL-07 — Reservation refund liability + admin workflow (WITH MRB-04/13)** — shipped 2026-08-03 on `feature/phase-12-crl-07-refund-liability` (decision #173). The destructive cancel (`handleCancelBooking`) now materialises a durable `cancellationLiability` snapshot onto the cancelled entity in the SAME `runTransaction` as the status flip — reservation header (`reservations/{id}.cancellationLiability`) for reservation-scope cancels (MRB-13) + new-path N=1, booking doc (`bookings/{id}.cancellationLiability`) for per-child cancels + legacy null-`reservationId` bookings (pre-MRB-01). The snapshot is `{ policyResult: { refundPct, policyRefund, netCollected, retainedAmount, cutoffHours, source, snapshottedAt }, approvedAmount, exception: { approvedAmount, reason, approvedBy, approvedAt } | null }`. **`policyResult` is immutable** post-cancel — a later settings change never rewrites the snapshot; the server reads `policyResult` for display + Reports, never recomputes. **`approvedAmount` defaults to `policyResult.policyRefund`** and is reduced only via the new admin-only `POST /api/bookings/cancellation-exception` endpoint that requires an admin UID + a non-empty reason (≤500 chars); the endpoint appends an `exception` audit object + updates `approvedAmount` atomically, with idempotency on (amount, reason). The destructive cancel never auto-refunds (CRL-04's invariant), so the admin records processed refunds over time using the existing admin-only `POST /api/bookings/add-refund` (the writer writes to `reservations/{id}/refunds/{refundId}` for new reservations and `bookings/{id}/payments/{refundId}` for legacy — the dual-write path MRB-04 Phase 2.x shipped). A new read-only `POST /api/bookings/cancellation-liability` projection endpoint reads the stored liability + the current `processedAmount` (sum of the refunds subcollection) and returns one of five states (`not-required` / `retained` / `pending-processing` / `partially-processed` / `processed`) via the pure `computeCancellationLiabilityState` helper in `shared/utils/cancellation.ts`; `state` + `outstandingAmount` + `retentionAmount` are derived (NEVER stored). The admin BookingsPage gains a `CancellationLiabilityPanel` (mounted in the cancelled-booking drawer's Folio section when `status === "cancelled"` and a snapshot exists — shows the policy row [immutable] + approved row [admin-controlled] + processed row [live from the refunds subcollection] + outstanding row [derived] + state badge + two action buttons gated on `currentUser?.role === "admin"`) + a `CancellationExceptionModal` (admin-only, required reason ≤500 chars, amount bounded by `policyRefund`). **Front desk can cancel; only Admin can record a processed refund or apply an exception** — the spec body's authorization rule. Reservation-scope cancel writes ONE liability snapshot to the reservation header (the aggregate, derived from the reservation-scope preview); per-child cancel writes ONE snapshot to the cancelled booking doc; legacy null-`reservationId` cancel writes the snapshot to the booking doc (byte-equivalent to per-child, the booking is its own reservation). Surviving rooms in a partial reservation-scope cancel do NOT carry a liability field (their status is unchanged); the reservation header is the source of truth for the aggregate. N=1 byte-equivalent: a cancel whose snapshot is `policyRefund === 0` (e.g. past the cutoff + no payment) skips the snapshot field entirely (the absence means "no liability work to do") so the legacy booking list + Reports continue to read from the booking doc without knowing CRL-07 exists. **Source-text guard:** `guest-app/tests/api/crl-07-refund-liability.test.ts` (24 tests) + **state-helper behavioural tests:** `shared/__tests__/crl-07-liability-state.test.ts` (23 tests). The two new helpers live in `shared/utils/cancellation.ts` next to CRL-05/CRL-06's `evaluateCancellation` / `evaluateCancelPreview`; the projection endpoint defers the import to avoid a circular dependency at module load time. The admin `Booking` type hydrates `cancellationLiability` from the Firestore snapshot in `AdminContext.tsx` so the drawer's selected booking carries the field. The `CancellationLiabilityPanel` re-projects on every render via a `refreshKey` prop the parent bumps after a successful refund or exception (so the panel re-fetches the live `processedAmount` without waiting for the Firestore onSnapshot to land). **Rejected:** a top-level `cancellationLiabilities/` subcollection (denormalized writes + the docs would need their own `bookingId`/`reservationId` linkage — adding a field to the cancelled entity is simpler); storing `processedAmount` as a denormalized field (the spec says "derived from immutable ledger entries" — Reports must read the ledger, not a possibly-stale counter); a separate `exceptionHistory[]` array (the `exception` field is a single object overwritten on each new exception, the audit trail lives in the admin notifications collection CRL-08 adds); auto-recording a partial refund at cancel time (CRL-04's "never auto-refund" rule); staff roles other than admin recording a processed refund (the spec explicitly gates that on admin — a front-desk operator who collects the GCash refund still needs an admin to "Record processed refund"); rewriting the policy result on a settings change (the snapshot is the contract — `policyResult` is read-only post-cancel). **Gates:** CRL-06 (the preview's `staffProcessingRequired` flag drives the new panel's render gate), CRL-08 (the refund-state email + Reports liability queue consume the new state), CRL-09 (the behavioural tests + staging rehearsal — partial coverage shipped here, full CRL-09 cycle closes the loop).
