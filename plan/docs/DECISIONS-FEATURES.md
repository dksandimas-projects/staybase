| 112 | **Google Sign-In is authentication only;** Spark Rewards enrollment requires explicit consent via Privacy Policy / Terms checkbox. |

| 123 | **Multi-booking picker for `/my-booking`:** when email-alone search matches >1 booking, returns a privacy-preserving list of 10 most recent stays. |

| 166 | **MRB-13 Cancellation Scope Model (proposed 2026-08-02):** `POST /api/bookings/cancel` gains an optional `scope: "room" \| "reservation"` (default `"room"` for byte-compatible single-child behavior). When `scope === "reservation"` and the booking has a `reservationId`, one transaction cancels every cancellable child, decrements voucher/corporate code `usageCount` exactly once per shared code (not per child), runs the MRB-05 loyalty clawback per-child, and updates the reservation header (`cancelledRoomCount` + `activeRoomCount` + `paymentStatus: "cancelled"` when the resulting `activeRoomCount === 0`). The first-created child has no special financial consequence because no child owns the reservation folio (`reservations/{id}/payments` and `refunds/` are the source of truth). Admin BookingsPage cancel modal shows a `This room` / `All N rooms` scope selector when `reservationRoomCount > 1`; guest `/my-booking` cancel modal always cancels the whole reservation and the copy states the room count. One reservation-scope `booking-cancelled` email lists every cancelled room + aggregate state (MRB-09 expands the template inventory). Auth is unchanged: the existing `ref + (email \| token)` guest credential is sufficient because the server resolves `reservationId` from the child doc. Gates: CRL-06 (guest policy preview), CRL-07 (refund liability + admin workflow), MRB-09 (full reservation-scope email template inventory), MRB-10 (guest lookup by reservation). Rejected: a new `/api/reservations/cancel` sibling (duplicates the auth + audit path); reservation-owned cancel that bypasses per-child CRL-02 audit metadata (silently drops Reports rows). |
| 167 | **Corporate multi-room negotiated rate + N-room usage cap (MRB-08, proposed 2026-08-02):** `/api/bookings/create` resolves the negotiated rate **per stay type** from `corporateCodes/{code}.ratePerRoomType` (then falls back to the room type's flat `corporateRate`, then the standard `pricePerNight`) instead of once for the primary type. The "Continue without code" flat-rate path applies the same per-stay fallback chain. The corporate code's `usageCount` increments by `assignedRooms.length` (N rooms = N uses), and the cap check inside the create transaction rejects when `usageCount + N > usageCap`. On `handleCancelBooking`'s full-reservation path, the same `usageCount` is decremented by the cancelled room count (the MRB-13 scope selector controls the count: `scope === "room"` decrements 1, `scope === "reservation"` decrements `activeRoomCount`). Rejected: keeping the single-rate model (silently overcharges/undercharges a mixed-type corporate block); `usageCount += 1` regardless of room count (turns a capped code into effectively unlimited at N>1); introducing a per-room `corporateUsageCount` (the cap is contract-level, not per-physical-room). The `/corporate/book` page mirrors `BookingPage`'s room cart from MRB-06: per-stay type + own adults/children/extra beds, claimed rooms filtered out, and submission blocked until every stay is creatable. Negotiated pricing + LOU wording, the "no public promo voucher" rule (decision #100), and the "Continue without code" intent flag (BI-04) all carry over unchanged. Gates: MRB-09 (one email per reservation), MRB-10 (guest lookup nests children), MRB-11 (Reports use reservation owners). |
| 168 | **Reservation-scope email fan-out (MRB-09, proposed 2026-08-02):** every guest-facing booking email (`booking-submitted`, `payment-confirmed`, `booking-confirmed`, `checkin-reminder`, `booking-confirmed-with-balance`, `booking-rescheduled`, plus the receipt PDF) renders a single "block" view that lists every room in the reservation, not just the first child's data + a flat rate breakdown line. The view is built by `buildReservationEmailView(reservation, children)` (exported from `guest-app/server/handlers/email.ts`) which synthesises a synthetic `rooms[]` array of per-stay projections (position + ref + type + occupancy + breakfast + per-stay total) and an aggregate total. The `bookingRows` helper + receipt PDF + subject lines detect the `rooms[]` array and switch into the multi-room shape; N=1 falls through to the legacy single-room render (byte-equivalent to pre-MRB-09). The new `booking-cancelled-reservation` action + template fires from MRB-13's reservation-scope cancel path; the per-child `booking-cancelled` action stays for the per-child path. The checkin reminder cron groups confirmed bookings by `reservationId` and sends one email per reservation (N duplicate reminders for an N-room reservation were the worst pre-MRB-09 artifact). A new `loadReservationEmailView(bookingId)` helper reads a booking + its reservation + siblings from Firestore so the confirm / cancel / reschedule handlers can hand a multi-room view to the templates without rewriting their own data plumbing. Rejected: per-child emails (creates N duplicate reminders for an N-room block); a per-room "view" object (would require every template to understand the array shape separately); rewriting the `sendBookingTrigger` signature to accept reservation data (the legacy `(action, booking)` shape stays — the `rooms[]` array is a property of `booking`, not a separate parameter). Gates: CRL-06..09 (refund lifecycle), MRB-10 (guest lookup nests children), MRB-11 (Reports use reservation owners). |
| 169 | **Guest lookup resolves a reservation with nested rooms (MRB-10, proposed 2026-08-02):** `/api/bookings/cancel` + the public `/my-booking` page both honour reservation-scope lookups. The handler accepts an optional `reservationRef` (regex `R-YYYYMMDD-NNNNN`) alongside the existing `bookingRef` / `guestEmail` / `token`; the credential is required (a bare `reservationRef` is not enough — `R-…` is enumerable at ~1k per day). When a looked-up booking has a `reservationId` AND the reservation has N>1 children, the response carries `kind: "reservation"` with a `rooms[]` array of per-stay projections (position + ref + type + occupancy + per-stay total + status + masked email) and the reservation header fields. The page renders one card with the reservation header + a per-room list. N=1 falls through to the legacy `kind: "single"` shape (byte-equivalent to the per-child view for N=1). Legacy pre-MRB-01 bookings (no `reservationId`) also stay `kind: "single"`. The privacy posture is unchanged from decisions #126/#128/#131: no `guestName` reflected, `maskedEmail` instead of `guestEmail`, "Booking not found." for every zero-match case. Cancel routes through `scope: "reservation"` (per MRB-13 decision #166) so the server cancels every child in one transaction; the modal copy states the room count + a per-room list so the guest can verify. Resend fires the primary child's email — the per-child template now renders the full reservation view (per MRB-09), so the guest gets the same block layout on resend. A future "resend reservation email" endpoint (MRB-15) can fire the `booking-cancelled-reservation` action's cousin for the active-state email. Rejected: a per-room "view" object (would require the page to understand the array shape separately); a per-room lookup endpoint (the credential gates the reservation, not the unit of action); rewriting the `enrichAndRespond` signature (the legacy `(res, bookingData)` shape stays — the new branch is a single conditional inside the existing function); rewriting the lookup schema to require `reservationRef` (backward compat — existing per-booking lookups still work). Gates: CRL-06..09 (refund lifecycle), MRB-11 (Reports use reservation owners), MRB-13 (cancel scope wires the new shape). |
