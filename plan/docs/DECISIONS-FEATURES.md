173 | **CRL-07 Reservation Refund Liability + Admin Workflow (proposed 2026-08-03):** the destructive cancel (`handleCancelBooking`) now **materializes** the policy result onto the cancelled entity in the same transaction as the status flip, so the financial snapshot is durable and re-derivable. The new field `cancellationLiability` lives on the reservation header (`reservations/{id}.cancellationLiability`) for reservation-scope cancels and new-path N=1 cancels, and on the booking doc (`bookings/{id}.cancellationLiability`) for legacy null-`reservationId` bookings and per-child cancels inside a multi-room reservation. The shape is `{ policyResult: { refundPct, policyRefund, netCollected, retainedAmount, cutoffHours, source, snapshottedAt }, approvedAmount, exception: { approvedAmount, reason, approvedBy, approvedAt } \| null }`. **`policyResult` is immutable** — a later settings change never rewrites a cancelled booking's snapshot; the server reads `policyResult` for display, never recomputes. **`approvedAmount` defaults to `policyResult.policyRefund`** and is reduced only via a new admin-only `POST /api/bookings/cancellation-exception` endpoint that requires an admin UID and a non-empty reason (capped at 500 chars); the endpoint appends an `exception` audit object and updates `approvedAmount` atomically. The destructive cancel itself never auto-refunds (CRL-04), so the admin records processed refunds over time using the existing admin-only `POST /api/bookings/add-refund` (the writer writes to `reservations/{id}/refunds/{refundId}` for new reservations and `bookings/{id}/payments/{refundId}` for legacy — the dual-write path MRB-04 Phase 2.x shipped). A pure `computeCancellationLiabilityState` helper in `shared/utils/cancellation.ts` takes the stored liability + the current cumulative `processedAmount` (derived from the refunds subcollection) and returns one of five states: `not-required` (`policyRefund === 0` — nothing to refund), `retained` (`approvedAmount < policyRefund` — admin applied an exception; the retention amount `policyRefund - approvedAmount` is the "extra we kept"), `pending-processing` (`approvedAmount === policyRefund` AND `processedAmount === 0`), `partially-processed` (`0 < processedAmount < approvedAmount`), `processed` (`processedAmount >= approvedAmount`). Derived fields (state + outstanding = approved − processed) are NEVER stored — the UI + Reports derive them from the ledger. Front desk (any staff role) can cancel; **only admins** can record a processed refund or apply an exception (mirrors the existing `handleAddRefund` admin-only gate, no new authorization surface). Reservation-scope cancel writes ONE liability snapshot to the reservation header (the aggregate, derived from the reservation-scope preview); per-child cancel writes ONE snapshot to the booking doc; legacy null-`reservationId` cancel writes the snapshot to the booking doc (byte-equivalent to per-child, the booking is its own reservation). The admin BookingsPage gains a `CancellationLiabilityPanel` rendered inside the cancelled-booking drawer's Folio section when `cancellationLiability` is present: it shows the policy row (immutable), the approved row (admin-controlled), the processed row (live from the refunds subcollection), the outstanding row (derived), the state badge, and two action buttons gated on `currentUser?.role === "admin"`. The "Record processed refund" button opens the existing refund modal pre-filled with the outstanding amount (the staff can still override) and reuses the idempotency contract from CRL-01. The "Apply exception" button opens a small modal with an amount input (must be `0 ≤ amount ≤ policyRefund`) and a reason input (required, ≤500 chars); on submit the page calls the new endpoint and the panel re-renders. Surviving rooms in a partial reservation-scope cancel do NOT carry a liability field (their status is unchanged); the reservation header is the source of truth for the aggregate. `processedAmount` is recomputed on every render by reading `reservations/{id}/refunds/` (or `bookings/{id}/payments/` for legacy) — Reports (CRL-08 follow-up) will use the same projection.
