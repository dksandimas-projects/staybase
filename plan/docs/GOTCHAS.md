> Requires: CLAUDE.md

Things agents must never do. Check this file before implementing any feature.

## Firebase

- **Always unsubscribe `onSnapshot` listeners** — return the unsubscribe function from `useEffect` cleanup. Failing to do so causes memory leaks and duplicate updates.
- **Never read-then-write for booking creation** — always use a Firestore transaction. The client's prior system had real overbooking incidents. See `plan/features/AVAILABILITY-LOCKING.md`.
- **Never re-initialize Firebase** — call `initializeApp` once in `firebase/config.ts`. Use `getFirestore()`, `getAuth()`, `getStorage()` everywhere else.
- **Never expose Firebase Admin SDK credentials client-side** — Admin SDK lives in `api/` only.
- **Always configure `cors.json` for Firebase Storage** before any file upload feature goes live — uploads will silently fail otherwise.
- **Firestore security rules block unexpected reads** — test rules in the Firebase emulator before deploying. A rule that looks correct in isolation may block legitimate reads.
- **Never deploy `firebase/firestore.rules` or `firebase/storage.rules` to a live project ahead of the app build that depends on them** — rules and client ship together, or rules ship second. Tightened rules against an older deployed client silently break guest flows with permission-denied errors (INC-01, 2026-07-17: staff-only Storage reads broke the old app's post-upload `getDownloadURL`, blocking online-payment bookings, and staff-only message creates killed guest intercom). Before any rules deploy, confirm the live app build already contains the matching client changes.
- **Never fan out per-item writes to a single Firestore array field** — always compute the next array and write it once. `setDoc(..., { merge: true })` on an array field replaces the field wholesale, so N concurrent writes that each compute "the original array with one item changed" from the same snapshot produce a race where only the last write survives and every other item's edit is silently dropped. Symptom: the success toast fires, the values snap back on the next snapshot echo, and no test fails. The original rates matrix save shipped this shape (RTS-01, 2026-07-31). Fix: a single batched `saveRoomTypes(next)` call (or any `save<EntityName>` bulk primitive) consumed by every write site, not N parallel single-item writers. Applies equally to `paymentMethods[]` (Settings → Payment Methods), `bookingSources[]` (per NBS-04), and `seasonalRateOverrides[]` — any future list-shaped editable content must use the same bulk-write primitive. The `AdminContext` `updateEntity` → `saveEntity` pairing is the right shape; the `updateEntity`-only path is the wrong shape.
- **For sequential per-item writes inside a `for...of await` loop, use `runTransaction` — never read from the in-memory React cache and write the full document** (MRB-15-11, 2026-08-04). The previous entry covers the *concurrent* fan-out case (N writers at the same time). MRB-15-11 hits the *sequential* version of the same root cause: the Settings → Room Types editor's photo upload handler at `admin-app/src/pages/SettingsPage.tsx:5566-5599` `for`-loops over the user-selected files and `await`s each `uploadRoomTypePhoto` call. Each call reads `type.imageUrls` from the React-side `roomTypes` cache, appends the new URL, then writes the full array via `saveRoomTypes`. The calls are sequential, so there's no concurrent-writer race — but the in-memory `roomTypes` is only updated when the Firestore subscription fires locally. Between the N sequential `await uploadRoomTypePhoto` calls, the subscription may not have fired yet, so the (N+1)th call reads **stale** in-memory state (still the pre-first-upload value) and overwrites the array with a single-element array `[url(N+1)]`. 5 uploads → 5 overwrites of a single-element array → only the last URL survives. The fix is `runTransaction` around the read-modify-write: read `tx.get(hotelConfigRef)` from Firestore (not the in-memory cache), do the `findIndex` + cap check + append / filter / reorder, then `tx.update(hotelConfigRef, { roomTypes: newRoomTypes, updatedAt: serverTimestamp() })`. Firestore's transaction guarantees serialized execution — every transaction sees the latest committed state, so the (N+1)th append sees the (N)th's write. The `MAX_ROOM_TYPE_PHOTOS` cap check goes INSIDE the transaction (atomic with the write — a parallel admin's append can't slip past it). The pattern applies to every read-modify-write against a Firestore document where the read can race with a parallel or sequential write — `removeRoomTypePhoto` + `reorderRoomTypePhotos` got the same treatment in the same fix. If a future feature needs to batch a user-driven N-item write (N photos, N notes, N tags), wrap the loop in a `runTransaction` that does the entire `find → cap-check → append-N-times → write` cycle in one transaction. The Storage upload stays OUTSIDE the transaction (Storage ops can't be in a Firestore transaction); the Storage cleanup on cap-reject is best-effort (`.catch(() => undefined)`).

## Auth & Security

- **Never trust `isCorporate`, `corporateCode`, or role claims from the client** — always verify server-side via API route with Firebase Admin SDK.
- **Never validate voucher or corporate access codes client-side only** — always call the validation API route. Client-side validation is for UX feedback only; server-side is authoritative.
- **Never allow public registration for admin/front-desk accounts** — admin creates all staff accounts manually.
- **Always force-refresh the ID token before attaching a staff-gated `onSnapshot` listener** (MRB-15-09, 2026-08-03) — the auth-state callback at `admin-app/src/context/AdminContext.tsx:809-822` calls `getIdTokenResult(firebaseUser, true)` to validate the `role` claim, but the Firestore SDK uses its OWN cached ID token for the listener handshake. If the SDK's cache is one refresh behind the React `currentUser` state (e.g. the staff claim was minted server-side moments ago, the user's session was idle long enough for the cached token to lose the claim, or the operator just signed in for the first time in a new tab), the listener attaches with a stale token and the staff-gated `isStaff()` rule (e.g. `/reservations/{id}`, `/bookings`, `/rooms`, `/members`, `/notifications`, `/storeOrders`) replies `Missing or insufficient permissions`. The current user's role is correct (the auth gate already passed), but the SDK hasn't re-fetched the token yet. The symptom is a `console.error("Error listening to <collection> collection: FirebaseError: Missing or insufficient permissions.")` in the admin console on first sign-in after claim mint, after a long idle, or on a new tab. The fix is to `await auth.currentUser?.getIdToken(true)` inside the listener `useEffect` BEFORE calling `onSnapshot`, with a `cancelled` flag for the unmount-mid-refresh race and a `.catch` for refresh-token failure. The same pattern applies to every staff-gated listener in `AdminContext` (bookings / rooms / roomPrivate / roomBlocks / notifications / members / reservations — MRB-15-09 ships the reservations fix; future listeners must follow the pattern from day one, not retrofitted after the operator hits it).
- **A Firestore snapshot hydration for any list-shaped collection must preserve EVERY field the contract guarantees** (MRB-15-10, 2026-08-03) — the `useEffect([hotelConfig.roomTypes])` hydration in `AdminContext` (and every sibling hydration in every React context) is a place where a missing field on the mapping silently resets that field to the type's default for every subsequent read AND silently overwrites the stored value with the default on the next no-op save. The pre-MRB-15-10 mapping preserved 11 fields but dropped 3 (`maxChildren / maxExtraBeds / extraBedRate` from CHD-03 / EXB-01), which manifested as "the Room Types table always shows 0 children and 0 max extra beds, even when I set them" + "the Edit form input shows 0 even when the stored value is 1" + "saving without changing the field overwrites the stored value with 0." The fix is to enumerate every field the `RoomTypeEntry` contract guarantees in the mapping body with the same normalization the writer uses (so the round-trip is byte-equivalent). The pattern applies to every list-shaped state in the codebase (room types, booking sources, payment methods — payment methods + booking sources already use a `normalize*` helper which encodes the contract in one place; room types should follow the same shape if the field count keeps growing). The MRB-15-10 test pins the contract at the source level — a future refactor that drops a field from the mapping breaks the test instead of silently regressing.
- **Never read "is this thing done" from a transient lifecycle state — use the durable signal** (FOL-01, 2026-08-06) — `bookings/{id}.status` is a transient state that the lifecycle moves past. A booking's payment can be verified (server stamps `paymentConfirmedAt: Date`) and then the booking can move on to `confirmed` → `checked-in` → `checked-out`; the `status === "payment-confirmed"` check returns `false` for all of those lifecycle moves, even though the payment was verified at the `payment-confirmed` moment minutes/hours/days earlier. The pre-FOL-01 admin booking drawer's Folio + Overview "Pending" / "Verified" payment badges both read `status === "payment-confirmed"` directly — a transient-state read — which manifested as "I confirmed the payment and confirmed the booking but the payment shows as not confirmed in the folio." The data was consistent (the booking's `paymentConfirmedAt` was set, the `onsitePayments[]` ledger had the verified entry, the `reservations/{id}.paymentStatus` mirror was set); only the UI's read was lossy. The fix is to introduce a single source of truth (a shared `isPaymentVerified()` helper that ORs the transient `status === "payment-confirmed"` axis with the durable `paymentConfirmedAt` timestamp) and route every per-render read through the helper. The pattern applies to any "is this event done?" check that has both a transient (status) and a durable (timestamp) signal in the data model: **(1) the helper is the only authoritative read** — never inline `status === "X"` in a render site, always go through the helper; **(2) the durable signal must be hydrated by the snapshot mapper** — if the field is dropped on read (the same shape of bug as MRB-15-10), the helper returns the wrong answer; **(3) the helper is strict on the legacy shortcut path** — a `confirmed` booking that was confirmed via a legacy `status` shortcut with no `paymentConfirmedAt` correctly reads as not-verified, so the verify CTA stays open and the staff can still verify the proof. FOL-01's unit tests + the admin source-text test pin the contract at both layers.
- **A Firestore snapshot hydration `useEffect` that maps to an extension of a shared type MUST preserve every field the contract guarantees** (FOL-02, 2026-08-07) — the admin `bookings` mapper at `AdminContext.tsx:1335-1448` is the same shape of pattern as MRB-15-10 (the room-types hydration) and FOL-01 (the `paymentConfirmedAt` hydration): the admin `Booking` extension declares more fields than the mapper actually reads from the snapshot, and the dropped fields silently break every read site that depends on them. FOL-02 found 8 dropped fields: `reservationId` / `reservationRef` / `reservationPosition` / `reservationRoomCount` (the MRB-01 reservation cluster — broke the booking drawer's payments listener which gates on `selectedBooking.reservationId` to choose between the canonical and legacy subcollection paths, so verified payments written to `reservations/{id}/payments/` were invisible to the Folio's "Payment history" + the "Collect <balance>" CTA stayed on screen); `onsitePayments` (the denormalized payment ledger array — broke the header's "Reference" line + the Folio's proof card + the Bookings table's "PAID" pill + the advanced filter's "Reference" search); `paymentRejectionReason` / `paymentRejectedAt` / `paymentRejectedBy` (the rejection audit cluster — broke the dashboard's reject-payment card). The fix is to enumerate every field the `Booking` contract guarantees in the mapping body with the same normalization the writers use (so the round-trip is byte-equivalent). The pattern applies to every list-shaped state in the codebase (room types, booking sources, payment methods, **bookings** — the bookings mapper is the new entry on the list). The FOL-02 test pins the 8 newly-hydrated fields + the FOL-01 field at the source level — a future refactor that drops any of the 9 fields breaks the test instead of silently regressing. **If a future feature needs to add a new field to the admin `Booking` extension, the per-field test pattern is the contract enforcement** — add the field to the type, add the hydration line to the mapper, add a per-field test that pins the exact normalization shape.
- **In a Firestore `runTransaction`, ALL reads (`await transaction.get(...)`) MUST complete BEFORE any write (`transaction.update(...)` / `transaction.set(...)`)** (FOL-03, 2026-08-07) — Firestore's `runTransaction` API enforces a structural rule that the SDK cannot bypass: a transaction body that mixes reads and writes, with any read landing AFTER any write, throws the canonical error `Firestore transactions require all reads to be executed before all writes` and aborts the entire transaction (no partial commit, no retries, no error-suppression). The pre-FOL-03 `handleCheckinBooking` and `handleCheckoutBooking` in `guest-app/server/handlers/bookings.ts` (lines 8203+ and 8433+) tripped this rule because the read needed to compute the post-update mirror (`childrenForCount` for the `checkedInRoomCount` + `paymentStatus` aggregate) was placed AFTER the writes that mutate the child statuses — the very thing the mirror needs to count. The visible symptom was a 500 on `POST /api/bookings/checkin` for a confirmed + payment-confirmed booking. **The rule applies to every `runTransaction` body, not just the booking handlers** — any future transactional write that needs to read a derived value (a count, a sum, a max) AFTER a write to one of the source documents is structurally invalid; the read has to happen before the writes, and the derived value has to be computed from the pre-read. The post-update state of any document the transaction mutates cannot be observed via a real read inside the same transaction (we'd be back to reads-after-writes); it has to be constructed in JavaScript from the pre-read + a per-doc ternary that replaces the target document's value with its post-update value. **The pattern is "pre-read + post-update construct"** — (1) every `await transaction.get(...)` completes first (including the read for the derived value); (2) the derived value is computed from the pre-read's results with a per-document ternary that injects the post-update state for documents the transaction mutates; (3) every `transaction.update(...)` / `transaction.set(...)` runs in a single contiguous block AFTER the reads. The variable naming should make this explicit: `preReadSnapshot` (or `childrenForCount` for the per-reservation case) for the raw read, `postUpdateStatuses` (or `postUpdateChildStatuses`) for the constructed array. **The fix is structural, not a workaround** — the SDK requirement is enforced at runtime, not a warning; a `try { transaction.get(...) } catch { /* swallow */ }` around the read-after-write would not silence the error (the SDK rejects the call before the body executes). The pre-FOL-03 mirror read was impossible to satisfy because the read's source-of-truth state CHANGED with the writes; the only correct shape is to read the pre-update state, then compute the post-update state in JavaScript. **Batched writes don't help** — `writeBatch` doesn't support reads at all (the `runTransaction` read API is the only one that can read inside an atomic block); a separate query for the mirror read would lose atomicity (a parallel writer could mutate the children between the batch and the query, leaving the mirror stale). **Splitting into two transactions doesn't help** — the whole point of `runTransaction` is atomicity across the writes; a crash between the two transactions leaves the booking `checked-in` with a stale `checkedInRoomCount` on the reservation header. **Reordering the writes to do the header first is wrong** — the count derives from the booking status flip, not the other way around; the order is booking → room → header mirror. The FOL-03 test pins the new ordering at the source level — the new pre-read appears before the first write, the `postUpdateChildStatuses` ternary is intact, the mirror write reads from `postUpdateChildStatuses`, and the pre-FOL-03 read-after-write pattern is gone from both handlers. The pattern applies to every future `runTransaction` body in the codebase (any handler that mutates a parent aggregate from a child collection change, any handler that needs to recompute a counter inside a transaction, any handler that needs to read-then-write to a derived view). If a future feature needs to add a new transaction that reads after a write, the AST-level lint rule is the right enforcement surface (catch at the AST, not at runtime); the FOL-03 source-text pin is the per-handler guard for the current state.
  - **FOL-03 audit follow-up (2026-08-10, per `fix/fol-03-reschedule-transaction-read-order`):** the same FOL-03 antipattern shipped in `handleRescheduleBooking` (lines 9948+ in `guest-app/server/handlers/bookings.ts`). The MRB-14 work (2026-08-03, per decision #180) added the `actualDateRange` recompute inside the same transaction as the booking + room updates but placed the children `get()` AFTER the writes — the comment explicitly noted "the just-rescheduled child is now `updatedBooking.checkIn`" (i.e. the read was supposed to observe the post-update state). The visible symptom was a 400 from `POST /api/bookings/reschedule` for any booking with a `reservationId` (the N>1 multi-room case), surfaced in production on 2026-08-10 as "Failed to move booking — Firestore transactions require all reads to be executed before all writes". The fix pre-reads the children at the TOP of the transaction (right after the reservation header read at line ~10058), and substitutes the just-rescheduled child's NEW dates (`checkInDate` / `checkOutDate` from the in-memory function scope) in the pre-read's `.map()` via `if (docSnap.id === String(bookingId))` — the post-update state is constructed in JavaScript, not observed via a re-read. The late `actualDateRange` block is now pure compute (uses the pre-built `rescheduleChildrenDates` array) + writes (no reads). The `fol-03-reschedule-transaction-read-order.test.ts` suite (5 source-text tests) pins the contract: the children read appears BEFORE the booking `transaction.update()`, the `.map()` substitutes the NEW dates for the just-rescheduled child, the late `actualDateRange` block contains NO `transaction.get(...)` calls, and the children read appears exactly once (not duplicated in both the early + late positions). The MRB-14 test (`mrb-14-reschedule-preserves-header.test.ts`) was updated to reflect the new pattern (the regex now matches `rescheduleChildrenDates || []` instead of the literal `rescheduleChildrenDates` because the new code falls through to an empty array for the legacy null-`reservationId` path). **The audit reinforces the FOL-03 rule for future writers** — the same shape of bug (read-after-write in a `runTransaction`) is structurally hard to spot in code review because the bad pattern looks correct (a re-read after a write is the natural way to observe post-update state). The "pre-read + post-update construct" pattern is the only correct shape; the `runTransaction` SDK enforces it at runtime, but a future "I'll just add this read after the writes" refactor on a different handler will re-introduce the same class of bug. AST-level lint is the right enforcement surface (the SDK only catches it when the handler runs in production); the per-handler source-text pin is the per-handler guard for the current state.
- **Every guest-facing page that displays a payment-method label MUST source it from `settings/hotelConfig.paymentMethods[].label`, not from a hardcoded map** (FOL-04, 2026-08-07) — decision #108 / SETTINGS.md §Payment Methods established `paymentMethods[]` as the canonical source for the booking flow's payment list. The `/book` page (`BookingPage.tsx`) honoured the contract from the start (it reads `pm.label` from the array dynamically), but the `/book/confirm` page (`BookingConfirmPage.tsx`) and the public `/my-booking` page (`BookingLookupPage.tsx`) carried their own independent hardcoded `paymentLabels` / `legacy` object literals. The visible symptoms: (1) **drift after admin rename** — when the admin renamed `gcash` → "GCash Only" in Settings, the booking page picked up the new label immediately but the my-booking + confirmation pages kept the legacy "Digital Wallet (GCash/Maya)" — guests saw two different labels for the same booking across the two surfaces; (2) **ugly raw keys for custom methods** — when the admin added a custom method (`pesonet` / `credit-card` / `crypto`), the my-booking + reservation cards fell through to the raw method key because the hardcoded map had no entry, so the guest saw "pesonet" / "credit-card" as the label. The pre-FOL-04 reservation-scope card was the worst offender — it dumped the raw `paymentMethod` key directly into the JSX, so every guest with an N-room reservation saw "gcash" / "pesonet" / etc. regardless of the admin's label. **The fix is a shared helper** — `resolvePaymentMethodLabel(methodKey, paymentMethods)` in `shared/utils/paymentMethodLabel.ts` is the single source of truth. Resolution order: (a) match by `method` in the admin-supplied `paymentMethods[]` → return that entry's `label`; (b) fall through to the `LEGACY_PAYMENT_METHOD_LABELS` map (`gcash` / `bank` / `pay-at-hotel`); (c) fall through to the raw `methodKey` as a last resort. The helper is defensive about input shape (nullish / non-string / non-array / missing `label` field) so a malformed admin doc never throws. **The pattern applies to every list-shaped admin config that a guest-facing surface renders** — `paymentMethods[]` was the third list-shaped config to be affected (after `roomTypes[]` per MRB-15-10 and `bookingSources[]` per NBS-04). The contract is: any guest-facing surface that displays a label sourced from a list-shaped admin config MUST read the label dynamically from the array, with a single shared legacy map as the last-resort fallback, and the same shared helper MUST be used by every surface that renders the same label. Per-surface hardcoded `paymentLabels` / `roomTypeLabels` / `sourceLabels` maps are an anti-pattern — they create a drift surface that the admin can't see and the tests can't catch. The FOL-04 test pins the helper's contract at the unit level (admin-wins / legacy-fallback / raw-key / empty-label / nullish-input / non-array / non-string-method cases); the source-text check is the future enforcement surface (any new guest-facing page that renders a label from an admin config must call the shared helper, not invent its own map). **The shared helper lives in `shared/utils/` so future server-side label rendering (e.g. an admin-side "guest-facing label preview" in Settings) can reuse it without a code-level refactor**. **Don't fetch the label server-side and include it in the public lookup response** — the lookup endpoint is privacy-sensitive (`ref + (email | token)` credential); adding a settings read into it would couple a public-facing credentialed endpoint to the admin's settings path, broadening the read blast-radius for no privacy gain. The public client is allowed to read `settings/hotelConfig` directly today, and the existing `BookingPage` already does the same focused `getDoc(settings/hotelConfig)` fetch. **Don't denormalize the label onto the booking doc at create time** — the label would create a second source of truth that can drift from the admin config; a guest who renames a method weeks later would see the old label on every pre-rename booking. The dynamic read is the canonical "what does the admin say NOW" answer.

- **Always verify Firebase ID token in API routes** — use `Authorization: Bearer <token>` header and verify with Admin SDK before processing any authenticated request.
- **Never match or link a booking to a member by the token's `email` claim without checking `email_verified`** — Firebase email/password signup lets a user claim an arbitrary, unverified email. Any code that grants booking access based on `guestEmail == token.email` (registration `linkBookingsByEmail`, `/api/members/stays`, `/api/email/early-checkin-request` `findBooking`) must require `decodedToken.email_verified === true` first, or an attacker who registers with a stranger's email can link, read (the stays projection leaks `bookingRef` + `lookupToken` = the public cancel credential), and act on that stranger's bookings (Spark Rewards audit 2026-07-18, HIGH-1). Matching by `memberId == token.uid` is always safe; only the email path needs the `email_verified` gate.

## npm Workspaces & Shared Code

- **`shared/` is an npm workspace package (`@spark-inn/shared`)** — always import from the package name, never via relative paths like `../../shared/types`. Relative imports break when files move.
- **`api/` handlers run in Node.js, not Vite** — they cannot use Vite path aliases. Import `@spark-inn/shared` via the workspace package (works in Node.js), and import `hotel.config.ts` via relative path (`../../hotel.config.ts`).
- **`@spark-inn/shared` ships raw `.ts` source (its `package.json` `exports` point directly at `.ts` files)** — fine for Vite, which transpiles it natively, but Vercel's Node.js Function builder does **not** transpile TypeScript reached through `node_modules`/workspace packages, only the `api/*.ts` entry point itself. Any server code that imports `@spark-inn/shared` must go through the esbuild bundle described in `plan/docs/VERCEL-FUNCTION-LIMIT.md` — do not add a second, unbundled import path into `@spark-inn/shared` from anywhere Vercel compiles directly.
- **guest-app's real API router lives at `guest-app/server/apiRouter.ts`, not `guest-app/api/[...route].ts`** — `guest-app/api/[...route].js` is a **committed, build-generated bundle** (run `npm run build:api -w guest-app` and commit the result after changing `server/apiRouter.ts`, any `server/handlers/*`, `server/lib/*`, or `@spark-inn/shared`). Never gitignore it — Vercel's function-detection for `api/` does not see build-generated files that aren't in the git checkout, confirmed during the 2026-07-01/02 outage (see `plan/docs/VERCEL-FUNCTION-LIMIT.md`). Never add a `.ts` file back at `guest-app/api/[...route].ts` — a `.ts`/`.js` pair at the same path is a Vercel build error.
- **The pre-commit API-bundle check is mandatory** — staged changes under `guest-app/server/` or `shared/` trigger `npm run check:api-bundle`, which independently rebuilds to a temporary file and rejects a stale or unstaged `guest-app/api/[...route].js`. Do not bypass the hook; it prevents source fixes from being absent in Vercel's deployed function.
- **Never add files under `guest-app/api/` other than the committed `[...route].js` bundle** — Vercel treats every `.ts` / `.js` file in `api/` (and subdirs) as a separate serverless function. Hobby plan caps at 12. Handlers, lib, and tests all live outside `api/` (`server/` and `tests/api/`). See `plan/docs/VERCEL-FUNCTION-LIMIT.md`.
- **Never set `"type": "module"` in `guest-app/package.json`** — causes every deployed `/api/*` request to crash with `ERR_REQUIRE_ESM` (Vercel's Node builder emits CJS-style `require()` between compiled files).
- **`api/tsconfig.json` at the repo root must keep `"allowJs": true`** — the repo-root `api/[...route].ts` shim (`export { default } from "../guest-app/api/[...route]"`) resolves to a `.js` file; without `allowJs`, `tsc` throws `TS7016` and Vercel silently drops the function (404, no build error surfaced).
- **Always run `npm install` from the repo root** — not from inside individual app folders. The root `package.json` manages all workspace dependencies together.
- **Never add `@spark-inn/shared` to `devDependencies`** — it must be in `dependencies` so Vercel can resolve it during deployment.

- **Only `VITE_`-prefixed variables are exposed to the browser** — never prefix server secrets with `VITE_`.

## React 19

- **No `forwardRef` needed** — in React 19, pass `ref` as a regular prop directly to components.
- **No `useEffect` for derived state** — compute it inline or with `useMemo` instead.

## jsPDF (Receipts & PDFs)

- **Use stable jsPDF fonts unless custom TTFs are verified** — jsPDF cannot access system fonts, and unverified OTF/missing TTF assets can break generation. Use built-in fonts for reliability unless known-good base64 TTF assets are added and visually tested.
- **Test PDF output on multiple browsers** — rendering differences between Chrome, Firefox, and Safari can cause layout shifts in generated PDFs.

## Payments & Uploads

- **Payment proof uploads go to Firebase Storage** — store the download URL in the booking document's `paymentProofUrl` field.
- **Booking upload paths use a preallocated Firestore booking ID** — the client may reserve a `bookings/{bookingId}` document ID before Step 3 uploads, but `/api/bookings/create` must create that exact document inside the transaction. The guest-facing `bookingRef` is still generated server-side inside the transaction.
- **Never store raw file blobs in Firestore** — Firestore has a 1MB document size limit. Always use Firebase Storage for files.
- **Compress images before upload** — use the shared `compressImageFile()` utility for room photos, IDs, payment proofs, QR images, store item photos, and website content photos so uploads stay readable but efficient.

## Intercom (Web Audio API)

- **Notification sound requires a user gesture to unlock** — browser autoplay policy blocks audio until the user has interacted with the page. Unlock on first click after login. Do not play sound on page load.
- **Only play notification sound when the inbox tab is not focused** — do not alert staff who are actively viewing the inbox.
- **`Permissions-Policy` must keep `microphone=(self)` in every `vercel.json` (root, guest-app, admin-app)** — an empty allowlist (`microphone=()`) denies `getUserMedia` for the page's own origin, which silently kills the intercom WebRTC voice call in production while it keeps working in local dev (no headers there). Camera and geolocation stay fully locked (BI-06, booking-intercom audit 2026-07-06).

## Booking Flow

- **Always lock rate at booking time** — store `ratePerNight` in the booking document at the moment of creation. Never recompute from current room rates after booking.
- **Discount IDs are verified at check-in** — the system applies the discount at booking time on guest's honor; staff verifies ID physically. Do not build ID verification into the booking flow.
- **Reservation counters + `paymentStatus` are derived, not denormalized (per #203 BAR-02)** — the 5 counter fields (`roomCount` / `activeRoomCount` / `cancelledRoomCount` / `checkedInRoomCount` / `checkedOutRoomCount`) and the `paymentStatus` aggregate mirror on the `Reservation` type are no longer written to the reservation header. Consumers that need them call `deriveReservationCounters(children)` + `computeReservationAggregatePaymentStatus(childStatuses)` (both in `shared/utils/bookingFolio.ts`) at read time. The 2026-08-08 audit verified that no `where()` / `orderBy()` anywhere references these fields — they are render-time projections only, so removing the writes cannot break a query. If a future feature needs the denormalized value, restore the writes (the data is still in pre-BAR-02 Firestore docs) and re-derive at the new read site. Do NOT add new transactional counter writes; the pattern is gone for a reason. The same audit verified the same posture for the `paymentStatus` aggregate mirror.

## Security & PII

- **Never log PII** — no `console.log(guestEmail)`, `console.log(guestName)`, or similar in any environment. Logs may be stored by Vercel and are accessible to anyone with project access.
- **Never expose payment proof URLs in guest-app** — `paymentProofUrl` is admin-only. Never include it in guest-facing API responses or Firestore queries from guest-app.
- **Never expose `remarks` field to guest-app** — room remarks are internal staff notes only. Filter before returning room data to guests.
- **Never create booking documents directly from the client** — public online/corporate bookings go through `/api/bookings/create`, and staff walk-ins go through authenticated `/api/bookings/create-walkin`. Direct client creates bypass the availability transaction and security checks. Authenticated staff/admin may still update existing booking documents directly for ordinary operational fields permitted by Firestore rules.
- **Never subscribe to or query the `bookings` collection from the guest client** — Firestore rules deny guest reads (`allow read: if isStaff()`). For Step 1 availability UX on the booking page, call `GET /api/rooms/availability?checkIn=...&checkOut=...` (PII-stripped, rate-limited). The actual double-booking prevention is the Firestore transaction in `/api/bookings/create`; the availability endpoint is a UX optimization only. See `plan/features/AVAILABILITY-LOCKING.md §Guest-side availability UX query`.
- **Never create corporate inquiry documents directly from the guest client** — public inquiry submissions must go through `/api/corporate/inquiry` so Turnstile, honeypot, validation, rate limiting, and staff notifications run server-side.
- **Never create Spark Rewards member documents directly from the guest client** — enrollment must go through `/api/members/register` so `memberNumber` is generated server-side and past booking linkage runs consistently.
- **Never change `members/{uid}.rewardsPoints` without a coupled `pointsHistory` entry in the same transaction** — the balance behaves like money; the invariant is `rewardsPoints == sum(pointsHistory.points)`. All server paths (checkout earn, settlement earn, `/api/members/redeem-points`, `/api/members/undo-redemption`) already do this and use deterministic history IDs (`earn-{bookingId}`) so a retry can't double-credit. The manual-adjustment path is still a client-side Firestore transaction, which forces the `members` update rule to allow `isStaff()` to write `rewardsPoints` directly (Spark Rewards audit 2026-07-18, MED-1) — meaning a stray client write could set a balance with no history entry. Preferred direction: move manual adjustment server-side and lock `rewardsPoints` to Admin-SDK-only writes in `firestore.rules`. Until then, never add a second client-side writer of `rewardsPoints`, and keep manual adjustment's member-update + `pointsHistory.add` inside one `runTransaction`.
- **Never trust client-supplied role, `isCorporate`, or `corporateCode`** — always derive from server-side token verification or Firestore lookup.
- **Booking lookup requires BOTH ref AND email** — never return booking data on ref alone. Prevents enumeration attacks.
- **Do not share PII via intercom chat** — staff must use the booking system for sensitive information. Intercom is open and unencrypted at rest.
- **Rate limit public API endpoints** — voucher validation, corporate code validation, and booking creation are unauthenticated and must be rate-limited to prevent abuse.
- **Firebase Storage payment proof files are not public** — Storage rules must restrict read access to authenticated staff. A leaked URL without proper rules gives anyone access.
- **Consent checkbox is required at booking Step 2** — do not allow booking submission without it. Links to `/privacy` and `/terms` pages.
- **Honeypot field must be hidden via CSS, not `display:none`** — bots detect and skip `display:none` fields. Use `position: absolute; opacity: 0; pointer-events: none` instead.
- **Honeypot rejection must be silent** — return `200` with a fake success response when honeypot is filled. Never return an error that reveals the anti-bot mechanism.
- **Turnstile token must be verified server-side** — client-side Turnstile rendering is not enough. Always POST the token to Cloudflare's verification endpoint in the API route before processing any request.
- **Never block a request on Turnstile verification failure with a technical error** — show a user-friendly "Something went wrong, please try again" message.
- **Turnstile bypasses are `NODE_ENV === "test"` only** — never accept sentinel tokens (`mock_token`, Cloudflare dummy tokens) in the API route outside unit tests, and never add client-side `|| "mock_token"` fallbacks. Both shipped once and made every bot gate decorative in production (BI-02, booking-intercom audit 2026-07-06). Local dev needs no bypass: non-production origins verify against Cloudflare's always-pass test secret.
- **Turnstile tokens are single-use** — reset the widget (`useTurnstileToken().reset()`) after every request that sent the token to siteverify, or the next submit fails with a duplicate-token error.
- **Render Turnstile through `useTurnstileToken` with a correct `enabled` gate** — never inline the widget mount in a page effect with `[]` deps; if the container div is conditionally rendered (step-gated forms, loading skeletons), an effect that bails on a null ref will never render the widget (BI-03). And never render a fake "verified" panel without a live widget behind it (BI-01).

## White-Label

- **Never hardcode hex color values in components** — always use Tailwind tokens (`primary`, `primary-dark`, `sidebar`). Hardcoded hex values break rebranding for other hotel clients.
- **Never hardcode logo filenames** — always use `config.logos.navbar`, `config.logos.white`, etc. Different clients have different filenames.
- **Never hardcode `spark inn` or any hotel name in UI copy** — always use `config.brandName`. Copy that reads "spark inn" in code will ship as "spark inn" for every client.
- **Never hardcode room count** — room count is dynamic from Firestore. Do not write `Array(14)` or similar anywhere.
- **`hotel.config.ts` is deploy-time, not runtime** — changes require a redeploy. It is not the same as `settings/hotelConfig` in Firestore which is runtime-editable.
- **`public/brand/` filenames must match `hotel.config.ts → logos` paths exactly** — a mismatch causes broken images with no build-time error.
- **Never hardcode room type strings** like `"single"` or `"executive"` in UI components — always iterate the active dynamic room types from context (admin app uses `roomTypes` from `AdminContext`, guest app uses `DEFAULT_ROOM_TYPES` from `@spark-inn/shared`). Hardcoded strings will be wrong for every non-Spark Inn client.
- **Never hardcode `₱`, `PHP`, `Asia/Manila`, `en-PH`, or `+63`** — use `config.currencySymbol`, `config.currency`, `config.timezone`, `config.locale`, `config.phoneCountryCode`.
- **Never hardcode `SI-` booking reference prefix** — use `config.bookingRefPrefix`.
- **`hotel.config.ts` is not editable at runtime** — it requires a redeploy. Do not instruct hotel admins to edit it. Runtime-editable content goes in Firestore Settings.
- **Cancellation policy and house rules come from Firestore, not config** — fetch from `settings/websiteContent` at runtime so hotel admins can update without DK.

## General

- **Never commit `.env` files** — all three are gitignored (`guest-app/.env`, `admin-app/.env`, `api/.env`).
- **Never add code snippets to MD files** — MDs are high-level specs only. Code lives in the codebase.
- **`FIREBASE_PRIVATE_KEY` in `api/.env` contains literal `\n` characters** — use `.replace(/\\n/g, '\n')` when initializing the Firebase Admin SDK, or the key will be malformed.
- **Brand name is always `spark inn`** — all lowercase. Never "Spark Inn" or "SPARK INN" in any UI copy.
- **Never add a granular `allow get: if true` (or `allow list`) next to a staff-only `allow read` in Storage rules** — allows are OR'd, so the public grant wins and the staff restriction becomes decorative. This shipped once on the payment-proof and discount-ID paths, making government-ID photos fetchable without auth (X-01, E2E audit 2026-07-17). If an anonymous uploader needs a preview, use a local blob URL client-side; mint download URLs server-side with the Admin SDK.
- **Never read `pricePerNight`, `weekendRate`, `corporateRate`, `maxCapacity`, `bedDefinition`, `description`, or `amenities` from a room document** — they moved to the RoomType entry in `settings/hotelConfig.roomTypes[]` (W3.6/W3.7). Reading them from `rooms/{id}` yields `undefined`, which silently prices bookings at ₱0 and disables capacity checks (C-01, E2E audit 2026-07-17). Always resolve the type entry (server: read `settings/hotelConfig` in the transaction; client: `useRoomTypes` helpers).
- **Never Zod-validate only part of a public API request body** — validate the entire body, including top-level scalar fields, with one strict schema. `/api/bookings/create` once validated only the nested `guestDetails` object while the top-level `guests` count reached price math unvalidated, letting negative/non-numeric values manipulate `totalPrice` (G-01, E2E audit 2026-07-17). Numeric fields that feed pricing must be validated as finite, integral, and range-bounded server-side.
