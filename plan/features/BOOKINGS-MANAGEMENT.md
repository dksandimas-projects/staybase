# Bookings Management
> Requires: CLAUDE.md, plan/docs/FRONTEND.md, plan/docs/BACKEND.md, plan/docs/API-ROUTES.md, plan/admin-app/CLAUDE.md

## Overview

The primary operational tool for front desk staff at `/bookings`. Displays all bookings in a filterable, sortable table. Staff view and work bookings in a status-aware four-section drawer workspace, advance booking status, manage the folio (payments, refunds, discounts, incidental charges, store charges), generate receipts, log cancellations, and create walk-in or manual bookings.

---

## Workspace Layout & BDUX Contract

The drawer is a status-aware workspace (`BookingDrawerWorkspace.tsx`):

- **Sticky Header:** Booking context (guest, room, stay, status, source), lifecycle indicator, Total/Paid/Balance summary, and actionable alerts.
- **Four Task-Based Sections:**
  - **Overview:** Guest info, room/dates, breakfast inclusion, compact payment status, financial summary.
  - **Check-in:** Readiness checklist, registration, signature, guest ID photo, discount verification, breakfast selections.
  - **Folio:** Money ledgers, discounts, payment proofs, receipts, incidental & store charges.
  - **Activity & More:** Email actions/history, move/upgrade/reschedule, audit detail, cancellation.
- **Sticky Footer:** Context-aware primary action button for the current status plus a **More actions** dropdown menu.
- **Focused Task Modals:** Bounded responsive modals for discount verification, payment recording, refund recording, charge adding/voiding, and cancellation.

Per `feat/staff-special-requests-capture` (2026-08-21): three staff surfaces capture inbound special requests (from email or phone) into the booking doc. The public `/book` form does NOT collect the input — see `feat/special-requests-redirect` (commit 78a79f7) for the redirect-only public path.

**Three capture surfaces:**
1. **Booking drawer editor** (`BookingDrawerWorkspace.tsx` → `BookingSpecialRequestsEditor`). Mounted in the drawer's Overview section so the staff sees the request alongside guest identity. Inline edit with "Last edited by &lt;uid&gt; · &lt;timestamp&gt;" metadata line. Save posts to `/api/bookings/set-special-requests`.
2. **Walk-in modal** (`BookingsPage.tsx`). The desk types the request directly when creating a walk-in booking. - Staff-only (firestore.rules: `isStaff()` + `affectedKeys().hasOnly([...specialRequests, specialRequestsUpdatedAt, specialRequestsUpdatedBy, ...])`)
- 30/min/IP rate limit on the server endpoint

**Discovery surfaces (read-only):**
- **Calendar grid icon + hover tooltip** (`CalendarPage.tsx` line ~580). Each booking cell that has a non-empty `specialRequests` renders a small amber icon with `title=` showing the text (truncated at 80 chars). Front desk sees requests at a glance when scanning the day's rooms.
- **Intercom amber banner** (`IntercomChatPanel.tsx`). When a guest mentions a request mid-chat, the banner surfaces the stored value. Coexists with the staff-capture surfaces — the drawer is the source of truth, the banner is the discovery aid.

### Approved Early Check-In Calendar Indicator

Per `fix/confirmed-early-checkin-badges` (2026-08-22), an approved Spark Rewards early check-in is visible at the two front-desk scanning points where arrival timing matters most:

- **Booking calendar:** the booking's arrival-day cell shows a small emerald `CalendarClock` icon with no time text. When the booking also has a special request, the green early-check-in icon and orange message icon form a compact vertical indicator stack at the cell's top-right.

Special-request details include the full request and last-edit metadata when available.

The green calendar icon renders only for approved requests. The staff-confirmed override time takes priority in the drawer, with the guest's requested time as the fallback when the request was approved as submitted. Pending and declined requests do not render the green icon.

### Admin-Granted Early Check-In

Admins can add early check-in directly from the booking drawer when the booking has no early-check-in record, its status is `payment-confirmed` or `confirmed`, and its check-in date has not passed. The Overview panel collects a required time and optional note, then sends the guest a source-aware confirmation email. The same approved calendar icon and drawer-header badge appear immediately after the write.

The server, not the drawer, is authoritative: grant mode is admin-only, runs in a Firestore transaction, never overwrites a guest request, and treats an exact retry as an idempotent replay without sending a duplicate email. The stored record is marked `source: staff-granted` and includes the resolver and timestamps. Front Desk can view the details but only an administrator can change the time or remove an admin grant. Existing and legacy guest requests keep the current Front Desk/Admin approve-and-decline workflow.

## New Booking Modal (Walk-in Create) — NBS-2026-08-08 fixes

The New Booking modal + the Calendar's "Book dates" modal are the staff walk-in create paths. Both post to `POST /api/bookings/create-walkin` via the shared `addWalkinBooking` helper in `admin-app/src/context/AdminContext.tsx`. The 2026-08-08 booking-flow audit closed 6 findings in one batch on `fix/new-booking-audit-2026-08-08` (decision #206):

- **Preallocation contract (F1):** the modal preallocates `bookingId` + `reservationId` in a `useState` lazy init. The same pair is reused across retries inside the modal session, so a retry-after-uncertain-response hits the server's idempotency replay path (MRB-02 / decision #164) instead of creating a duplicate booking. The pair rotates when the modal opens and after a successful submit, so a second booking in the same page session gets a fresh pair. The Calendar create modal has the same pattern.
- **Required email + phone (F4):** the previous walk-in path wrote `walkin-${Date.now()}@example.invalid` + the literal string `"n/a"` to Firestore when the desk left the email/phone fields blank. The fake email then occupied the match-by-email field for every later Spark Rewards link / /my-booking lookup / contact-inquiry reply. The fix requires both fields at submit time (toast warning + early return) and stores the desk-entered values. The "we'll get the real one at check-in" rationale is gone — the brief was wrong; the fake email did real harm.
- **Adult/child + extra bed steppers (F8, Calendar only):** the Calendar create path now collects the adult/child split + extra bed count the same way the New Booking modal does. The pre-F8 path only collected `guestCount` (the total), so a 3-guest booking in a 2-adult room silently defaulted to "all adults, no extra beds" — bypassing the EXB-03 overflow check. The form distributes `numAdults = guestCount, numChildren = 0` on a quick-set via the `Guests` field, and the split steppers override when the desk knows the actual mix. The server derives `numGuests = numAdults + numChildren` (CHD-04) and applies the EXB-03 overflow rule against the selected room type's `maxExtraBeds`.
- **Walk-in reset on success (F9):** the post-success reset no longer seeds the next stay with `roomTypes[0]?.value || ""` while the room type catalog was still hydrating (the previous shape produced a permanent empty dropdown for the desk's next booking). The fix seeds with `""` and lets the existing effect re-sync to the first loaded type on the next paint.
- **Walkin `isSubmitting` reset (F13):** the `finally` block always clears the submitting flag; the previous shape left the flag set on a successful submit + blocked the next attempt if the navigation was blocked.
- **Turnstile skipped by design (decision #205):** the walk-in endpoint does NOT call `verifyTurnstile` on the way in. Staff sessions are already gated by the Firebase Auth staff login + the admin role-claim check at the API route (`authenticateStaff`); both are stronger than Turnstile. A leaked staff token is the same blast radius as a leaked staff account (revocation = staff-side credential rotation). The walk-in endpoint shares the `bookings-reschedule:30/min/IP` rate-limit bucket with the reschedule + add-room paths.

**Test coverage** — `admin-app/src/__tests__/nbs-2026-08-08-walkin-preallocation.test.ts` + `nbs-2026-08-08-walkin-required-fields.test.ts` + `nbs-2026-08-08-walkin-reset-room-type.test.ts` + `nbs-2026-08-08-calendar-adult-child-extrabed.test.ts` pin the contracts at the source-text level (per the existing MRB-15-10 / FOL-02 / audit pattern).

## Multi-Room Reservations (MRB-07)

The New Booking modal creates a reservation covering one **or more** rooms — walk-in groups, phone bookings, and OTA entry all book blocks.

- **Room stay list:** each stay picks its own room type + specific vacant room and carries its own occupancy steppers (adults / children / extra beds). Rooms may be of different types. The lead guest, dates, source, payment, discount, and voucher stay reservation-level; guests are distributed across rooms, never repeated on each.
- **Picker safety:** a room already claimed by another stay is filtered out, and the submit button stays disabled until every stay names a vacant room and fits its own type's caps — all of these are server rejects.
- **Preview:** the accommodation figure is the sum of the per-stay charges, each priced against its own type; a multi-room reservation states its room count and room numbers.
- **Reset:** a successful create drops the modal back to a single empty stay, so the next booking never inherits the previous group's rooms.

**List rendering.** The main Bookings list shows one row per reservation with its room stays nested beneath it (collapsed by default; the row expands rather than opening a workspace). The reservation row shows the public reservation ref, room count, aggregate total, and group balance due. **Status** is now an aggregate read from the `Reservation` header (per MRB-12 below) — a tone-mapped pill (`Awaiting` / `Verified` / `Confirmed` / `In-house` / `Completed` / `Cancelled`) with the outstanding amount surfaced inline when the group is not settled, plus a `X cancelled` chip when the denormalized `cancelledRoomCount > 0`. The legacy `Mixed` chip stays as the cold-start fallback (when the listener hasn't hydrated yet); the next snapshot replaces it with the aggregate pill. Operational quick views — Needs attention, Arrivals today, Departures today, In house — stay **room rows**, because the unit of work there is a room. A reservation is only grouped when it holds more than one row currently in view, so filters never misreport the result set; single-room reservations and legacy bookings without a reservation link render as plain room rows.

**Action scope.** Inside a multi-room reservation, the drawer shows a reservation strip (ref, "Room X of N", one-tap navigation to sibling rooms) and every action states what it touches: `This room` for check-in, confirm, move/upgrade, and cancel; `All rooms` for the reservation-owned folio actions (payment review, collect balance, confirm with balance). Single-room and legacy bookings show no scope labels.

**Deep links.** `?bookingId=` opens that room's drawer. `?reservationId=` / `?reservationRef=` expand the reservation in the list and open its lead room.

## Multi-Room Reservation Affordances (MRB-12)
> Decision: `plan/docs/DECISIONS-FEATURES.md #179`. Builds on MRB-07 (the reservation row + drawer reservation strip + per-action scope labels) and the MRB-11 stored `aggregateRevenueAllocation` (the header fields the row reads from).

- **The header is the source of truth for the row summary.** A new `subscribeToReservations` listener in `AdminContext` hydrates every `Reservation` doc into a `Record<reservationId, Reservation>` map (full-collection `onSnapshot`, no `orderBy`; the row builder is a hash lookup keyed by `reservationId`). A second `collectionGroup("payments")` listener filters to `reservations/{id}/payments/{paymentId}` paths in JS (legacy `bookings/{id}/payments/{paymentId}` entries are excluded by the regex anchor) and sums positive-amount entries + negative refund entries into a `Record<reservationId, paidAmount>` aggregate. The reservation row's Total reads `reservation.totalPrice`; the Balance reads `Math.max(0, reservation.totalPrice − paidAmount)`. The child-sum is gone — it was the source of a silent filter-hides-room bug (`brt=Deluxe` on a 3-room group with 1 Standard + 2 Deluxe would drop the Standard room from the math because the children array was already filtered before the sum). N=1 + legacy null-`reservationId` paths stay byte-equivalent to pre-MRB-12 (the row never synthesises a reservation row for those, so the legacy code paths render). The cold-start race is preserved: when the listener hasn't fired yet, the row falls back to the child sum so the first paint never reads zero.
- **The `Reservation` contract — the row never sums N children to render a summary.** This is the headline guarantee of MRB-12 — and the bug the previous code violated. A desk officer filtering by `brt=` or `bs=` or `bq=` on a multi-room reservation sees the GROUP-level total + balance + status, not a filtered partial. The header doesn't filter, so the bug is impossible by construction. Per-room detail is still available via the existing Show/Hide rooms expander (MRB-07) — MRB-12 is a summary-level guarantee, not a removal of the per-room drill-down.
- **The Status column reads `Reservation.paymentStatus`.** The aggregate `paymentStatus` (`awaiting-payment` / `payment-uploaded` / `payment-confirmed` / `confirmed` / `in-house` / `completed` / `cancelled`, mapped from the booking-status enum per the existing `mapBookingStatusToReservationPaymentStatus` / `computeReservationAggregatePaymentStatus` helpers in `shared/utils/bookingFolio.ts`) renders as a tone-mapped pill. The outstanding amount (`totalPrice − paidAmount`) surfaces inline when the group is not yet settled — a `Verified` 3-room reservation with ₱X paid shows `Verified ₱Y due`; a `Settled` group shows just `Settled` (no `₱0 due` noise). When `Reservation.cancelledRoomCount > 0`, an additional `X cancelled` chip renders with a tooltip listing the cancelled room numbers — the desk never has to expand a row to know a group has cancellations in it.
- **The drawer reservation strip shows the reservation aggregate.** The existing strip (ref + position + sibling-room buttons from MRB-07) gains three pills (Total / Paid / Balance) reading the `Reservation` header + the reservation-scope paid-amount aggregate. The per-room `BookingDrawerWorkspaceHeader` below keeps its own per-room money (Total / Paid / Balance for the room the desk is currently looking at); the strip's pills are the GROUP-level read, not a replacement. Hidden when `selectedReservationContext` is null (N=1 / legacy) — the strip already gates on that.
- **The discount form has a `This room` / `All N rooms` segmented control** mirroring the MRB-13 cancel-modal pattern. `scope=room` calls the existing per-booking `apply-discount` endpoint (byte-equivalent to today). `scope=reservation` iterates `selectedReservationContext.rooms` and calls the same endpoint for each — errors on a single room abort the loop and surface the failure to the desk (already-repriced rooms keep their new totals; the operator retries the failed room). The modal title, the submit button label, and the success toast all switch with the selected scope (`Apply to all N rooms` / `Reservation repriced (N rooms)`). The scope state resets to `null` on close (mirrors the MRB-13 `bookingCancelScope` reset). The API surface does not change. A transactional `applyReservationDiscount` endpoint is the MRB-14+ follow-up if atomicity ever matters.
- **The `Apply discount` action carries the `renderActionScope("room")` chip** (MRB-12-04). The chip is informational so the desk sees the scope before opening the modal; the segmented control in the form is the actual scope picker. Other multi-room actions (Confirm pay-at-hotel, Confirm booking, Move / upgrade room, Check in, Review proof in Folio, Collect balance, Confirm with Balance, Cancel) already have their scope chips from MRB-07 / MRB-13.
- **BDUX verification rows #144-152 close automatically** with MRB-12. The row's group-level read + the strip's money pills + the action-scope chip on every multi-room action together satisfy the "no-scroll, all-status, no-hidden-rooms" criteria: a desk officer triages a 3-room group without expanding it, sees the group's due total inline, and every action states what it touches.

## Post-Create Room Changes (MRB-14)
> Decision: `plan/docs/DECISIONS-FEATURES.md #180` (implementation record). Builds on MRB-04 (the reservation header + aggregate counters), MRB-07 (the multi-room `WalkinRoomStay` pattern + per-action scope labels), MRB-08 (corporate + voucher `usageCount` increment-by-N), MRB-09 (the reservation-scope email view), MRB-11 (the stored `revenueAllocation` + the `aggregateRevenueAllocation`), and MRB-12 (the AdminContext reservations listener + the drawer reservation strip).

- **The header's `checkIn` / `checkOut` are immutable shared-dates snapshots from create time.** This is the headline contract of MRB-14. Pre-MRB-14, `handleRescheduleBooking` did `transaction.update(reservationDocRef, { checkIn, checkOut, numNights, ... })` — extending one room by 2 nights rewrote the header's "Jan 1 → Jan 5" to the new child's "Jan 1 → Jan 7", and every other room in the reservation, the email subject, the receipt PDF, the dashboard's date filter, and the checkin reminder cron all suddenly showed "Jan 1 → Jan 7" even though the other 2 rooms were still "Jan 1 → Jan 5". The fix: freeze the header's `checkIn` / `checkOut` at create time and add a new `actualDateRange: { earliestCheckIn, latestCheckOut, isDivergent } | null` field for the children's spread. The reschedule handler now queries every child via `where("reservationId", "==", id)` in the same transaction + recomputes the header's `actualDateRange` (and re-stamps each child's `revenueAllocation` per the MRB-11 invariant). Pre-MRB-14 reservations have no `actualDateRange` field (the admin + email + receipt surfaces fall through to the legacy per-child read, byte-equivalent to pre-MRB-14).
- **Staff can add a room to an existing pre-arrival reservation using the header's current dates.** New `POST /api/bookings/add-room` endpoint (staff auth, shares the `bookings-reschedule:30/min/IP` rate-limit bucket) — body: `{ reservationId, roomId, numAdults, numChildren, extraBedCount?, discountType?, voucherCode? }`. **Dates are NEVER in the body** — the server reads them from the header. The new child is created via the existing `walkinRoomStayFinancials` chain (same per-line pricing, same per-stream `revenueAllocation` snapshot, same `getLockedManualNightlyRate` for manual-rate reservations) and the reservation header is updated in the same transaction: `roomCount += 1`, `activeRoomCount += 1`, `subtotal += newChild.subtotal`, `totalPrice += newChild.totalPrice`, `aggregateRevenueAllocation = sum(children.allocation)`, `actualDateRange` recomputed (always the same as the header on add-room — `isDivergent` stays `false`). `corporateCodes.usageCount` increments by 1 if the reservation is corporate (per MRB-08's "N rooms = N uses" rule); `vouchers.usageCount` increments by 1 if a `voucherCode` is applied. The new child's `holdExpiresAt` inherits the header's. One `booking-rescheduled` email fires after the commit. Idempotency key: `add-room-${reservationId}-${roomId}-${now}` (a retry after an uncertain response replays the original commit, never appends a duplicate).
- **Admin modal — "Add room to this reservation" button** in the Bookings drawer More actions section. Gates on `selectedBooking.reservationId && RESCHEDULABLE_STATUSES.includes(selectedBooking.status)` (hidden for legacy null-`reservationId` bookings — the add-room flow is a multi-room concept; hidden for in-stay bookings — the in-stay path is the reschedule handler). The button carries the `renderActionScope("reservation")` chip (MRB-07) so the desk knows the new room is part of the reservation. The modal collects room, occupancy, optional extra bed, optional discount + voucher; dates are not collected (read from the header server-side).
- **Per-child dates UI when `actualDateRange.isDivergent === true`.** The Bookings table Dates column renders the divergent dates with a `data-testid="reservation-dates-divergent"` badge ("Jan 1 → Jan 8" + a "varies by room" pill) and a per-room tooltip listing each child's dates. The drawer reservation strip gains a third pill row (`data-testid="reservation-strip-actual-range"`) below the Total / Paid / Balance pills showing the actual range + "varies by room" + a per-room tooltip. The email `buildReservationEmailView` emits `actualDateRange` on the view and per-room `checkIn` / `checkOut` on `roomProjections`; the reservation branch in `bookingRows` reads `booking.actualDateRange?.isDivergent` and shows the actual range + "(varies by room)" + per-room dates when divergent. The receipt PDF's Stay card gains an "Actual range" line + per-room dates inline under each room label when divergent. N=1 + legacy null-`reservationId` paths stay byte-equivalent (no children to diverge, no header to read).
- **Test coverage.** 6 pure-helper tests (`shared/__tests__/mrb-14-actual-date-range.test.ts`) + 5 source-text tests (`guest-app/tests/api/mrb-14-reschedule-preserves-header.test.ts`) + 11 endpoint tests (`guest-app/tests/api/mrb-14-add-room-endpoint.test.ts`) + 1 admin hydration test + 2 admin modal tests (in `mrb-12-admin-reservation-affordance.test.ts`) + 12 per-child-dates-UI source-text tests (`admin-app/src/__tests__/mrb-14-04-per-child-dates-ui.test.ts`) = **37 new tests** across 5 test files. The `firebase/tests/mrb-14-add-room.emulator.test.ts` round-trip is the Java-gated follow-up.

## Key Workflows & Rules

### Discount Verification (Senior/PWD)
- Uploaded OSCA/PWD ID photo thumbnail displayed in Check-in section.
- Verification actions: **Verified** (`discountVerified: true`), **Rejected** (`discountRejected: true`, requires staff reason).
- Rejection restores `totalPrice` to pre-discount amount, triggers rejection email, and requires guest to pay full balance.
- **Re-verify after rejection (DSC-05, decision #228, 2026-08-20).** After a rejection the booking's `discountType` field stays populated (rejection sets the rejection flags but doesn't clear the type), so the folio's "Discount or voucher" card at `admin-app/src/pages/BookingsPage.tsx:5768-5811` must re-show an affordance for staff to verify the (physically re-checked or resubmitted) ID. **The state machine is 4 states, with the rejected state being reversible:**
  - `pending review` → `verified` (terminal happy path; staff clicks **Approve Discount** in the check-in panel — server stamps `{ discountVerified: true, discountVerifiedBy, discountRejected: false, updatedAt }`)
  - `pending review` → `rejected` (terminal email + full-price bill; staff clicks **Reject Discount** with a required reason — server stamps `{ discountRejected: true, discountRejectedBy, discountRejectionReason, updatedAt }` and the existing `handleRejectDiscount` re-prices to `originalTotalPrice`)
  - `rejected` → `re-verified` (the DSC-05 path; staff clicks the new **Re-verify ID** button in the folio card — fires the SAME `updateDoc` payload as the check-in Approve, no new server endpoint, no new field, no email re-sent)
  - `re-verified` → `rejected` (a SECOND rejection after a re-verify is allowed — same server shape as the first rejection)
- **The DSC-05 UI bridge** — three folio changes, no data model change:
  1. **Chip 3-state:** replace the pre-DSC-05 `discountVerified ? "Verified" : "Pending review"` 2-state ternary with the 3-state shape the check-in chip uses at `:5838-5850`. The chip text becomes `✓ Verified` (green) / `✗ Rejected` (red) / `⌛ Pending Review` (amber), matching the check-in chip's exact wording + colour palette so the desk sees the same chip on both panels.
  2. **Re-verify ID button** — a `<button>` labelled `Re-verify ID` renders next to (or below) the existing `Apply discount` slot when `discountRejected && RESCHEDULABLE_STATUSES.includes(status)`. Opens a `<ConfirmForm>` titled "Re-verify this rejected discount?" whose body cites the prior `<strong>{discountRejectedBy}</strong> · <em>{discountRejectionReason}</em>` from the audit cluster. Confirming fires the same `updateDoc` payload as `:5914-5924` (`{ discountVerified: true, discountVerifiedBy: currentUser.email, discountRejected: false, updatedAt }`).
  3. **Apply discount stays hidden on rejection** — re-applying the same discount type the ID just rejected is meaningless. The button only re-shows when `!hasVoucherOrDiscount` (no discount + no voucher) OR after a successful re-verify.
- **No new server contract.** DSC-05 reuses the existing approve-discount writer. The audit trail lives on the existing fields (`discountVerifiedBy` + `discountRejectedBy` + `discountRejectionReason` + `updatedAt`). The lifecycle event is silent on the guest's email (deliberate — the guest already saw the rejection email + the full-price total; a successful re-verify restores the discount without sending a third email).
- **Source of truth.** The `discountVerified` boolean flip is the durable "verified at some point" signal per FOL-01 (decision #197); the audit cluster is the WHY of any rejection. No `discountReverifyAt` timestamp — the FOL-01 pattern + the audit cluster's `discountRejectedBy` already carry the durability required for 14-room scale.
- **Downstream gates.** IDG (#227 reserved) reads `!discountVerified && !discountRejected` for its dashboard gate — a re-verified-after-rejection booking falls through to IDG's "verified or rejected → buttons re-enable" branch, same as a first-time verify. CRL-02..09 unaffected (cancellation audit is a separate cluster). MRB-12 (reservation-scope apply-discount segmented control) unaffected — the re-verify is always booking-scoped because `discountType` lives on the booking doc. DSC-04 (atomic `handleApplyReservationDiscount`) unaffected — DSC-05 is at the verify-rejection seam, not the apply seam.
- **Tests.** `admin-app/src/__tests__/dsc-05-discount-reverify-after-rejection.test.ts` (NEW, ~10 source-text guards: 3-state branch on folio, `✗ Rejected` chip matches check-in copy verbatim, `Re-verify ID` render condition + label, `Apply discount` stays-hidden-on-rejection anti-regression, prior-rejection audit cluster surfaces in confirm body, confirm handler calls same `updateDoc` shape as `:5914`, audit cluster fields hydrated via FOL-02 admin mapper). The `phase-12-booking-drawer-folio-interaction.test.ts` line-97 assertion splits into "hides apply discount when verified" + "shows Re-verify ID when rejected" (replace, not duplicate).

### Onsite Payments & Refunds
- **Record Payment:** Collects payment amount, method (from `hotelConfig.paymentMethods`), and tender reference (`transactionReference`). Append-only ledger in `payments` subcollection.
- **Refunds:** Admin-only, requires method and reason. Appends immutable negative refund record. Idempotent via client-preallocated doc ID.
- **Receipt:** Reservation-linked stays generate one reservation-referenced PDF with deterministic child-room allocation lines, aggregated VAT, attributed folio charges, and one reservation payment/balance section. Legacy bookings retain the historical single-room PDF.

### Unpaid Checkout (UCO) & Confirm with Balance (CWB)

### Cancellation Rules (CRL)
- Staff can cancel any pre-arrival status (`pending`, `payment-uploaded`, `payment-confirmed`, `confirmed`).

- **Snapshot fallback chain at read time (decision #210).** At booking create, `cancellationPolicySnapshot` is stamped on the **reservation header** (`reservations/{id}.cancellationPolicySnapshot`, per CRL-05), not on the child booking. Both `handleCancelPreview` and `handleCancelBooking` therefore resolve the per-child snapshot via a 3-link chain: (1) the child booking's own snapshot if present, (2) the reservation header's snapshot if the booking has a `reservationId`, (3) a synthesized legacy-default snapshot (48h cutoff / 100% before / 0% after / `source: "legacy-fallback"`) derived from the booking's own `checkIn` Timestamp for legacy pre-MRB-01 null-`reservationId` bookings. Without the chain, the helper's `fallbackContext.checkInDateKey: ""` falls through to `Date.now()` and every future-dated booking's cancel would report "0.0 hours before check-in" with `refundPct: 0` — silent money eating on a paid beyond-cutoff cancel.

### Reservation-Scope Cancellation (MRB-13)
> Decision: `plan/docs/DECISIONS-FEATURES.md #166` (spec) + `#170` (implementation record). Builds on MRB-01..06 (decision #159, reservation header) and CRL-02..05 (audit metadata + server-side status matrix + structured policy snapshot).

- **Scope field on the cancel endpoint.** `POST /api/bookings/cancel` accepts an optional `scope` field: `"room"` (default, byte-compatible with the current single-child behavior) or `"reservation"`. The `bookingId` / `bookingRef` in the body anchors the request as today; `scope` chooses the unit of action. The guest body validates `scope` through `guestCancelSchema` (`scope: z.enum(["room", "reservation"]).optional().default("room")`); the staff body reads `req.body.scope` directly (the staff router does not gate the staff body's shape — the same default `"room"` applies).
- **Server transaction (room scope).** Today's behavior is preserved byte-for-byte. The MRB-05 reservation header mirror still runs; the CRL-02 audit metadata still stamps; the existing per-booking `booking-cancelled` email still fires. The room-scope branch lives in the `else` arm of the `if (isReservationScope)` dispatch — the original per-child `runTransaction` is unchanged.
- **Server transaction (reservation scope).** When `scope === "reservation"` and the looked-up booking has a `reservationId`, the server runs a single `runTransaction` that: (a) reads the `reservations/{id}` header + every child via `where("reservationId", "==", lookedUpReservationId)`; (b) splits the children into a cancellable set (skipping `checked-in` / `cancelled` for any source, plus source-mismatched statuses for the guest path — the same matrix the per-child pre-transaction check enforces) and skips the rest; (c) for each cancelled child writes the canonical CRL-02 audit stamps (`status: "cancelled"`, `cancelledAt`, `cancelledBy`, `cancellationSource`, `updatedAt` — all sharing the `now` captured at the top of the try block) + the per-child MRB-05 loyalty clawback (`clawback-${bookingId}` negative `pointsHistory` entry, `rewardsPoints` field unchanged, `pointsAwarded` reset to `0` and `loyaltyAwardStatus` flipped to `"clawback-recorded"` — the invariant `rewardsPoints == sum(pointsHistory.points)` is preserved); (d) **deduplicates** voucher + corporate code `usageCount` decrements by building a `Map<code, count>` from every cancelled child — a code shared across N children decrements by N (matches the MRB-08 create-time `+= assignedRooms.length` increment, decision #167), not by 1; (e) updates the reservation header (`cancelledRoomCount += cancelledCount`, `activeRoomCount -= cancelledCount` floored at 0, `paymentStatus: computeReservationAggregatePaymentStatus(postStatuses)` where cancelled children report `"cancelled"` and survivors report their current status — a full cancel returns `"cancelled"`, a partial cancel returns the aggregate of the survivors).
- **First-created room has no special consequence.** The reservation folio (`reservations/{id}/payments` and `reservations/{id}/refunds`) is the source of truth. Cancelling the first child looks the same as cancelling any other child — the same `cancelledRoomCount++`, the same `activeRoomCount--`, no folio claim, no "primary room" concept. The decision entry records the rejected alternative of a "primary room" model.
- **Admin scope selector.** The `BookingsPage` cancel modal (`admin-app/src/pages/BookingsPage.tsx` cancel footer + the new `bookingCancelScope` state + the `ConfirmForm`'s `additionalFields?: ReactNode` slot) gains a `This room` / `All N rooms` segmented control when `selectedReservationContext` is set (N>1). The default is `"room"` (safer — staff must opt into the whole-reservation path). The control forwards the chosen scope to `updateBookingStatus` via a new 4th `options?: { scope?: "room" | "reservation" }` parameter, which sets `scope` in the API body. The `ConfirmForm`'s `additionalFields` slot is the source-text anchor (`data-testid="booking-cancel-scope-selector"`, `data-testid="booking-cancel-scope-room"`, `data-testid="booking-cancel-scope-reservation"`); other `ConfirmForm` callers (order cancel, discount reject) omit the prop and keep the legacy reason-only shape. For `reservationRoomCount === 1` or legacy null-`reservationId` bookings, the selector is hidden and the modal behaves as today.
- **Email action dispatch.** The handler computes a `postTransactionAction: "booking-cancelled" | "booking-cancelled-reservation"` local from `isReservationScope`. The reservation-scope path fires `sendBookingTrigger("booking-cancelled-reservation", view)` (the MRB-09 multi-room template — splits rooms into "cancelled" + "surviving" via the per-child `cancelledAt` stamp, subject reads "Reservation updated: R-… (N rooms)"); the per-child path keeps the legacy `sendBookingTrigger("booking-cancelled", view)` (which MRB-09 already taught to render the full reservation view when the booking has a `reservationId`). The view is loaded by the existing `loadReservationEmailView(bookingId)` helper. Per CRL-04 the explicit "no refund is issued automatically" callout stays.
- **Voucher / corporate code double-decrement fix.** The pre-MRB-13 code decrements `usageCount` once per cancelled child — a shared code on a 3-room reservation that gets all three rooms cancelled is decremented 3×. The reservation-scope path decrements once per shared code by the count of cancelled children that used it (a code shared by 3 children decrements by 3 — matches the MRB-08 create-time `+= assignedRooms.length` increment); the existing room-scope path is byte-compatible (decrements once per cancelled child, which is correct because the room-scope cancel never cancels more than one child). Source-text guard: `guest-app/tests/api/mrb-13-cancel-scope.test.ts` (29 tests).

### Cancellation Refund Liability + Admin Workflow (CRL-07)
> Decision: `plan/docs/DECISIONS-FEATURES.md #173`. Builds on CRL-02 (audit metadata), CRL-05 (structured policy snapshot), CRL-06 (preview's `staffProcessingRequired` flag), MRB-04 Phase 2.x (canonical refund subcollection), and MRB-13 (reservation-scope cancel). Behavioural tests + staging rehearsal close in CRL-09.

- **Destructive cancel materialises a `cancellationLiability` snapshot in the same transaction as the status flip.** The new helper `computeCancellationLiabilityInTransaction` (in `guest-app/server/handlers/bookings.ts`) reads the reservation folio (the new `reservations/{id}/payments` + `reservations/{id}/refunds` dual-read pattern, or the legacy `bookings/{id}/payments` for null-`reservationId` bookings), calls `evaluateCancelPreview` with the cancellable-children set, and produces a `CancellationLiability` shape via the pure `buildCancellationLiabilitySnapshot` builder. The snapshot is included in the same `transaction.update(bookingDocumentRef, bookingUpdate)` (per-child + legacy) or `transaction.update(reservationRef, reservationHeaderUpdate)` (reservation-scope) call as the status flip + the CRL-02 audit stamps, so a partial failure cannot leave a half-stamped cancellation. When `policyRefund === 0` the helper returns `null` and the field is omitted (the absence is the "no liability work to do" signal — the destructive cancel never auto-refunds per CRL-04).
- **The snapshot is immutable post-cancel.** `policyResult` is the contract: `refundPct` (MIN per-room, per CRL-06), `policyRefund`, `netCollected`, `retainedAmount`, `cutoffHours` (the snapshotted value, NOT the live settings value), `source` (`"settings"` / `"corporate-override"` / `"legacy-fallback"` per CRL-05), and `snapshottedAt` (the same `now` as the cancel's `cancelledAt` — no clock skew). A later settings change never rewrites a cancelled booking's snapshot. The server reads `policyResult` for display + Reports (CRL-08), never recomputes.
- **`approvedAmount` defaults to `policyResult.policyRefund`.** Reduced only via a new admin-only `POST /api/bookings/cancellation-exception` endpoint. The handler re-checks the admin role (403 for any other role — front desk cannot apply an exception), requires a non-empty `reason` (≤500 chars), and rejects `approvedAmount > policyResult.policyRefund` (400). The endpoint reads the stored liability in the same `runTransaction` that writes the new value, so a concurrent refund write cannot race the exception read. Idempotency: the same `(approvedAmount, reason)` from a retry-after-uncertain-response replays the original commit (`idempotentReplay: true`); a different value overwrites the `exception` field (the audit trail lives in the admin notifications collection CRL-08 adds). Rate-limited at 30/min/IP (a deliberate admin mutation, not a tap-and-confirm action).
- **The five derived states are NEVER stored.** The pure `computeCancellationLiabilityState` helper in `shared/utils/cancellation.ts` takes the stored liability + the derived `processedAmount` (sum of the refunds subcollection — `|sum(refunds entries)|`) and returns the live state. The states: `not-required` (policyRefund === 0), `retained` (approvedAmount < policyRefund — an exception reduced the refund; the retention `policyRefund - approvedAmount` is the "extra we kept beyond the policy"), `pending-processing` (approved === policy AND processed === 0), `partially-processed` (0 < processed < approved), `processed` (processed >= approved). The exception check takes precedence over the processed-vs-pending check — a fully-processed exception is still `retained` until a later change moves it elsewhere. The UI + Reports (CRL-08) + the read-only `/api/bookings/cancellation-liability` projection endpoint all derive from the ledger, never from a denormalized counter.
- **Where the snapshot lives.** `reservations/{id}.cancellationLiability` for reservation-scope cancels + new-path N=1; `bookings/{id}.cancellationLiability` for per-child cancels + legacy null-`reservationId` bookings. Surviving rooms in a partial reservation-scope cancel carry no liability field (their status is unchanged); the reservation header is the source of truth for the aggregate. The per-room detail is recoverable from the cancelled children's own snapshots when N>1.
- **Admin UI surface.** The `BookingsPage` drawer mounts a new `CancellationLiabilityPanel` (in `admin-app/src/components/CancellationLiabilityPanel.tsx`) inside the Folio section when the selected booking is cancelled and a snapshot exists. The panel shows the policy row (immutable) + the approved row (admin-controlled) + the processed row (live from the refunds subcollection) + the outstanding row (derived) + the state badge + a retention callout when an exception was applied. Two action buttons appear when `currentUser?.role === "admin"`: "Record processed refund" (opens the existing `add-refund` modal pre-filled with the outstanding amount — front-desk staff do not see the button) and "Apply exception" (opens a new `CancellationExceptionModal` with the amount input bounded by `policyRefund` + a required reason input). Front-desk staff can see the panel and cancel; only admins can record a processed refund or apply an exception (mirrors the existing `add-refund` admin-only gate, no new authorization surface).
- **Source-text guard + state-helper behavioural tests.** `guest-app/tests/api/crl-07-refund-liability.test.ts` (24 source-text tests covering the type, the state helper, the cancel handler stamping the snapshot, the exception + projection handlers, the apiRouter routes, the admin UI mount, the type hydration) + `shared/__tests__/crl-07-liability-state.test.ts` (23 behavioural tests covering each state, the null fall-through, defensive coercion, the breakdown invariants, and the snapshot builder). End-to-end coverage (book → collect → cancel outside/inside cutoff → partial refund → complete refund → exception → full refund) follows in CRL-09.

### Payment-Verified Read (FOL-01)
> Decision: `plan/docs/DECISIONS-FEATURES.md #197` (off-roadmap bug fix shipped 2026-08-06, v0.264.7 → v0.264.8). Builds on PRC-13 (the verify-and-record-payment flow) and the `handleVerifyAndRecordPayment` server-side `paymentConfirmedAt` stamp.

- **The booking drawer's payment-verified read routes through `isPaymentVerified(booking)`, not the transient `status === "payment-confirmed"` check.** The pre-FOL-01 admin surface read `status === "payment-confirmed"` directly to decide whether the payment was verified — a transient state that doesn't survive the `payment-confirmed` → `confirmed` transition. So a booking the staff had already verified (the common case after `Verify & Record Payment` → `Confirm Booking`) silently fell through to the "Pending" label in the Folio section, and rendered NO badge at all in the Overview section. **Two related UI bugs from the same root cause.** **(1) Folio (line 5195-5208)** — the outer ternary widened the rendered block to include `status === "confirmed"` (so the "View proof" CTA stayed visible), but the inner ternary `status === "payment-confirmed" ? "Verified" : ... : "Pending"` never got the same widening. **(2) Overview (line 4803-4811)** — the `status === "payment-confirmed"` badge check meant a `confirmed` booking with a stamped `paymentConfirmedAt` rendered NO badge at all.
- **The `paymentConfirmedAt` timestamp is the durable "verified at some point" signal.** Stamped by `handleVerifyAndRecordPayment` (line 7700) and `handleMarkPaymentConfirmed` (line 7507) and `handleConfirmBookingWithBalance` (line 8130) on the full-payment transition, and NEVER cleared by any other lifecycle handler. The `onsitePayments[]` ledger entries don't carry a "verified" flag — they're just money-movement rows; the `paymentConfirmedAt` timestamp is the only durable signal for the verification event.
- **The helper ORs the two signals.** `isPaymentVerified(booking)` returns `true` when `status === "payment-confirmed"` (transient: verified right now, before the lifecycle moves on) OR `paymentConfirmedAt` is set (durable: verified at some earlier point; survives the lifecycle). The function is intentionally permissive on either signal alone (a `confirmed` booking that somehow lost the `paymentConfirmedAt` field but the lifecycle says it was verified still reads as verified), but strict (an unknown status with no timestamp does not). Accepts both ISO-string (admin mapper shape) and `Date` (guest lookup shape) for the timestamp. Defensive against null / undefined / empty-string / whitespace / invalid-Date inputs.
- **Both render sites route through the helper.** The Folio block's outer ternary widens to `isPaymentVerified(selectedBooking) || selectedBooking.status === "confirmed" || selectedBooking.paymentRejectionReason`; the inner ternary replaces `status === "payment-confirmed"` with `isPaymentVerified(selectedBooking)`. The Overview's "Pending" badge adds a `!isPaymentVerified(selectedBooking)` guard (so the "Pending" + "Verified" badges are mutually exclusive); the "Verified" badge condition switches from the transient status check to the helper. The DrawerWorkspaceHeader's "Reference" fallback ("Pending verification" italic) is intentionally NOT routed through the helper — it's a different concern (about the reference number, not the verification state).
- **The `paymentRejectionReason` axis stays.** A booking with a rejection reason still shows the "Rejected" badge in the Folio + Overview (different axis; the helper doesn't touch it). The `paymentRejectionReason` field is already hydrated by the existing reject-payment flow and is the only rejection signal the UI needs.
- **The admin bookings mapper hydrates `paymentConfirmedAt`.** The pre-FOL-01 mapper at `AdminContext.tsx:1362` silently dropped the field on every snapshot echo (the same shape of bug as MRB-15-10). The post-FOL-01 mapper adds `paymentConfirmedAt: data.paymentConfirmedAt ? parseDateTimeString(data.paymentConfirmedAt) : null` next to `paymentProofUrl`. The shared `Booking` type declares the field as `Date | null`; the admin extension declares it as `string | null` (the admin's Date → ISO-string convention).

### Check-in / Check-out `runTransaction` Reads-Before-Writes Ordering (FOL-03)
> Decision: `plan/docs/DECISIONS-FEATURES.md #199` (off-roadmap bug fix shipped 2026-08-07, v0.264.11 → v0.264.12). Builds on FOL-02 (decision #198) and the MRB-15-03 "transactional counters" pattern.

- **The Firestore `runTransaction` API requires every `await transaction.get(...)` to complete BEFORE any `transaction.update(...)` / `transaction.set(...)` call.** The pre-FOL-03 `handleCheckinBooking` (line 8203+) and `handleCheckoutBooking` (line 8433+) both read the booking doc, the room doc, and the "other check-ins in this reservation" doc first, then started a write (`transaction.update(bookingRef, ...)`), then read the "all children of this reservation" doc for the `checkedInRoomCount` + `paymentStatus` mirror — exactly the reads-after-writes shape the SDK forbids. The error surfaced as `500 POST /api/bookings/checkin: Error: Firestore transactions require all reads to be executed before all writes.` The check-in flow died before the booking's status flipped to `checked-in` and the room's status flipped to `occupied`; the same shape of bug lived in `handleCheckoutBooking` and would have fired the moment a guest tried to check out. **The read needed to compute the post-update mirror was placed AFTER the writes that mutate the child statuses (the very thing the mirror needs to count), which is structurally impossible to satisfy with a single transaction.** Batched writes don't support transactional reads, splitting into two transactions loses atomicity (the whole point of MRB-15-03), and reordering writes to do the header first is wrong because the count derives from the booking status flip.
- **The fix is a three-part change to `bookings.ts`.** **(1) Pre-read the children-for-count snapshot BEFORE any write** — the read is hoisted out of the post-write block into the pre-write block in both handlers. The read's result is stored in a new `childrenForCount` local (the pre-update state of every child in the reservation). **(2) Compute the post-update child statuses in a separate `postUpdateChildStatuses` array** — built from the pre-read's docs with a per-doc ternary that replaces the target booking's status with its post-update value (`"checked-in"` for checkin, `"checked-out"` for checkout) while leaving the other children's pre-update statuses untouched. The SDK doesn't let us observe the post-update state via a real read (we'd be back to reads-after-writes), so we have to construct it. The mirror computation now reads from this array: filter `s === "checked-in"` for `checkedInRoomCount` in checkin; filter `s === "checked-in"` AND `s === "checked-out"` for the two counts in checkout; then derive `paymentStatus` via `computeReservationAggregatePaymentStatus(postUpdateChildStatuses)`. **(3) Apply all writes in a single contiguous write block AFTER the reads** — the booking + room (and, for checkout, the intercom thread + the reservation header) updates are placed after the pre-reads; the reservation header's `checkedInRoomCount` / `paymentStatus` mirror write uses the pre-computed `postUpdateChildStatuses` so the transaction remains valid.
- **The variable name `postUpdateChildStatuses` makes the "pre-read + post-update replacement" semantic explicit** — a future reviewer can see the construct at a glance without having to trace the per-doc ternary back to its source. The pre-read is named `childrenForCount` to flag that it's a read for the mirror math, not a check for an invariant (the existing `activeCheckinSnap` read serves the invariant purpose; the two are different reads with different consumers).
- **Atomicity is preserved (the whole point of MRB-15-03).** The booking + room + reservation-header mirror still flip together or not at all. The only thing that changed is the order: all reads first, then all writes. The mirror math is the same; only its source changed (from a now-impossible read to a pre-computed array). The 2 affected MRB test files (`mrb-15-03-transactional-counters.test.ts` + `mrb-05-aggregate-and-handler-mirror.test.ts`) are updated to reference `postUpdateChildStatuses` instead of the old `childStatuses` name in 7 places total — a cheaper change than duplicating the test, and the FOL-03 source-text test adds 9 new ordering-specific guards on top.
- **N=1 + multi-room + legacy null-`reservationId` paths are all byte-equivalent.** The pre-read query `adminDb.collection("bookings").where("reservationId", "==", bookingReservationId)` is the same shape for all three cases (a single-child "reservation" of 1 is a list of 1 doc; the per-doc ternary is a no-op for the other children since they all stay at their pre-update status). The mirror math derives from the post-update array regardless of list length. The legacy `bookingReservationId === ""` path is gated separately (it skips the mirror write entirely per the MRB-15-08 legacy fallback) and is unaffected.
- **Test coverage.** 9 source-text guards in `guest-app/tests/api/fol-03-checkin-checkout-transaction-read-order.test.ts` (the test slice boundaries correctly bound the `handleCheckinBooking` body to the `handleCheckoutBooking` declaration and the `handleCheckoutBooking` body to the `handleLookupBooking` declaration so the test reads only the relevant code — `handleAddRefund` comes BEFORE in the file and is NOT a slice boundary; the new pre-read appears before the first write in `handleCheckinBooking`; the new pre-read appears before the first write in `handleCheckoutBooking`; `postUpdateChildStatuses` is constructed via the per-doc ternary that replaces the target booking's status with `"checked-in"` for checkin and `"checked-out"` for checkout; the mirror write in `handleCheckinBooking` reads from `postUpdateChildStatuses`; the mirror write in `handleCheckoutBooking` reads from `postUpdateChildStatuses` for BOTH `newCheckedInCount` AND `newCheckedOutCount`; the pre-FOL-03 read-after-write pattern is gone from both handlers; the 2 MRB test files reference the new var name). The check-in / check-out end-to-end behaviour tests (`bookings-checkin.test.ts` + `bookings-checkout.test.ts` + `bookings-checkout-archive.test.ts`) already cover the round-trip; the FOL-03 source-text pin is the cheap, deterministic guard against future reordering. No new runtime tests added — 0 behavioural tests because the existing round-trips already cover the happy path, and the source-text pin is the structural guard against the regression.

### Verify-Payment Reservation-Scope (FOL-05)
> Decision: `plan/docs/DECISIONS-FEATURES.md #201` (off-roadmap bug fix shipped 2026-08-07, v0.264.12 → v0.264.13). Builds on FOL-03 (decision #199, the "reads before writes" rule), MRB-04 Phase 3 (decision #159, the reservation header `paymentStatus` mirror), MRB-12 (decision #179, the admin reservation affordance), and MRB-15-03 (the transactional counters).

- **The dashboard's "pending payment alerts" list groups children of a `reservationId` into one card per RESERVATION, and the verify / add-payment / reject handlers flip every covered child in one transaction.** The operator-reported bug was "for reservations with multiple rooms, I see 1 row for verification per room". Two related issues from the same root cause. **(1) Dashboard UI** — the pre-FOL-05 list was `bookings.filter(b => b.status === "payment-uploaded")`, a flat per-booking render. A 2-room reservation with both children `payment-uploaded` rendered TWO cards (one per child). The verify amount on each card was the lead room's `totalPrice - onsitePayments.reduce(...)` — not the reservation's. **(2) Server** — the pre-FOL-05 `handleVerifyAndRecordPayment` only flipped the TARGET child's `status` to `payment-confirmed`, even when the cumulative reservation payment covered all siblings (the money was already at the reservation level per MRB-04 Phase 2.x, but the booking-doc status updates were per-room). So even if a guest paid the full reservation in one GCash transfer and the staff verified the full amount on the lead, only the lead flipped to `payment-confirmed` — the second room stayed `payment-uploaded` and the dashboard kept showing the second card. The staff had to verify a second time on the second card. The same shape of bug lived in `handleAddPayment` (the staff-new-payment path) and in `handleRejectPayment` (the rejection path).

- **The dashboard groups children of a `reservationId` into a single `PendingPaymentItem`.** The new `useMemo` at `DashboardPage.tsx` builds a `Map<reservationId, Booking[]>` keyed by `booking.reservationId || \`legacy:${booking.id}\``, sorts each group by `reservationPosition` (the FOL-05 lead is the first child = the lowest position), and emits one `PendingPaymentItem` per group. The item carries reservation-scope `totalPrice` (from the `Reservation` header, falling back to the children-sum for the cold-start race), `paidAmount` (from the `collectionGroup("payments")` aggregate, MRB-12's wire, falling back to the in-memory `onsitePayments` sum), and `dueAmount` (= `totalPrice - paidAmount`). The room breakdown lives in `rooms[]` (per-room `{ bookingId, roomNumber, roomType, totalPrice, status }`). The card renders one row per item with the `R-YYYYMMDD-NNNNN` reservation ref + a `{N} rooms` chip + the reservation-scope total/paid/due. Legacy N=1 paths render as a single-row item keyed by the lead's `bookingId` — byte-equivalent to the pre-FOL-05 surface.

- **The verify modal pre-fills the amount to the reservation-scope `dueAmount` and shows a per-room coverage preview.** The new `verifyScope` state (`PendingPaymentItem | null`, `null` for the N=1 / legacy case) carries the reservation-scope context. The `openVerifyForm(item)` action sets `verifyTarget` to the lead booking (the verify handler still takes a `bookingId`) + sets `verifyScope` to the item + pre-fills `verifyAmount` to `item.dueAmount`. The modal renders a "Coverage preview" panel listing each room with a "Cleared" / `{N} still owed` / "Pending" badge that updates live as the staff edits the amount. The preview is a CLIENT-SIDE approximation; the server is the source of truth (a fresh `runTransaction` reads the live state on submit).

- **The server's three payment-handlers gain a sibling-flip pass that mirrors the FOL-03 check-in / check-out pattern.** **(1) Pre-read the children for the reservation BEFORE any writes** — `adminDb.collection("bookings").where("reservationId", "==", bookingReservationId)` is hoisted into the read phase of the `runTransaction` (after the existing payments-snapshot read, before the first write). **(2) Compute the per-child post-update statuses** — for verify / add-payment, the rule is "if the child's current status is `pending` or `payment-uploaded` AND the new cumulative reservation payments cover its `totalPrice`, the post-update status is `payment-confirmed`"; for reject, the rule is "every child currently in `payment-uploaded` flips to `pending`". The post-update array's name is `postUpdateChildStatuses` (FOL-03's same-name convention). **(3) Queue per-sibling `transaction.update` writes** — each flipped sibling gets its own `transaction.update(bookings/{id}, { status: "payment-confirmed" / "pending", paymentConfirmedAt: now / paymentRejectedAt: now, handledBy: staffUid, holdExpiresAt: ..., updatedAt: now })` call. The target's own update is queued separately above. **(4) Update the reservation header's `paymentStatus` via the N>1 aggregate** — `paymentStatus: computeReservationAggregatePaymentStatus(postUpdateChildStatuses)`, not the pre-FOL-05 single-child mapper. The `if (fullyPaid && bookingReservationId.length > 0)` and `if (transitionedToPaymentConfirmed && bookingReservationId.length > 0)` guards are REMOVED — the FOL-05 mirror fires on EVERY verify / add for new reservations (a partial that flips zero siblings still leaves the aggregate unchanged, and a partial that flips N siblings correctly surfaces the new aggregate). The new guard is `if (bookingReservationId.length > 0 && siblingChildBookings.length > 0)`.

- **The status check is reservation-aware.** The pre-FOL-05 verify handler threw `ALREADY_CONFIRMED` whenever the target was `payment-confirmed` or `confirmed`. For N>1 with the lead already past the money gate + flippable siblings, the FOL-05 check proceeds: the target's own status update is skipped (its post-update status equals its pre-update status), but the sibling-flip pass still runs. N=1 + no flippable siblings throws `ALREADY_CONFIRMED` (preserves the pre-FOL-05 contract for the legacy surface). The same relaxation applies to `handleRejectPayment` (the lead may already be `payment-confirmed` and the staff wants to walk back the still-`payment-uploaded` siblings).

- **The `siblingFlippedCount` / `siblingRejectedCount` field on the 200 OK response surfaces the flip count to the admin UI.** The post-verify success modal renders a "X more rooms cleared — {reservationRef}" breadcrumb when the count is > 0. The post-reject toast renders a similar breadcrumb. The bell panel emits a separate `payment` notification with the same breadcrumb (the post-FOL-05 dual-notification surface mirrors the pre-FOL-05 single-notification surface, just with the additional sibling-flips notification appended).

- **N=1 + legacy null-`reservationId` paths are byte-equivalent.** A N=1 reservation produces a single-element `postUpdateChildStatuses` array; the aggregate is the same answer the pre-FOL-05 single-child mapper returned (`mapBookingStatusToReservationPaymentStatus(status)` for N=1). A legacy booking has `bookingReservationId === ""` and skips the pre-read + the sibling-flip pass + the header mirror entirely; the pre-FOL-05 contract for the legacy surface is preserved.

- **Why one click verifies the whole reservation, not a per-room sub-step.** The actual money is held at the reservation scope post-MRB-04 Phase 2.x (one payment record at `reservations/{id}/payments/{paymentId}`); the per-room status flips are bookkeeping. A per-room sub-step modal would force N staff clicks for the same end state, with no upside (one GCash / bank transfer covers the whole reservation, so the ref + method are the same for every room). The FOL-05 contract is "one click = whole reservation, with a per-room coverage preview in the modal so the staff sees the math".
